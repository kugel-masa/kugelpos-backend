# クライアント持ち回りカート（phase 2）

対象: issue #156 / spec `specs/156-stateless-cart/`。phase 1（issue #148、署名付きスナップショットの発行）を前提とする。

## 概要

POS が**変更系リクエストのたびに署名付きカートスナップショットを同梱**し、バックエンドはそれからカートを再構成して処理する。サーバ側カートキャッシュは「正」ではなくなり、Redis のタイムアウトや split-brain による取引消失が構造的に発生しなくなる。

phase 1 の restore API（明示復元）は、この方式に機能的に包含されるため撤去された。

## リクエスト形式

変更系エンドポイントは、本体を封筒で包んだ形を受け付ける。

```json
{
  "signedSnapshot": { "kid": "v1", "cart_document": { ... }, "signature": "..." },
  "payload": [ { "itemCode": "49-01", "quantity": 2 } ]
}
```

ミドルウェアが `signedSnapshot` を剥がして `payload` だけをエンドポイントに渡すため、既存のエンドポイント定義（`list[Item]` など）は変更されていない。

スナップショットを含まない従来形式のリクエストも受け付ける（後述の DUAL モード）。

### 圧縮リクエスト

スナップショット同梱でリクエストが大きくなるため、圧縮されたリクエストボディを受け付ける（FR-009）。

| 項目 | 内容 |
|---|---|
| 対応エンコーディング | `gzip` / `deflate` / `br`（.NET 8 が標準対応） |
| ヘッダ | `Content-Encoding: gzip` |
| ボディ上限 | `MAX_REQUEST_BODY_BYTES`（cart の既定は 4MB） |
| 上限超過 | `413`（コード `401509`）。展開しきる前に打ち切るため、小さな偽装ボディでメモリを枯渇させられない。非圧縮ボディも同じ上限で読むため、圧縮しないことは回避手段にならない（#195） |
| 未対応エンコーディング | `415`。連鎖指定（`gzip, br`）も対象 |

圧縮は任意で、非圧縮リクエストは従来どおり動作する。実測では 50 明細で生 50KB が gzip 3.6KB / brotli 2.9KB になる。

圧縮が節約するのは帯域であって上限枠ではない。上限は展開後サイズで判定するため、非圧縮で拒否される取引は圧縮しても同じサイズで拒否される。稼働スタックでの実測では、999 明細（全て別 SKU）の取引が運ぶスナップショットは 894KB（うち 55% が商品マスタの写し）で、gzip 後は 19KB。上限 1MB のとき、圧縮の有無にかかわらず 1,221 明細で拒否された。

## 移行モード

環境変数 `CART_REQUEST_SNAPSHOT_MODE` で切り替える。

| 値 | 挙動 |
|---|---|
| `DUAL`（既定） | スナップショットなしのリクエストも受け付け、サーバ側キャッシュ経路で処理する |
| `REQUIRED` | スナップショットなしの変更系リクエストを拒否する（`401508`）。全クライアントの移行完了後に切り替える |

## 取引番号の体系

phase 2 で **`transaction_no` は営業回数ごとの連番（seq）** になった。営業回数（`business_counter`）は端末オープンごとに増える単調増加値で、`transaction_no` はオープンのたびに振り直される。

**取引の一意キーは `(tenant_id, store_code, terminal_no, business_counter, transaction_no)`** であり、`transaction_no` 単独では取引を特定できない。

| 経路 | transaction_no | receipt_no | 取引日時 |
|---|---|---|---|
| ステートレス（スナップショット + finalize context 同梱） | クライアント持ち込み（seq） | クライアント持ち込み | クライアント打刻 |
| DUAL / 従来（context なし） | サーバ採番 | サーバ採番 | サーバ時刻 |

クライアントが採番を持ち込むのは、**再送された精算がどのバックエンドで処理されても同じ番号・同じ時刻になる**ようにするため。重複した精算は下流（report / journal / stock）で `cart_id` により1件に収束する。

採番の整合性はユニークインデックスで担保される。同じ `(business_counter, transaction_no)` の二重登録は DB が拒否する。

### 営業回数の持ち回り

`business_counter` と `receipt_no` は端末が所有する。オフラインセッション中に端末側で進む可能性があるため、端末オープン時に `max()` で調整され、オフラインで使われた値が再利用されることはない（欠番は許容）。

持ち込み値には上限がある。調整が不可逆なため、壊れた値で採番空間を焼き切られないよう、スキーマ上の絶対上限と、保存値からの跳躍幅の両方を検証する。

## 取消と返品の適用範囲

両者は意図的に射程が異なる。

| | 対象範囲 | 理由 |
|---|---|---|
| **取消（void）** | 自端末・当日・現在の営業回数のみ | ドロアと当日の売上が open な状態で売上を打ち消す操作のため |
| **返品（return）** | 同一テナントの任意の店舗・端末・過去の営業回数 | 客がレシートを持ち込む店舗を選べるため |

過去の取引を取り消そうとすると `400`（`401514`）で拒否され、返品を使うよう案内される。

返品取引そのものは**実施した端末に帰属**する（元取引の店舗・端末ではない）。元取引は `origin` フィールドに店舗コード・端末番号・営業回数・取引通番の4点で記録される。

### 元取引の特定

`transaction_no` が営業回数ごとに振り直されるため、取引照会・取消・返品の各 API は `business_counter` をクエリパラメータで受け付ける。

- **返品**: 他店舗・過去の営業回数を対象にできるため、既定値が存在しない。省略して複数該当した場合は `409`（`401513`）で拒否される
- **取消**: 現在の営業回数しか対象にできないため、省略時は現在の営業回数が既定値になる

レシートには元取引の特定に必要な4項目（店舗コード / レジNo. / 営業回数 / 取引通番）が印字される。

## 冪等性

精算の重複は `cart_id` を軸に収束する。

- **cart**: 挿入前に `cart_id` で既存を検索し、同一の精算の再送であれば既存の取引ログを返す。別の操作が同じ `cart_id` を使い回した場合は `409`（`401511`）
- **report / journal / stock**: `cart_id` で先勝ちスキップ。重複配信は1件に収束する
- **DB レベル**: `tran` / `stock_updates` に `cart_id` の部分ユニークインデックス

## インデックス移行

**実行契機はテナント作成 API（`POST /api/v1/tenants`）のみ**であり、アプリ起動時には走らない。新規テナントは作成時にこの手順を通るが、**既に存在するテナントには自動では適用されない**。本番稼働後に本機能を導入する場合は、既存テナントに対して移行を実行する手立てを別途用意すること。

移行の中身は次のとおり。

1. 旧ユニークインデックス（`business_counter` を含まないもの）を削除
2. 新インデックスを作成
3. **最終状態を検証し、達成できていなければ `DatabaseException` で起動を中止**

黙って失敗すると、古いユニークインデックスが精算を阻んだり、`cart_id` の重複排除インデックスが欠けたまま正常に見えたりするため、明示的に落とす設計になっている。

`status_tran` については、新しいユニークキーを強制する前に**データ移行**が走る。既存レコードは参照先の取引から営業回数を取り込む。「営業回数が一致 or 未設定」で照合する方式は採れない（従来の `transaction_no` と `seq` はどちらも1始まりで値域が重なるため、当セッションの `seq=1` が端末の最初の取引を拾ってしまう）。

## レシート採番 (issue #166)

端末が持つのは**通算カウンタ 1 本**（`receipt_counter` = 確定した取引の通算数）で、印字するレシート番号はそこから導出する。

```
receipt_no = RECEIPT_NO_START_VALUE + ((receipt_counter - 1) mod レンジ幅)
```

巻きを導出側に置くことで open 時の突合が成立する。カウンタは増える一方なので `max(保存値, 提示値)` が有効な比較になるが、印字番号は巡回するため `max(999999, 111111)` は巻き戻りを恒久的に打ち消してしまう。

| 値 | 持ち主 | 動くタイミング |
|---|---|---|
| `receipt_counter` | 端末（耐久ホームは terminal service） | 取引を確定するたび |
| `receipt_no` | 導出値（端末には保存しない） | カウンタに従い、レンジ内で巻く |
| レンジ（`RECEIPT_NO_START_VALUE` / `RECEIPT_NO_END_VALUE`） | master-data 設定 | 運用者が変更したとき |

クライアントはレンジを他の端末設定と同様に master-data から取得し（`GET /tenants/{tenant_id}/settings/{name}/value`）、カウンタは open 時に端末トークンの `receipt_counter` クレームで受け取る。テナント初期化時に `RECEIPT_NO_START_VALUE` / `RECEIPT_NO_END_VALUE` を既定値でシードするため、この取得は必ず応答する（#174）。設定が無い場合サービスは自身の設定にフォールバックするが、その値は API からは見えず、クライアントはバックエンドが採番に使うのと同じレンジを見る必要があるため。次の open で自分の高水位を提示し、`max()` で突合されるため、オフラインセッション中に使った番号が再発行されることはない。

**carried 経路での不変条件**: `1 tranlog = 1 seq = 1 receipt_counter = 1 印字番号`。カートを放棄した場合は番号を消費しない。

**取引中止も確定の一種**であり、同じ規則に従う（#170）。取引ログを書きレシートを印字するため、`POST /carts/{cart_id}/cancel` は `bill` と同じ finalize context を運び、端末の系列から番号を 1 つ消費する。これがないと中止取引はサーバー側カウンタで採番され、その `transaction_no` は carried な per-open `seq` と `(business_counter, transaction_no)` の番号空間を共有するため衝突しうる。

**欠番**は許容するが、発生源は 3 つに限られる。端末交換時の安全ジャンプ、オフラインで確定した取引が届かなかった場合、突合で保存値の方が高かった場合。通常運用では発生しないため、`receipt_counter` の穴は調査に値するシグナルとなる。

`receipt_counter` は取引ログにも記録する（非ユニークインデックス）。印字番号は一周すると順序づけできず、`111115` がどの周回のものか判別できないため。**取引の同一性キーではない**——重複排除は `cart_id` で行う。

#166 以前のクライアントもそのまま動作する。カウンタを持たず、open では旧来の `receipt_no` 名で同じ値を送り（1, 2, 3 と巻かずに数えていた＝通算値そのもの）、レシート番号は送られた値のまま記録される。

## 巻き戻しは受け入れ、事後に可視化する (#165)

署名が証明するのは「サーバーが発行したまま改変されていない」ことであって、「それが**最新**である」ことではない。ステートレス経路ではサーバーが意図的にキャッシュを参照しないため、同一カートの最新エンベロープと以前のものを区別する材料が他にない。古いエンベロープを同期的に拒否するには、カートごとの高水位をサーバーが知る必要があり、それはリクエストごとの書き込み——phase 2 が取り除いたもの——を復活させることになる。

そこで巻き戻しは受け入れたうえで、**発見可能**にする。カート文書は単調増加の `revision` を持ち（署名の対象）、スナップショットを発行するたびに進む。

```
作成 → revision 1 → 明細追加 → revision 2 → 明細追加 → revision 3
```

リクエストが**提示した** revision は、そのリクエストログに専用フィールド `snapshot_info` として記録する（ボディではない——ボディはログミドルウェアが除去する、#155）。

```json
"snapshot_info": {"cart_id": "…", "revision": 3, "schema_version": 2, "kid": "v1"}
```

通常運転では厳密に増加し、lost-ACK の再送は同じ値を繰り返す。**下がる**のは古いエンベロープを再生した場合だけで、`snapshot_info.cart_id` を `request_info.accept_time` 順に並べるクエリで直接見つかる（そのためのインデックスがある）。

このインデックスを作るのはテナントセットアップであり、起動時には作られない。したがって既存テナントがある環境では、テナントごとに `POST /api/v1/tenants/{tenant_id}` を一度流し直すまで、上記のクエリはインデックスではなくコレクションスキャンになる。インデックス作成は冪等で、#156 が自身のインデックスに必要としたのと同じ手順である。

発行するエンベロープは `schema_version` 2。バージョン 1 も引き続き受理する——移行していないクライアントが提示するものであり、拒否するとスナップショットが存在する理由であるフェイルオーバー自体が壊れるため。その場合は記録すべき revision が無いだけである。

仕組み上の注意: エンベロープを剥がすミドルウェアはリクエストログの**外側**で動くため、ログを書く時点でエンベロープは既に無い。peel 側がスカラーだけをリクエストスコープに残し、ログ側が拾う。

1 つのカートの中で経路を切り替えるケースが、以前はこの検出をすり抜けていた。持ち回り経路は何も書かないため、持ち回りで積み上げたカートに対してキャッシュは**作成時のまま**残る。そこにスナップショット無しのリクエストが 1 本混ざると、その古い状態から続行され——間の変更をすべて落としたうえで、**正当に署名されたスナップショット**を返す。その後もう一度キャリーすれば提示 revision が下がるので**時々は**見えるが、そのままキャッシュ経路に留まれば痕跡は一切残らない。

これは検出ではなく**不可能**になった（#192）。次節を参照。

## 1 つのカートに 1 つの経路 (#192)

経路はリクエストごとに、スナップショットが付いているかどうかだけで選ばれる——つまり 1 つのカートが両方を使うことを妨げるものが無かった。クライアントはカートを開く時点で、どちらで動くかを宣言する。

```json
POST /carts   {"transactionType": 101, "carrySnapshot": true}
```

`carrySnapshot: true` のカートは**キャッシュに一切書かれない**——作成時すらも。作成は「持ち回るものがまだ無く、クライアントがどうするかサーバーに分からない」ため、唯一必ず書いていたリクエストだった。書かなければ、スナップショット無しのリクエストが続行する古いコピーが存在せず、カートそのものが見つからない。

```
carrySnapshot=true    持ち回り → 200      スナップショット無し → 404 (401002)
carrySnapshot=false   持ち回り → 409 (401515)   スナップショット無し → 200
```

**両方向とも拒否する。**失われるものが同じだからである。キャッシュ経路を宣言しておいて持ち回ると、カートが進む間キャッシュのコピーが取り残され、反対側から同じ静かな消失に至る。

宣言は**署名されたカート文書に載る**ので、確認にキャッシュ読み取りは要らない——スナップショット自身が「このカートはどちらで開かれたか」を語る。このフィールドが存在する前に作られたカートはどちらとも言わず、素通しする（デプロイをまたいで進行中のカートはそのまま動く）。

`carrySnapshot` の既定は false で、これはこのフィールドを知らないクライアントが送らないことの意味そのものである。`CART_REQUEST_SNAPSHOT_MODE=REQUIRED` では宣言は不要——すべての mutation が持ち回る以上、キャッシュのコピーは読まれようがなく、書かれもしない。

## DUAL モード中は採番系列が 2 本ある (#168)

確定経路の分岐は**端末単位ではなく取引単位**である。

| リクエスト | 採番元 |
|---|---|
| finalize context を運ぶ | 端末の通算カウンタ `receipt_counter` |
| 運ばない | cart 自身の `terminal_counter` コレクション |

スナップショット署名が縮退した phase 2 端末にはスナップショットが発行されないため、何も運べず、次の売上が**もう一方の系列**で採番される。その系列は端末がどこまで進んでいるかを知らないため、**端末が既に発行したレシート番号を再び印字しうる**。

未設定・不正な鍵はここには到達しない。使える鍵がなければサービスが起動を拒否するようになったため（#192）。残るのは、読み込みには成功して署名時に失敗する鍵で、これはここに同じ形で現れる——検知はそのために残してある。

これは**遮断せず検知する**。鍵の設定ミスで店舗の販売を止める方が有害であり、採番の整合性に対する本システムの姿勢は「強制ではなく監査検知」だからである（spec 156 Q58）。端末が自前の系列を持っているのにサーバー系列で採番された確定は ERROR ログを出し、

```
Finalize numbered from the server-side series while the terminal has its own
(issue #168): cart_id=… reason=signing_degraded terminal_receipt_counter=…
```

リストア監査証跡（`log_cart_restore`）に `numbering_fallback` レコードを書く（`reject_reason` はどの条件で発火したかを示す——`signing_degraded` / `snapshot_without_finalize_context` / `no_carried_context`）。

1 つだけ意図的に検知できないケースがある。まだ 1 件も採番していない phase 2 端末が、署名は正常でスナップショットも運ばずに確定した場合、phase 1 端末と完全に見分けがつかない。open は全端末のカウンタを 0 でシードするため、0 を「自前の系列を持つ」と扱うと**すべてのレガシー確定をインシデントとして報告してしまう**。

`CART_REQUEST_SNAPSHOT_MODE=REQUIRED` にすればこの窓は完全に消える（スナップショットなしの更新系リクエストが拒否されるため、落ちる先の系列が存在しない）。それまでは、署名鍵の縮退は修正すべきインシデントであり、起動ログだけでなく**取引単位で可視化される**ようになった。

## 署名は機能ではなく要件 (#192)

カートをクライアントだけが保持できるようになった以上、署名のないレスポンスは
「おまけが欠けた」ではなく「カートを失った」を意味する。クライアントの手元には
何も指さない `cart_id` だけが残り、サーバにも探す先はない。だから回避策ではなく、
その状況自体を無くす。

**使える署名鍵が無ければサービスは起動しない。** 未設定・不正・32 バイト未満の
いずれも起動時にプロセスを止める。正しく応答できないリクエストを受け付けさせない
ためである。本リポジトリにコミットされている鍵も同様に拒否する——署名も検証も
通るため、他のあらゆるシグナルが健全に見えたまま署名が何も守らない状態になる。
`SNAPSHOT_ALLOW_INSECURE_KEY=true` で開発用スタックだと明示した場合のみ許可する。

起動時に見えない場合が 1 つだけ残る。読み込みには成功して署名時に失敗する鍵である。
持ち回りカートのレスポンスがスナップショット無しになった場合は、署名なしで返さず
**503（`401507`）** で拒否する。拒否しても失われるものは無く、クライアントは
再送で回復できる。

- 持ち回りリクエストはカートの状態を一切書かないため、手元のスナップショットを
  付けた再送は同じリクエストにすぎない
- 確定（finalize）は書き込むが、`cart_id` で冪等（#170）なので、再送は既に記録済みの
  取引を返す

**再送であって、打ち直しではない。** 確定はレスポンスを組み立てる前に取引を記録して
パブリッシュするため、クライアントが失敗と伝えられた時点で売上は既に存在する。
打ち直すと `cart_id` が変わり、重複排除は `cart_id` で行うため**2 件目として記録される**。
この 503 は返しうる全ルートの OpenAPI に宣言してあるので、生成クライアントは
このドキュメントを読まなくても契約として認識できる。

サーバがキャッシュに保持しているカートは影響を受けない。そのスナップショットは
利便性であり、フィールドは null になり、操作自体は成功する。

## 設定

| 環境変数 | 既定値 | 内容 |
|---|---|---|
| `SNAPSHOT_HMAC_KEYS` | 未設定 | スナップショット署名鍵。**必須——未設定ではサービスが起動しない**（#192）。32 バイト未満の鍵も拒否する。運用は [鍵ローテーション手順](../cart-snapshot-key-rotation.md) を参照 |
| `SNAPSHOT_ALLOW_INSECURE_KEY` | `false` | 本リポジトリにコミットされている署名鍵での起動を許可する。ローカル開発専用——この鍵は署名も検証も通るため、リポジトリを読める者は任意の価格のスナップショットを作れる |
| `CART_REQUEST_SNAPSHOT_MODE` | `DUAL` | 移行モード（上述） |
| `MAX_REQUEST_BODY_BYTES` | `4194304` | リクエストボディ上限（圧縮の有無を問わない）。カート自身の予算（下記）もこの値から導出される。他サービスの既定 1MB より大きいのは、運ばれるカート文書が cart の最大の正当なボディだから（#195） |
| `REQUEST_DECOMPRESS_MAX_BYTES` | 未設定 | 上記の旧名。設定されていれば引き続き有効で、新名より優先される（既存デプロイが黙って既定値に戻らないようにするため） |
| `REQUEST_LOG_STRIP_FIELDS` | `signedSnapshot,signed_snapshot` | 共通（commons）設定。リクエストログでマーカーに置き換えるボディフィールド。運ばれるスナップショットを毎リクエスト保存しないための措置（#155） |
| `REQUEST_LOG_MAX_BODY_BYTES` | `32768` | 共通（commons）設定。ログに残すボディのサイズ上限 |

## カートはクライアントが送り返せる範囲に収まる

スナップショットはサーバが発行し、クライアントが次の mutating リクエストで提示するため、`MAX_REQUEST_BODY_BYTES` に縛られる。一方でカート自身には上限が無かったので、十分に大きなバスケットでは端末が「送り返せないエンベロープ」を持たされ、以降の全リクエストが `413`、`REQUIRED` モードでは会計も取消もできなくなっていた（#200）。

明細の追加と、明細／小計への値引追加は、スナップショットが **`MAX_REQUEST_BODY_BYTES` の 60%** を超えるなら `409`（コード `401516`）で拒否する。いずれもリクエストからリストを受け取って append する経路で、長さにも送信回数にも上限が無いため。支払・会計・明細取消・数量/単価変更は**意図的に対象外** — カートを締めるか小さくする操作であり、これを拒否することこそがこのガードが防ごうとしているデッドロックだから。明細数からの推定ではなく**実際に発行されるスナップショットを測る** — 1 明細のコストは同梱される商品マスタに左右されるため。拒否は**何も確定する前**に行うので、カートは追加前のまま残り、そこまでで会計を締めて残りを別取引にできる。

予算の 80% で warning をログに出す。レジより先にログが知らせるための位置づけ。

既定の 4MB では、別 SKU で約 2,800 明細が上限、警告は約 2,260 明細。実測では 999 明細の取引が 894KB なので十分内側にある。

## 撤去された API

| 撤去 | 代替 |
|---|---|
| `POST /api/v1/carts/{cart_id}/restore` | 操作リクエスト自体にスナップショットを同梱する（再構成されるため、事前の明示復元が不要） |
| `GET /api/v1/carts/{cart_id}` | クライアントがスナップショットとしてカートを保持するため、サーバから読む必要がない |

DUAL モードはスナップショットなしの**変更系**リクエストを受け付け続けるが、この2つのエンドポイントは復活しない。
