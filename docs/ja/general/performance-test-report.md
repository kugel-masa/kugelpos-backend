## テスト 5: Redis activedefrag + THP 無効化

**日付**: 2026-04-07
**目的**: Redis のメモリフラグメンテーション対策の効果を検証
**コード**: main（変更なし）
**Redis**: RDB 有効 + `activedefrag yes`
**OS**: THP（Transparent Huge Pages）を `never` に設定

### 変更内容

```bash
# Redis activedefrag 有効化
docker exec redis redis-cli CONFIG SET activedefrag yes

# THP 無効化 (madvise → never)
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/enabled
```

#### activedefrag

Redis がアイドル時にメモリフラグメンテーションを自動修復する機能。デフォルトは無効。有効にすると `mem_fragmentation_ratio` が高くなった際に自動的にメモリ再配置を行う。

#### THP (Transparent Huge Pages) とは

Linux のメモリ管理機能で、通常の 4KB ページの代わりに 2MB の大ページを自動的に使う仕組み。大きなメモリを連続的に使うアプリケーションでは TLB キャッシュヒット率が上がり高速化するが、**Redis では逆効果**になる。

Redis は小さなメモリ領域（カートドキュメント1個 ≒ 16KB）を頻繁に確保・解放する。THP 有効時は以下の問題が生じる:

- Redis が 16KB 書き換え → OS は **2MB ページ全体**を COW コピー（4KB なら 4ページで済む）
- RDB fork 時に COW の単位が 2MB になり、メモリ使用量が急増
- 4KB の変更に対して 2MB のコピーが発生 = **約500倍のオーバーヘッド**

| 設定値 | 動作 | Redis との相性 |
|--------|------|---------------|
| `always` | 常に大ページを使用 | **悪い** |
| `madvise` | アプリが明示的に要求した場合のみ（Redis は要求しない） | 影響小 |
| `never` | 大ページを使わない | **Redis 推奨** |

今回の環境は `madvise` → `never` への変更のため影響は小さい。`always` からの変更であれば大きな差が出る可能性がある。

| **Aggregated** | **98** | **42** | **380** | **870** | **89.49** |

### 9-4: 原因特定 — log_requests ミドルウェア

調査の結果、`kugel_common/middleware/log_requests.py` の以下のコードが原因と判明:

```python

```

- 全 HTTP リクエストに対して `asyncio.create_task()` で MongoDB に fire-and-forget 書き込み
- 1リクエストにつき 2回 insert（commons DB + tenant DB）= 毎秒 ~200 個のタスク発火
- タスクの完了より発火が速いため、未完了タスクが蓄積
- イベントループのスケジューリングコストが増大し、リクエスト処理自体が遅延
- MongoDB のデータ蓄積（5回テストで 163K件/645MB）で insert も遅延し、悪循環が加速

| 10-15分 | 52.5 | 21 | 227 | 398 | 107.2 |
| 15-20分 | 57.8 | 22 | 245 | 450 | 105.7 |

前のテストの蓄積が次のテストの開始時点に引き継がれている。

## 結論と今後の方針

### 順序効果の原因

`log_requests` ミドルウェアが `asyncio.create_task()` で毎秒 ~200 回の MongoDB insert を
fire-and-forget で発火。タスク完了より発火速度が上回り、未完了タスクが蓄積。
イベントループのスケジューリングコストが増大し、データ蓄積による insert 遅延と相まって
悪循環的に劣化する。

### パフォーマンステストへの影響

パフォーマンステストは本番業務のレスポンスタイムを測定する目的であり、
リクエストログの DB 書き込みはテスト対象の業務処理ではない。
テスト時は `REQUEST_LOG_TO_DB=false` を設定し、ログ書き込みによるノイズを排除することを推奨。

### 本番環境への対策（未実施・検討中）

| 対策 | 状態 | 効果 |
|------|------|------|
| バッチ書き込み（insert_many） | 実装済み・未マージ | create_task 頻度を 1/100 に削減 |
| unique 制約削除 | コード修正済み・未マージ | 一意性チェックのオーバーヘッド削減（効果小） |
| REQUEST_LOG_TO_DB 環境変数 | 実装済み・未マージ | テスト時の DB 書き込み無効化 |

本番では「バッチ書き込み」が有力だが、長時間（25分以上）で悪化する傾向があり、
バッチサイズ・タイマー間隔のチューニングが必要。
代替案として Dapr pub/sub によるプロセス分離や、ファイルログからのバッチ取り込みも検討対象。

## テスト 24: 非同期 insert_many (create_task fire-and-forget)

**日付**: 2026-04-10
**目的**: バッチ書き込みの insert_many を await（同期）から create_task（非同期 fire-and-forget）に変更し、レスポンス時間への影響を検証
**変更**: `_flush_unlocked()` 内の DB 書き込みを `asyncio.create_task(self._write_to_db(db_docs))` で非同期化。shutdown 時のみ await で同期書き込みを維持

2. **cart メモリリークなし**: 10分で ~810MB に到達後、180分間プラトー維持（810±15MB）
3. **MongoDB 安定**: WiredTiger キャッシュ内で安定（~1,480MB、周期的に ~1,580MB のスパイクあり）
4. **Redis 線形増加**: カートキャッシュの蓄積で ~4.7MB/分の線形増加。本番環境では TTL 設定または定期的な FLUSHALL が必要
5. **ホスト空き 960MB**: 8GB環境では180分が安全な運用上限。Redis の蓄積が OOM リスクの主因

## テスト 26: Redis maxmemory 1GB + スワップ4GB 長時間テスト

**日付**: 2026-04-10〜11
**目的**: 8GB環境の長時間運用限界を検証。Redis maxmemory による eviction 挙動とスワップによる OOM 回避効果を確認
**変更**: Redis に `maxmemory 1gb --maxmemory-policy allkeys-lru` を設定。ホストに 4GB スワップファイルを追加
**構成**: cart:6w, md:2, t:1（8GB環境）/ buffer=100
**条件**: 300 users / 360分（目標）/ DB クリア（`down -v`）

### パフォーマンス結果

| Endpoint | Reqs | Fails | P50 | P95 | P99 | Max | req/s |
|----------|------|-------|-----|-----|-----|------|-------|
| Create Cart | 105,934 | 0 | 90 | 160 | 230 | 3,200 | — |
| Add Item | 2,113,621 | 228 | 15 | 55 | 87 | 2,500 | — |
| Cancel Cart | 105,424 | 0 | 220 | 320 | 450 | 3,300 | — |
| **Aggregated** | **2,324,979** | **228 (0.01%)** | **16** | **150** | **260** | **3,300** | **107.6** |

- **稼働時間**: 345分（目標360分に対し96%）
- **エラー**: 228件、02:25 に集中発生（開始から約345分後）

### エラー詳細分析

#### エラー概要

全228件が **Add Item の 404 エラー**: `Failed to get cached cart, cart_id: xxx: cart not found (collection_name->cache_cart)`

- **evicted_keys**: 56,746件（テスト終了時）
- **発生期間**: 02:25:26〜02:25:42 の **わずか16秒間** に集中

#### エラー発生タイムライン

```
02:25:26  最初のエラー（4件/秒）
02:25:30  エラー加速（48件/秒）
02:25:36  最大バースト（66件/秒）
02:25:42  最後のエラー（2件/秒）
```

#### 失敗した item 番号の分布

| item番号 | 件数 | 意味 |
|:--------:|:----:|------|
| 2 | 70 | カート作成直後の2品目で失敗（最多） |
| 3 | 68 | 同上、3品目 |
| 4〜7 | 22〜36 | 序盤 |
| 8〜20 | 8〜26 | 中盤以降 |

**item 2〜3 が最多** — Create Cart 直後のカートが evict された。LRU では最も新しいキーが最後に削除されるはずであり、**異常な eviction 動作**。

#### 根本原因: スワップ環境下での Redis eviction の異常動作

テスト終了後の調査で以下が判明:

1. **カートキーのサイズは小さい**: 1キーあたり ~6KB（2〜7KB）
2. **288キー × 6KB = ~1.7MB** だが、Redis の `used_memory` は **636MB**
3. **`mem_fragmentation_ratio`: 0.62** — Redis の報告メモリ（667MB）に対し、物理 RSS（394MB）が大幅に小さい

これは **Redis のデータがスワップに退避されている** ことを示す。Redis はインメモリDBであり、スワップ環境での動作は保証されていない。

**推定メカニズム**:

```
1. テスト継続により Redis メモリが 1GB に到達
2. eviction 開始 → 981MB → 135MB に急減（大量一括削除）
3. eviction 後、Redis メモリが再び増加（新規カート作成）
4. この時点でホストの物理メモリは枯渇、Redis データの一部がスワップ上に存在
5. LRU 判定時にスワップ上のデータへのアクセスが遅延
6. 345分時点で再度 eviction が発生した際、スワップスラッシングにより
   LRU の判定精度が低下し、最近作成されたカートも evict 対象に
```

#### Dapr state store のキー構造

- Dapr の cartstore は `databaseIndex: 2` を指定しているが、実際のキーは **DB0** に格納されていた
- キー形式: `cart||{cart_id}`（Dapr のプレフィックス付き）
- `maxmemory` は Redis インスタンス全体（全DB合計）に適用されるため、DB 分離は eviction の保護にならない

### メモリ推移（5分間隔サンプリング）

| 経過 | cart (MB) | MongoDB (MB) | Redis (MB) | フェーズ |
|------|----------|-------------|------------|---------|
| 0分 | 457 | 267 | 21 | 開始 |
| 21分 | 841 | 1,463 | 111 | 安定期 |
| 84分 | 782 | 1,428 | 411 | cart がスワップへ退避開始 |
| 147分 | 714 | 1,436 | 710 | |
| **211分** | **672** | **1,487** | **981** | **Redis 1GB 直前** |
| **243分** | **691** | **1,466** | **135** | **eviction 開始 → Redis 急減** |
| 306分 | 715 | 1,458 | 427 | eviction 継続しつつ正常運用 |
| **345分** | — | — | — | **処理中カートが evict → テスト失敗** |

テスト終了時: スワップ使用 3,340MB / 4,095MB

### スワップなし（テスト#26中断版）との比較

| 項目 | スワップなし | スワップ4GB |
|------|-----------|-----------|
| エラー発生時間 | ~104分 | ~345分 |
| エラー原因 | OOM（ホストメモリ枯渇） | Redis eviction |
| エラー件数 | 165件 | 228件 |
| 延命効果 | — | **約3.3倍** |

### 分析

1. **スワップにより OOM Killer は完全回避** — 8GBメモリを使い切ってもプロセスは生存し、345分まで稼働延長
2. **パフォーマンス劣化は軽微** — スワップ 3.3GB 使用でも Avg 34ms を維持。cart メモリがスワップに退避（841→672MB）されるが、ホットパスは物理メモリに残る
3. **Redis + スワップの組み合わせは危険** — Redis はインメモリDB前提の設計。スワップ上のデータに対する LRU 判定が不正確になり、アクティブなカートが evict される致命的な問題が発生
4. **eviction 後も ~100分間は正常動作** — evict されたカートの大半は既に cancel 済み。2回目の eviction サイクルで処理中カートに当たりテスト失敗

### 結論と推奨

1. **8GB/300users の安全な連続運用時間は ~180分**（スワップなし）、~300分（スワップあり、ただし信頼性に懸念）
2. **Redis にスワップを使わせてはならない** — LRU の判定精度が低下し、処理中データが削除される。本番環境では Redis コンテナに `--memory-swappiness=0` またはホストレベルで `vm.swappiness=0` を設定すべき
3. **Redis maxmemory-policy は `noeviction` を推奨** — eviction でアクティブカートが消えるより、メモリ上限エラーの方がアプリケーションとして制御しやすい
4. **本番環境では Redis を別ホストに分離**し、十分な物理メモリを確保すべき
5. **スワップは OOM 防止の安全弁として有効**だが、Redis 以外のプロセス（cart, MongoDB）に限定すべき

## テスト 27: maxLenApprox 50000 + Redis コンテナメモリ制限 360分テスト

**日付**: 2026-04-11
**目的**: Dapr pub/sub の `maxLenApprox` による Redis Stream trim の効果を検証。8GB環境での6時間安定運用を確認
**変更**:
- pub/sub 3コンポーネントに `maxLenApprox: 50000` を追加（`deleteAfterDeliver` も追加したが、Dapr Redis pub/sub では未サポートのため無効）
- Redis コンテナに `deploy.resources.limits.memory: 1200m` を設定
- ホストに 4GB スワップ有効
**構成**: cart:6w, md:2, t:1（8GB環境）/ buffer=100
**条件**: 300 users / 360分 / DB クリア（`down -v`）

| その他（pub/sub topics, overhead） | ~34MB | |

### スワップ使用状況

| 指標 | 値 |
|------|-----|
| Redis used_memory | 793MB |
| Redis RSS（物理メモリ上） | 665-712MB |
| **スワップ上の Redis データ** | **~80-130MB** |
| mem_fragmentation_ratio | 0.84-0.90 |
| ホストスワップ合計 | 2,775MB / 4,095MB |

Redis のデータの一部がスワップに退避している。現在は eviction が発生しないため影響なしだが、構造的リスクとして残存。

### 発見事項

1. **`deleteAfterDeliver` は Dapr Redis pub/sub に存在しない** — [components-contrib#3100](https://github.com/dapr/components-contrib/issues/3100) で「Redis pub/sub は本番非推奨」と明言。消費済みメッセージの自動削除機能はない
2. **Redis Stream が Redis メモリの ~95% を占める** — cart store（~3MB）に対して Stream が ~750MB。pub/sub 移行で劇的に改善可能
3. **`maxLenApprox` は有効な緩和策** — Stream 件数を固定し、メモリ増加を停止させた。ただし根本解決（Stream 自体の排除）ではない
4. **Redis のスワップ使用は公式が警告する既知の制約** — Redis は `vm.swappiness=0` またはスワップ完全無効を推奨。スワップ上のデータに対する LRU 判定精度が低下するリスクあり
5. **MongoDB WiredTiger キャッシュヒット率 99.65%** — 1.5GB のキャッシュサイズは妥当

### 結論と推奨

1. **`maxLenApprox: 50000` により 8GB/300users で6時間エラー0件を達成** — 暫定的な運用は可能
2. **ただし Redis pub/sub は本番非推奨**（Dapr 公式） — RabbitMQ 移行を推奨（#99）
3. **Redis Stream が全メモリの 95% を占有** — pub/sub 移行で Redis メモリが ~800MB → ~10MB に削減される見込み
4. **冪等性保証の不備を修正すべき** — Report/Journal の無限リトライ（#97）、Stock の在庫2重減算（#98）
5. **最終目標**: pub/sub → RabbitMQ、state store → MongoDB、Redis 撤去

**注: 最終的な適用値は `maxLenApprox: 1000` に変更。** テスト#27 は 50,000 で実施したが、Cart のバックグラウンド再配信ジョブ（5分間隔）との重複リスクを考慮し、`processingTimeout: 180s` と整合する ~5分分のバッファ（1,000件）を採用。Redis メモリは ~750MB → ~15MB に削減される見込み。
