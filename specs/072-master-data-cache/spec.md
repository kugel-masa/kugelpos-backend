## User Scenarios & Testing *(mandatory)*

### User Story 1 — マスタ参照の高速化と外部負荷低減 (Priority: P1)

POS 端末ユーザが商品をスキャンしたり会計を進める際、カートサービスは商品マスタ・支払マスタ・税マスタ等を都度参照する。同じ店舗・同じ端末で同じマスタ項目が短期間に何度も問い合わされても、最初の 1 回以外は近接した記憶領域から即座に応答されるべきである。これにより会計操作のレスポンスが安定し、マスタ管理サービスへの負荷も大幅に減る。

**Why this priority**: 体感速度に直結する最大価値。すべての販売トランザクションが恩恵を受ける。マスタサービスへのトラフィック減によりインフラコスト・障害波及面積も小さくなる。

**Independent Test**: 同一テナント・同一店舗で同一商品コードを連続して引いたとき、初回のみマスタサービスへのリクエストが発生し、2 回目以降は許容時間内（フレッシュネス期間内）はリクエストが発生しないことを確認できる。

**Acceptance Scenarios**:

1. **Given** カートサービスが起動済みでマスタキャッシュが空の状態、**When** あるテナントが商品 A をスキャンする、**Then** マスタサービスへの参照が 1 回発生し、商品 A の内容がカートに反映される。
2. **Given** 上記の直後（フレッシュネス期間内）、**When** 同テナントが商品 A を再度スキャンする、**Then** マスタサービスへの追加参照は発生せず、商品 A の内容がカートに反映される。
3. **Given** 同一テナントに対し並列で複数のカート操作が走り、いずれも商品 A を必要とする、**When** 100 件の操作が同時に流れる、**Then** マスタサービスへの参照はフレッシュネス期間あたり最大 1 回しか発生しない。
4. **Given** フレッシュネス期間が経過した状態、**When** 同テナントが商品 A を再度参照する、**Then** マスタサービスへ再フェッチが発生し、最新値が反映される。

---

### User Story 2 — マスタ更新時の手動でのキャッシュ無効化 (Priority: P2)

業務運用上、マスタ管理者が商品価格や税率を更新したあと、カートサービスのキャッシュフレッシュネス期間を待たずに即時反映したい場面がある。運用担当者（あるいは将来の自動連携処理）は、キャッシュエントリ単位または対象マスタ種別単位で「これ以降は再フェッチしてほしい」と指示できなければならない。

**Why this priority**: 価格変更や緊急の修正に対する即応性に必要。ただし運用頻度は P1 のリードリクエストに比べて大幅に低い。

**Independent Test**: 任意のキャッシュ済み項目に対して無効化操作を呼び出した直後、その項目への次回参照がマスタサービスへの再フェッチを発生させることを観測できる。

**Acceptance Scenarios**:

1. **Given** 商品 A がキャッシュ済み、**When** 商品 A 単独の無効化を呼ぶ、**Then** 直後の商品 A 参照はマスタサービスから取得され、商品 B 等のキャッシュ状態は変化しない。
2. **Given** 商品マスタ種別に多数のエントリがキャッシュ済み、**When** 商品マスタ種別全体の無効化を呼ぶ、**Then** その種別の全エントリは次回参照時に再フェッチされ、他のマスタ種別（支払・税など）は影響を受けない。

---

### User Story 3 — キャッシュバックエンド障害時の継続稼働 (Priority: P2)

キャッシュ用ストアが一時的に不通になっても、POS 端末での会計処理は停止してはならない。カートサービスはキャッシュ参照に失敗した場合でも、マスタサービスに直接問い合わせることで処理を継続する。

**Why this priority**: 可用性に直結。キャッシュは高速化のための補助層であって、止まってはならない販売処理のクリティカルパスではない。

**Independent Test**: キャッシュバックエンドを意図的に停止した状態でカートの主要シナリオを通すと、すべてのマスタ参照が成功し、レジ操作が完了することを確認できる（応答時間は劣化してよい）。

**Acceptance Scenarios**:

1. **Given** キャッシュバックエンドが応答不能、**When** 商品参照を行う、**Then** マスタサービスから直接取得され、操作は成功する。レスポンスは遅くなり得るが、エラーは返らない。
2. **Given** キャッシュバックエンドが復旧した、**When** 次の商品参照が走る、**Then** キャッシュ層が再び使われ、以降の同一参照は高速化される。

---

### User Story 4 — 新マスタリポジトリ追加時の実装コスト削減 (Priority: P3)

カートサービス開発者が将来新しいマスタ参照（例: 顧客マスタ、ロイヤリティマスタ等）を追加する場合、キャッシュロジック・キー設計・無効化 API・直列化処理を一から書く必要はなく、共通基盤を継承して「どこから取得するか」だけを記述すれば、即座に同等のキャッシュ・無効化機能を備えたリポジトリが完成する。

**Why this priority**: 内部 DX 改善であり、ユーザ体験には間接的にしか効かない。ただし保守性に長く効く。

**Independent Test**: 新規マスタリポジトリのコード行数のうち、キャッシュ関連のボイラープレートが含まれていないこと（共通基盤に集約されていること）を静的に確認できる。

**Acceptance Scenarios**:

1. **Given** 共通基盤が導入済み、**When** 新しいマスタ種別のリポジトリを追加する、**Then** 追加コードは「キャッシュ名前空間の宣言」「ドキュメント型の宣言」「単一・リスト取得処理の実装」のみで完結し、キャッシュ取得・保存・キー組み立て・無効化 API・直列化のコードは記述不要である。

---

### Edge Cases

- **存在しないマスタの問い合わせ**: マスタサービスが「該当なし」を返した場合、その不在情報はキャッシュせず毎回マスタソースに問い合わせる（新規登録直後の即時反映を優先）。
- **マルチテナント分離**: テナント A の参照結果がテナント B に漏洩することは決して許されない。キーはテナント単位（必要に応じ店舗単位）で必ず分離されること。
- **同一マスタ種別を異なる経路で参照**: 商品マスタを HTTP 経由と gRPC 経由の 2 系統で取得する実装が併存する場合、両者は同じ論理キーで同じキャッシュエントリを共有しなければならない（経路が違うだけで内容は同一）。
- **リスト系の参照**: 「店舗 X で有効な販促一覧」のようなリスト結果と「商品コード Y 単独」のような単独結果は、別々のキャッシュエントリとして扱う。
- **設定切替時の一貫性**: ある時点でキャッシュを無効化（disabled）に切り替えた場合、以降の参照は直接フェッチに切り替わり、保存済みエントリは時間経過で自然消滅する。
- **キャッシュバックエンド復旧後の整合性**: 障害中に変更されたマスタが、復旧後のキャッシュに古いまま残ることがないよう、フレッシュネス期間で必ず再フェッチされる。
- **書き込み競合**: 同じ商品を 2 つのリクエストがほぼ同時に問い合わせ、両方ともキャッシュミスする場合、両方ともマスタへフェッチに行ってよい（最終的に同じ値が格納される）。完全な thundering-herd 抑制は本フィーチャの対象外。
- **大きなリスト値**: 「全設定」のようなリストが過大になった場合の挙動は、現状の利用規模（数十件オーダ）では問題視しない。閾値を超えた場合の対処は将来課題。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: カートサービスは、商品・支払・販促・設定・税の各マスタ参照について、同一論理キーに対する短期間の繰り返し参照を再フェッチせずに応答できなければならない。
- **FR-002**: キャッシュエントリは、カートサービスのワーカープロセス間および再起動を跨いで共有・保持されなければならない。
- **FR-003**: キャッシュエントリは、テナント単位（および対象マスタが店舗依存である場合は店舗単位）で完全に隔離されなければならない。テナント A の参照結果がテナント B に観測されてはならず、また同一テナント内であっても店舗依存マスタについて店舗 X の参照結果が店舗 Y に観測されてはならない。
- **FR-004**: 各マスタ種別ごとに、キャッシュ済みエントリが「鮮度ありと見なされる期間（フレッシュネス期間）」を設定可能でなければならない。
- **FR-005**: 個別キャッシュエントリ単位での無効化操作を提供しなければならない。無効化後の最初の参照は必ず元のマスタソースから取得される。
- **FR-006**: マスタ種別全体（名前空間単位）の一括無効化操作を提供しなければならない。一括無効化は他のマスタ種別のキャッシュに影響してはならない。
- **FR-007**: キャッシュバックエンドが利用不能または異常応答を返す場合、マスタ参照は元のソースへの直接フェッチにフォールバックして成功しなければならない。キャッシュ層の障害がカート業務操作の失敗原因となってはならない。
- **FR-008**: キャッシュ機能は構成で無効化できなければならない（全体スイッチ）。無効時はすべての参照が直接フェッチに切り替わる。
- **FR-009**: 新しいマスタリポジトリを追加する際、開発者は「キャッシュ名前空間の宣言」「ドキュメント型の宣言」「ソースからの取得処理」のみを記述すれば、キャッシュ・無効化・キー組み立て・直列化が自動で具備されなければならない。
- **FR-010**: 単一エントリ参照とリスト参照の両方を扱うマスタ種別では、両者のキャッシュエントリを区別して保存・取得できなければならない。
- **FR-011**: 同一マスタ種別を複数の取得経路（例: HTTP / gRPC）で参照する場合、論理キーが同一であれば同じキャッシュエントリを共有しなければならない。
- **FR-012**: キャッシュ関連の異常（バックエンド到達失敗、フォールバック発生）は運用ログに記録されなければならない。ログは機微情報（マスタ値そのもの）を平文で保持してはならない。
- **FR-013**: マスタソースから「該当なし」と返された応答は、キャッシュに保存してはならない。同一論理キーへの後続参照は、毎回マスタソースに問い合わせ、新規登録されたマスタが即時に観測されるようにする。

### Key Entities

- **Cached Master-Data Entry**: マスタソースから取得した 1 件分のマスタレコードのスナップショット。テナント識別子、（適用される場合）店舗識別子、マスタ種別、論理キー、値、有効期限を属性として持つ。
- **Cache Namespace**: マスタ種別ごとの論理グルーピング（商品 / 支払 / 販促 / 設定 / 税）。名前空間ごとに既定フレッシュネス期間および一括無効化対象範囲が定義される。
- **Cache Backend**: 上記エントリを永続化・共有する記憶層。TTL（time-to-live）による自動失効と、キー単位の読み書き削除に対応する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一テナント・同一論理キーに対する同マスタ種別の連続参照（フレッシュネス期間内）において、マスタソースへのリクエストはフレッシュネス期間あたり最大 1 回しか発生しない。
- **SC-002**: フレッシュネス期間内のキャッシュヒット参照は、直接フェッチに比較して平均応答時間が 80% 以上短縮される。
- **SC-003**: キャッシュバックエンドを停止した状態でも、カートの主要購買シナリオ（端末オープン → 商品スキャン → 会計 → 端末クローズ）は 100% 成功する。
- **SC-004**: 個別無効化操作の呼び出しから 1 秒以内に、対象キーへの次回参照がマスタソースからの再フェッチを発生させる。
- **SC-005**: 一括無効化操作後、対象マスタ種別の全エントリは次回参照時に再フェッチされ、他のマスタ種別のキャッシュ動作には何ら影響を与えない。
- **SC-006**: 任意の 2 テナント間で、相手テナントが書いたキャッシュ値が観測可能であってはならない（マルチテナント分離テストで 0 件の漏洩）。
- **SC-006b**: 同一テナント内の任意の 2 店舗間で、店舗依存マスタについて相手店舗が書いたキャッシュ値が観測可能であってはならない（同テナント・別店舗分離テストで 0 件の漏洩）。
- **SC-007**: 同じマスタ種別を 2 経路（HTTP/gRPC 等）で参照しても、一方が書いたキャッシュ値をもう一方が読める（共有率 100%）。
- **SC-008**: 新規マスタリポジトリを追加した際のキャッシュ関連コード行数は 0 行（共通基盤への宣言・型指定・取得関数のみで完結）。
- **SC-009**: マスタに新規登録された論理キーは、登録完了から最初の参照で必ず観測される（不在応答は一切キャッシュされないため、新規登録の反映に遅延が発生しない）。

## Assumptions

- マスタデータの読み込み頻度は更新頻度に比して十分に大きい（キャッシュが有効に機能する前提）。
- フレッシュネス期間内における若干の古さ（stale 値）は業務上許容される。即時反映が必須の運用フローには手動無効化を用いる。
- マスタ種別ごとに適切なフレッシュネス期間を分けて設定する（例: 販促は短め、税率は長め）。具体の値は構成で調整可能とする。
- マスタ管理サービス側からの能動的な「変更通知イベント」は現時点では存在しない。本フィーチャは TTL + 手動無効化を一次手段とし、将来のイベント連動は別途対応する。
- 共有可能・TTL 対応のキャッシュ用記憶層（インフラ）が本サービスの実行環境に存在する。
- すべての参照経路（HTTP / gRPC / DB 直読）はキャッシュ抽象を通る前提で再構築されてよい。

---

## Out of Scope

- マスタ管理サービス側からの変更通知イベントの発行、およびそれを受けたカート側の自動無効化フロー。
- 本キャッシュ基盤をカートサービス以外（account / report / journal / stock 等）に展開すること。
- 2 段階キャッシュ（プロセス内 + 共有ストア）等の階層化。
- 起動時のキャッシュウォームアップ（現状の税マスタ一括ロード以上の自動先読み）。
- マスタ書き込み経路へのキャッシュ更新（write-through）。カートサービスはマスタを書き込まないため対象外。
- 同一キーへの同時ミス時の thundering-herd 抑制（重複フェッチを許容）。
