# Feature Specification: 署名付きカートスナップショットのレスポンス付加と restore API（client-carried cart phase 1）

**Feature Branch**: `148-cart-snapshot-restore`
**Created**: 2026-06-11
**Status**: Draft
**SPEC_TYPE**: functional
**Issue**: [#148](https://github.com/kugel-masa/kugelpos-backend/issues/148)（parent: [#146](https://github.com/kugel-masa/kugelpos-backend/issues/146)）
**派生元**: ダウンストリーム展開で実証済みのフェイルオーバー設計の移植

---

## 概要

POS の進行中取引（カート）を、**クライアント（POS 端末）が常に復元可能なかたちで持ち歩ける**ようにする。具体的には:

1. **カートを変更する全レスポンス**に、カート文書全体（参照マスタ `cart.masters` を含む）の**署名付きスナップショット**を追加で載せる。
2. 署名付きスナップショットを受け取り、**署名検証のうえで、そのカートを一度も見たことのないバックエンド上にカートを再構築する restore API** を新設する。

これにより:

- POS は取引途中で**別のエッジ/クラウドバックエンドに切り替えて取引を継続**できる（直前のスナップショットを新しいバックエンドに提示するだけ）。
- 「サーバ側キャッシュのデータ消失 ⇒ 進行中取引は再入力」という運用が**なくなる**（フロントエンドが常に復元可能なコピーを保持しているため）。

マスタ（商品・税・設定・プロモーション）は**バージョン参照ではなくスナップショットにそのまま同梱**する（#146 の決定事項）。復元先バックエンドがマスタ同期状態に依存せず、取引開始時点の価格・税計算の文脈をそのまま引き継ぐためである。

本フェーズ（phase 1）では**サーバ側キャッシュ（Redis / MongoDB フォールバック）が引き続き正**であり、スナップショットはあくまで「持ち出し用の復元コピー」。完全ステートレス化（サーバが取引状態を持たない）は phase 2 のスコープ。

## Clarifications

### Session 2026-06-12

- Q: FR-007 の「cart_id をキーとした冪等な確定」の実装範囲は？ → A: **取引確定の冪等化（tranlog への `cart_id` 追加 + 確定時の重複検査）は別 issue で対応**し、本フィーチャーのスコープ外とする。現行の tranlog は `cart_id` を持たず一意性は `(tenant_id, store_code, terminal_no, transaction_no)`（bill ごとに新規採番）のため、確定済み取引の**終端前**スナップショット（status=paying 等）を restore→ 確定すると二重計上が構造上可能。本フィーチャーは (1) 終端状態スナップショットの冪等拒否、(2) 全 restore の監査証跡（事後検知）までを担い、SC-004 の完全達成（二重計上の防止）は当該別 issue の完了に依存する。

### Session 2026-06-11

- Q: 署名鍵（HMAC）のスコープと配布・ローテーション方式は？ → A: **全バックエンド共有シークレット + 鍵 ID（kid）による世代管理**。フェイルオーバー網に参加する全バックエンド（エッジ/クラウド）で共通の専用鍵（256bit、JWT の `SECRET_KEY` とは別物・流用禁止）を環境変数/シークレットストアで配布する。スナップショットのメタデータに kid を含め、kid 自体も署名対象に含める（鍵すり替え防止）。ローテーションは「署名は常に現行鍵、検証は現行+前世代の 2 世代を受け入れ」とし、猶予期間は取引の最大寿命に合わせて 24 時間（既存の端末トークン寿命と整合）。猶予により、ローテーション時に POS が保持する旧鍵署名スナップショットが一斉無効化されない。漏洩時は緊急ローテーション（旧鍵即時削除 = 進行中取引の復元コピーは犠牲）を運用手順として明記する。テナント別鍵は鍵の保管・同期という新たな設計問題を持ち込むため phase 1 では採らない（エッジ配備での影響分離が必要な場合は、スキーマを変えず配備単位で鍵値を変える運用で緩和できる）。
- Q: restore を要求できる端末の範囲は？ → A: **スナップショット発行端末と同一のテナント + 店舗に属する端末なら、別端末でも復元可**。端末故障時に代替端末で取引を引き継ぐ運用を救うため、同一端末限定にはしない。一方、店舗を跨ぐ復元は「店舗間の取引移動」という新しい運用を許すことになるため認めない（テナント一致に加えて店舗一致も MUST）。発行端末と異なる端末による復元は正常系として扱うが、監査証跡に発行端末・復元要求端末の双方を記録し追跡可能とする。
- Q: restore 時に同一 `cart_id` のカートが復元先に既に存在する場合の勝者ルールは？ → A: **既存サーバ側カートを優先 + 差分通知**。restore は上書き・新規作成を行わず、既存カートの現在状態（と新しい署名付きスナップショット）を返す。その際、提示されたスナップショットと既存カートの内容が異なる場合は**レスポンスで判別可能な差分通知**を返し、差分があった事実を監査証跡にも記録する。理由: (1) phase 1 の「サーバ側が正」と一貫、(2) リプレイ「許容+検知」方針の下で上書きを許すと有効署名付きの古いスナップショットによる巻き戻しの穴になる、(3) リビジョン比較（新しい方優先）が救う唯一のケース「1 取引中の二重フェイルバック」は稀であり、phase 2 で権威の所在自体が変わる前に衝突解決機構へ投資する価値が低い。差分通知により、フェイルバック時に POS が黙って古い状態へ戻る事故は検知できる。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 別バックエンドへの切替後に取引を継続できる (Priority: P1)

店舗のエッジバックエンドが取引途中で停止した。POS は直前のレスポンスで受け取った署名付きスナップショットをクラウドバックエンドの restore API に提示する。クラウド側はそのカートを見たことがないが、署名検証のうえカートを再構築し、POS は商品追加〜会計までを**再入力なしで**継続する。

**Why this priority**: 本フィーチャーの存在理由そのもの。これが成立しなければ phase 1 の価値はない。

**Independent Test**: バックエンド A でカートを作成し商品を入れ、スナップショットを取得 → バックエンド B（別の MongoDB/Redis）に restore → B 上で商品追加・小計・支払い・確定まで通ることを確認。

**Acceptance Scenarios**:

1. **Given** バックエンド A で進行中のカート（明細あり）と最後のスナップショット、**When** そのスナップショットをバックエンド B の restore API に提示する、**Then** B 上にカートが同一の `cart_id`・状態・明細・参照マスタで再構築され、後続のカート操作（商品追加〜確定）が成功する。
2. **Given** restore で再構築されたカート、**When** 取引を確定（bill）する、**Then** 取引ログが通常どおり生成・配信され、レシートデータも取引開始時点のマスタ文脈で正しく出力される。
3. **Given** restore 後のカート変更レスポンス、**When** クライアントがスナップショットを確認する、**Then** 再構築後の最新状態を反映した新しい署名付きスナップショットが含まれている。

---

### User Story 2 - すべてのカート変更レスポンスで最新の復元コピーを受け取る (Priority: P1)

POS はカートに対する操作（作成・商品追加・数量変更・割引・小計・支払い・確定・中止 等）のたびに、レスポンスに含まれる署名付きスナップショットを保持する。どの時点でバックエンドが失われても、POS は常に「最後に成功した操作の直後」の復元コピーを持っている。

**Why this priority**: User Story 1 の前提。スナップショットが欠けるレスポンスが 1 つでもあると、その操作後の障害で復元できない。

**Independent Test**: カート変更系の全エンドポイントを順に呼び、すべてのレスポンスにスナップショットと署名が含まれ、内容がその時点のカート状態（サーバ側の正のデータ）と一致することを確認。

**Acceptance Scenarios**:

1. **Given** 進行中のカート、**When** カートを変更するいずれかの API を呼ぶ、**Then** レスポンスに変更適用後のカート文書全体（`cart.masters` 含む）の署名付きスナップショットが含まれる。
2. **Given** カートを変更しない参照系 API（カート照会等）、**When** 呼び出す、**Then** 既存のレスポンス形式が維持される（スナップショット付加はカート変更系のみ。GET には付加しない — plan R-005 で確定）。
3. **Given** スナップショットを利用しない既存クライアント、**When** カート変更 API を呼ぶ、**Then** 既存フィールドのみで従来どおり動作する（破壊的変更なし）。

---

### User Story 3 - 改ざん・偽造されたスナップショットは復元できない (Priority: P1)

攻撃者（または不具合のあるクライアント）が、金額・明細・マスタを書き換えたスナップショットを restore API に提示しても、署名検証で拒否される。

**Why this priority**: スナップショットはクライアント側に渡るため、改ざん耐性がなければ「クライアントが任意の取引状態をサーバに注入できる」ことになり、POS として致命的。

**Independent Test**: 正当なスナップショットの本文を 1 バイトでも書き換えて restore に提示し、拒否されること（および拒否が監査可能であること）を確認。

**Acceptance Scenarios**:

1. **Given** 本文を改ざんしたスナップショット、**When** restore API に提示する、**Then** 署名不一致として拒否され、カートは作成されない。
2. **Given** 署名部分を欠落・破損させたスナップショット、**When** restore API に提示する、**Then** 検証不能として拒否される。
3. **Given** 他テナントの正当なスナップショット、**When** 別テナントの端末認証で restore API に提示する、**Then** テナントスコープ違反として拒否される。
4. **Given** 同一テナント内の別店舗で発行された正当なスナップショット、**When** restore API に提示する、**Then** 店舗スコープ違反として拒否される。
5. **Given** 署名検証失敗の発生、**When** 運用者がログ/監査証跡を確認する、**Then** いつ・どの端末が・どの `cart_id` で失敗したかを追跡できる。

---

### User Story 4 - 古いスナップショットの再提示（リプレイ）は受け入れつつ検知できる (Priority: P2)

古い署名付きスナップショットは構造上「正当」である（署名は有効）。方針は**防止ではなく許容 + 検知**: restore 自体は受け入れ、取引の確定は `cart_id` をキーに冪等とし、同一取引の二重計上を防ぐ。再提示の事実は監査証跡に残す。

**Why this priority**: 整合性（二重計上防止）に関わるが、正常系（Story 1, 2, 3）が成立していることが前提のため P2。

**Independent Test**: 同一カートの古いスナップショットを restore → 確定、を 2 系統で実施し、取引ログが二重計上されないこと、監査証跡から再提示を追跡できることを確認。

**Acceptance Scenarios**:

1. **Given** 既に確定（または中止）済みの取引の古いスナップショット、**When** restore して再度確定を試みる、**Then** 同一 `cart_id` の取引として冪等に扱われ、取引が二重計上されない。
2. **Given** restore API の利用、**When** 監査証跡を確認する、**Then** どのスナップショット（いつ時点・どの端末発行）がいつ・どこで復元されたかを追跡できる。
3. **Given** 復元先に同一 `cart_id` の進行中カートが既に存在し、提示スナップショットの内容がそれと異なる、**When** restore API に提示する、**Then** 既存カートの現在状態が返り（上書きされない）、レスポンスで差分の存在を判別でき、差分の事実が監査証跡に記録される。

---

### Edge Cases

- **同一 `cart_id` のカートが復元先に既に存在する**（念のため restore / フェイルバックで旧バックエンドにデータが残っている）: 既存サーバ側カートを優先し、内容が異なる場合は差分通知を返す（FR-006・Clarifications 確定済み）。
- **署名鍵のローテーション中**: 旧鍵（前世代）で署名されたスナップショットは猶予期間内（24 時間以上）は検証可。猶予を過ぎた鍵・未知の kid は検証不能として拒否（FR-011・Clarifications 確定済み）。
- **スナップショットのスキーマバージョン不一致**: 旧バージョンのスナップショットを新バックエンドが受けた場合、サポート範囲内なら復元、範囲外なら明確なエラーで拒否（FR-008）。
- **確定済み・中止済み状態のスナップショット**: restore の対象は進行中状態のみとし、終端状態のスナップショットは復元せず冪等応答（FR-007）。
- **巨大カート**（数百明細・大きなマスタ同梱）: サイズ上限の扱いと計測（NFR-001）。上限超過時も既存フィールドの応答は損なわない。
- **スナップショット内マスタが最新マスタと乖離**: 復元後も取引開始時点のマスタ文脈を維持する（マスタ再取得で価格が変わってはならない — #146 の決定に整合）。
- **restore 要求の認証端末とスナップショット発行端末が異なる**（端末故障による入替え等）: 同一テナント + 店舗内なら許可し、発行端末・要求端末の双方を監査証跡に記録。店舗が異なる場合は拒否（FR-012・Clarifications 確定済み）。

## Functional Requirements *(mandatory)*

### FR-001: カート変更系レスポンスへの署名付きスナップショット付加

カートの状態を変更するすべての API レスポンスは、変更適用後のカート文書全体のスナップショットと、その署名を追加フィールドとして含めなければならない（MUST）。既存のレスポンスフィールドは変更しない（後方互換）。

### FR-002: スナップショットの内容

スナップショットは、復元先バックエンドが事前知識なしにカートを再構築するのに十分な情報を含まなければならない（MUST）。少なくとも: カート本体（状態・明細・金額・支払い）、参照マスタ（`cart.masters`: 商品・税・設定・プロモーション）、テナント/店舗/端末の帰属情報、スナップショットのメタデータ（スキーマバージョン・発行時刻・署名鍵 ID）。

### FR-003: 署名と正規化

スナップショットには HMAC によるメッセージ認証符号を付す（MUST）。署名対象は正規化（canonical）されたシリアライゼーションとし、同一内容なら常に同一の署名対象バイト列になること（MUST）。鍵 ID（kid）を含むメタデータも署名対象に含めること（MUST — 鍵すり替え防止）。署名鍵がクライアントに渡ることがあってはならない（MUST NOT）。

### FR-004: restore API

署名付きスナップショットを受け取り、(1) 署名検証、(2) 認可検証（FR-005）、(3) 衝突判定（FR-006）を経て、復元先バックエンド上にカートを再構築する API を提供しなければならない（MUST）。復元されたカートは通常のカートと同等に後続操作（商品追加〜確定・中止）を受け付けられること（MUST）。復元成功レスポンスにも最新の署名付きスナップショットを含める（MUST）。

### FR-005: 認可とテナントスコープ

restore API は端末 API キー認証を要求し、スナップショットの帰属テナントと認証コンテキストのテナントが一致しない場合は拒否しなければならない（MUST）。端末の範囲は FR-012 に従う。

### FR-006: 同一 cart_id 衝突時の勝者ルール（既存サーバ優先 + 差分通知）

復元先に同一 `cart_id` のカートが既に存在する場合、restore はスナップショットによる上書きを行ってはならず（MUST NOT）、既存カートの現在状態と最新の署名付きスナップショットを返さなければならない（MUST）。`cart_id` は取引同一性のキーである（ダウンストリーム設計に整合）。提示されたスナップショットと既存カートの内容が一致しない場合、レスポンスはそれを判別できる差分通知を含まなければならず（MUST）、差分が発生した事実を監査証跡（FR-007）に記録しなければならない（MUST）。

### FR-007: リプレイの許容と検知（冪等な確定）

古い正当なスナップショットの restore は拒否しない（許容）。一方で、取引の確定は `cart_id` をキーとして冪等でなければならず（MUST）、同一取引が二重に計上されてはならない（MUST NOT）。**冪等な確定の実装（tranlog への `cart_id` 付与 + 確定時の重複検査）は別 issue で対応する**（Clarifications 2026-06-12）。本フィーチャーの範囲は、終端状態スナップショットの冪等拒否と、restore の実行（成功・拒否とも）の監査証跡記録 — 発行時刻・発行元・復元先・結果を追跡可能にすること（MUST）— まで。

### FR-008: スナップショットのバージョニング

スナップショットはスキーマバージョンを持ち、将来のスキーマ変更後も旧バージョンの受け入れ可否を判定できなければならない（MUST）。サポート外バージョンは明確なエラー（専用エラーコード）で拒否する（MUST）。

### FR-009: 検証失敗時のエラー応答

署名不一致・検証不能・テナント不一致・バージョン非対応・終端状態スナップショットの冪等拒否は、それぞれ区別可能な cart サービスのエラーコード（`cart_error_codes.py` のカート予約帯。具体的な割当ては plan で確定 → 4015xx）で応答しなければならない（MUST）。エラー応答にスナップショットの内容を反映（部分復元）してはならない（MUST NOT）。

### FR-010: サーバ側キャッシュとの関係（phase 1 の正）

スナップショットは常にサーバ側の正のデータ（Redis / MongoDB フォールバック）から生成する（MUST）。restore はサーバ側の正のデータを再形成する操作であり、復元後はサーバ側が引き続き正となる（MUST）。クライアント保持のスナップショットを通常操作の入力として信頼してはならない（restore 時の署名検証済み入力を除く）（MUST NOT）。

### FR-011: 署名鍵の管理とローテーション（共有シークレット + 鍵 ID 世代管理）

署名鍵は、フェイルオーバー網に参加する全バックエンド（エッジ/クラウド）で共有する専用鍵とし、環境変数またはシークレットストアで配布しなければならない（MUST）。JWT 署名鍵（`SECRET_KEY`）の流用は禁止（MUST NOT — 用途別の鍵分離）。スナップショットのメタデータは署名に使用した鍵 ID（kid）を含み（MUST）、検証側は kid に対応する鍵で検証しなければならない（MUST）。ローテーションをサポートし、署名は常に現行鍵で行い、検証は現行鍵と前世代鍵の 2 世代を受け入れること（MUST）。前世代鍵の受け入れ猶予は 24 時間以上とする（進行中取引のスナップショットがローテーションで一斉無効化されないため）。漏洩時の緊急ローテーション手順（前世代鍵の即時無効化 = 進行中取引の復元コピーを犠牲にする判断を含む）を運用文書に明記すること（MUST）。

### FR-012: 復元を許可する端末の範囲（同一テナント + 店舗）

restore を要求する端末は、スナップショットの帰属テナントおよび店舗と一致しなければならない（MUST）。一致すれば発行端末と異なる端末でも復元できる（端末故障時の代替端末への引き継ぎを許容）。店舗が一致しない要求は拒否する（MUST — 店舗間の取引移動は許可しない）。発行端末と異なる端末による復元は、監査証跡（FR-007）に発行端末・復元要求端末の双方を記録すること（MUST）。

## Non-Functional Requirements

- **NFR-001（サイズ予算）**: 標準的な 40 商品カートで、スナップショット込みレスポンスの圧縮後サイズが机上見積り（~5–15 KB）に収まることを実測で検証する。実測はダウンストリーム展開の実データを参考にし、超過する場合は plan で対策（同梱マスタの絞り込み等）を検討する。圧縮は #147 に依存。
- **NFR-002（レイテンシ予算）**: スナップショット生成・署名によるカート変更 API の応答遅延の増加は、利用者が体感できない範囲（目標: p95 で +50ms 以内）に収める。実測で検証する。
- **NFR-003（セキュリティ）**: 署名鍵は環境変数またはシークレットストアで管理し、リポジトリ・ログ・レスポンスに出力しない。検証失敗はセキュリティイベントとして記録する。
- **NFR-004（可用性）**: スナップショット生成の失敗が本来のカート操作を失敗させてはならない（操作成功 + スナップショット欠落の縮退を許容するか、操作ごと失敗とするかは plan で確定。ただし縮退する場合はログで検知可能にする）。

## Key Entities

- **カートスナップショット**: ある時点のカート文書全体（明細・金額・状態・参照マスタ・帰属情報）+ メタデータ（スキーマバージョン・発行時刻・鍵 ID）。クライアントが保持し、restore の入力となる。
- **スナップショット署名**: スナップショットの正規化表現に対する HMAC。改ざん検知の唯一の根拠。
- **restore 監査レコード**: restore 要求の発生事実（いつ・どの端末・どの `cart_id`・スナップショット発行時刻・結果）。リプレイ検知と事後追跡の根拠。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 取引途中のカートについて、最後に受け取ったスナップショットを別バックエンドに提示することで、**再入力ゼロ**で取引を継続し会計完了まで到達できる。
- **SC-002**: サーバ側キャッシュの全データ消失後も、クライアント保持のスナップショットから進行中取引を復元でき、「消失 ⇒ 再入力」となるケースが 0 件になる。
- **SC-003**: 内容を改ざんしたスナップショットの復元試行は 100% 拒否され、すべて追跡可能なかたちで記録される。
- **SC-004**: 同一取引（同一 `cart_id`）のスナップショットを何度復元・確定しても、計上される取引はちょうど 1 件である。
- **SC-005**: 標準的な 40 商品カートで、スナップショット込みレスポンスの転送サイズ（圧縮後）が 15 KB 以下であることが実測で確認される。
- **SC-006**: カート操作の応答時間の悪化が利用者に体感されない（p95 の増加が +50ms 以内）。

## Out of Scope

- **完全ステートレス化（phase 2）**: サーバ側キャッシュを正としない運用、毎リクエストでのスナップショット提示。本フェーズではサーバ側が正。
- **マスタのバージョン参照化**: マスタは同梱（#146 の決定）。参照化の再検討は phase 2 以降。
- **リプレイの「防止」**（ワンタイムトークン・nonce 等）: 方針は許容 + 検知。
- **クライアント（POS フロントエンド）側のスナップショット保持・提示ロジック**: 本リポジトリのスコープ外（API 契約のみ提供）。
- **cart 以外のサービスの状態持ち出し**（terminal のサインイン状態等）。
