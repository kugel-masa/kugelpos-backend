# パフォーマンス検証: 従来パターン vs ステートレスパターン

**Branch**: `156-stateless-cart` | **Date**: 2026-06-14 | **Spec**: [spec.md](./spec.md)

phase 2（client-carried cart）の完了後、**従来パターン（サーバー側キャッシュ権威）** と
**ステートレスパターン（署名付きスナップショットをリクエストに同梱）** を、稼働中スタックで
比較計測した結果をまとめる。

- **従来パターン**: 変更系リクエストは素のボディを送る。バックエンドは Redis/Mongo の
  カートキャッシュを読み書きして処理する。
- **ステートレスパターン**: 変更系リクエストは `{signedSnapshot, payload}` でラップし、
  最後のスナップショットを持ち回る。peel ミドルウェアが取り出し、HMAC 検証のうえ
  キャッシュを読まずにカートを再構成して処理、新しい署名付きスナップショットを返す。

---

## 1. 計測方法

| 項目 | 内容 |
|---|---|
| 対象スタック | ローカル docker-compose 全7サービス（再ビルド済み・healthy） |
| モード | `CART_REQUEST_SNAPSHOT_MODE=DUAL`、スナップショット鍵設定済み |
| クライアント | 単一クライアント・**完全直列**（無競合）、httpx、localhost ループバック |
| 計測区間 | クライアント壁時計（`perf_counter`）で **1 HTTP 往復**＝リクエスト直列化 → 送信 → サーバー処理 → 全レスポンス受信 → JSON パース まで |
| 計測オペ | `subtotal` / `payment` / `bill`（カート作成・明細追加は「準備」として対象外） |
| 反復 | 各 (明細数, パターン) を M=10〜12 回、legacy→stateless を交互実行、毎回新規カート |
| 集計 | 平均(mean)。明細数 N ∈ {1, 5, 20, 50} |
| 商品 | **明細ごとにユニークな商品コード**（distinct code / 日本語名 / 異なる価格）で実取引に近い entropy を再現 |

各レイテンシ値には、ステートレスの**大きいリクエストのクライアント側直列化コスト**や、
DUAL モードゆえ**従来経路でも生成されるレスポンス用スナップショットの署名コスト**が
含まれる（＝クライアント観測のエンドツーエンド値であり、サーバー内訳の分離値ではない）。

---

## 2. 結果: レイテンシ（mean, ms）

| 明細数 | op | 従来(cache) | ステートレス(snapshot) | Δ(s−l) |
|---:|---|---:|---:|---:|
| 1 | subtotal | 16.4 | 14.3 | −2.1 |
| 1 | payment | 16.9 | 18.1 | +1.2 |
| 1 | bill | 30.6 | 29.4 | −1.2 |
| 5 | subtotal | 19.2 | 13.0 | −6.2 |
| 5 | payment | 16.8 | 17.1 | +0.3 |
| 5 | bill | 30.6 | 31.0 | +0.4 |
| 20 | subtotal | 20.0 | 18.8 | −1.2 |
| 20 | payment | 20.0 | 19.5 | −0.6 |
| 20 | bill | 37.9 | 37.2 | −0.7 |
| 50 | subtotal | 27.4 | 21.0 | −6.4 |
| 50 | payment | 24.8 | 25.4 | +0.5 |
| 50 | bill | 56.5 | 51.0 | −5.5 |

- **両パターンはほぼ同等**（差は±数 ms ＝ M=10〜12 のノイズ範囲、符号も一定しない）。
- レイテンシは**明細数とともに両者とも増加**（subtotal は再計算/直列化、bill はレシート/
  ジャーナルテキスト生成が明細数に比例）。増え方は両パターンで同じ。
- **大バスケット（N=50）でステートレスがやや有利**（subtotal −6.4 / bill −5.5）。カートが
  大きいほど従来経路の Redis キャッシュ I/O 量が増えるため、**cache バイパスの優位が
  明細数とともにじわっと現れる**（小さな実効果＋ノイズ）。bill では加えて、従来経路の
  サーバー側カウンタ採番（取引番号・レシート番号の DB findAndModify ＋設定参照）を
  ステートレスは持ち回り採番でスキップする。

> ⚠️ 補足: 再起動直後の最初の計測では legacy bill が ~52ms と重く出て「ステートレスが
> −22ms 高速」に見えたが、これは**従来経路のサーバー側採番キャッシュがコールド**だった
> アーティファクト。ウォーム定常状態では legacy bill も ~30ms に下がり差は消える。
> 上表のウォーム計測を正とする。

## 3. 結果: 転送量（リクエスト同梱スナップショット）

明細ごとにユニークな商品コードでのラップ済みリクエストボディのサイズ:

| 明細数 | 生 JSON | gzip(6) | brotli(q5) | gzip比率 |
|---:|---:|---:|---:|---:|
| 1 | 5,358 B | 1,308 B | 1,214 B | 24% |
| 5 | 9,074 B | 1,565 B | 1,446 B | 17% |
| 20 | 22,853 B | 2,377 B | 2,114 B | 10% |
| 50 | 50,436 B | 3,640 B | 2,927 B | 7% |

- 生サイズは**ほぼ線形**に増加（約 +920 B/明細, ※日本語名の JSON `\uXXXX` エスケープで
  やや膨らみ気味）。
- 圧縮後も明細数に応じて増えるが**サブリニア**: 概ね **gzip ≈ +46 B/明細、brotli ≈ +33 B/明細**。
- 実用目安: **オンワイヤ ≈ 1.3 KB（基底）+ 約 40 B/明細（圧縮後）**。
  50 明細の取引で **約 3 KB（brotli）〜 3.6 KB（gzip）**。これは issue #148 の実測値
  「典型バスケットで gzip 約 3.3 KB」とよく整合する。

> 注: 全明細が同一商品コードだと圧縮率が過大に良く出る（50 明細でも gzip ~1.6 KB）。
> それは繰り返しによる楽観値であり、上表のユニーク商品版が実態に即した転送コスト。

### レスポンス転送量

DUAL モードでは**従来経路でもレスポンスに `signedSnapshot` が含まれる**ため、レスポンス
サイズは両パターンでほぼ同一。ステートレス化で増えるのは**リクエスト方向のみ**。

---

## 4. 結論

| 観点 | 従来パターン | ステートレスパターン |
|---|---|---|
| レイテンシ | 基準 | ほぼ同等。大バスケットで数 ms 有利（cache バイパス＋持ち回り採番） |
| リクエスト転送量 | 最小 | +約 1.3 KB + 40 B/明細（圧縮後）。クライアント→サーバー方向のみ |
| レスポンス転送量 | ＝ | ＝（phase 2 では両者スナップショット返却） |
| サーバー状態依存 | Redis/Mongo キャッシュ必須 | **不要（ステートレス）** |

**ステートレスパターンはレイテンシを実質犠牲にせず**、phase 2 の目的である
**ステートレス化（キャッシュ消失耐性・任意バックエンドで取引継続）** を達成できている。
コストは主に**クライアント→サーバー方向のリクエスト転送増（圧縮後 数 KB）**に限られる。

---

## 5. 計測の限界と今後

- 単一クライアント・直列・ローカルウォームスタック（低競合）での実測。**並行負荷時の
  スループット／競合時の cache バイパス効果は未計測**。
- localhost ループバック（実ネットワーク遅延ゼロ）。本番では転送量の影響が相対的に拡大。
- サンプル数が少なく（M=10〜12）、一桁 ms の差はノイズ範囲。
- DUAL モードのため従来経路もレスポンス用スナップショットを生成（純 phase-1 ではない）。

より厳密化するなら: (a) サーバー側計測でサーバー内訳を分離、(b) 並行負荷で
スループット／競合時の cache バイパス効果を計測、(c) 実商品マスタ分布での転送量再計測。

> 計測スクリプトは throwaway（`tmp_*`）として実行後に削除済み。本ドキュメント以外の
> リポジトリ変更はない。
