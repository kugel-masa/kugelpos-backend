# パフォーマンス検証: 従来パターン vs ステートレスパターン

**Branch**: `156-stateless-cart` | **Date**: 2026-06-14 | **Spec**: [spec.md](./spec.md)

phase 2（client-carried cart）の完了後、**従来パターン（サーバー側キャッシュ権威）** と
**ステートレスパターン（署名付きスナップショットをリクエストに同梱）** を、稼働中スタックで
比較計測した結果をまとめる。

- **従来パターン**: 変更系リクエストは素のボディを送る。バックエンドは Redis/Mongo の
  カートキャッシュを読み書きして処理する。
- **ステートレスパターン**: 変更系リクエストは `{signedSnapshot, payload}` でラップし、
  最後のスナップショットを持ち回る。peel ミドルウェアが取り出し、HMAC 検証のうえ
  キャッシュを読まずにカートを再構成して処理、新しい署名付きスナップショットを返す。

---

## 1. 計測方法

| 項目 | 内容 |
|---|---|
| 対象スタック | ローカル docker-compose 全7サービス（再ビルド済み・healthy） |
| モード | `CART_REQUEST_SNAPSHOT_MODE=DUAL`、スナップショット鍵設定済み |
| クライアント | 単一クライアント・**完全直列**（無競合）、httpx、localhost ループバック |
| 計測区間 | クライアント壁時計（`perf_counter`）で **1 HTTP 往復**＝リクエスト直列化 → 送信 → サーバー処理 → 全レスポンス受信 → JSON パース まで |
| 計測オペ | `addItem`（1スキャン=1回の最頻オペ）/ `subtotal` / `payment` / `bill` |
| 反復 | 各 (明細数, パターン) を M=10〜12 回、legacy→stateless を交互実行、毎回新規カート |
| 集計 | 平均(mean)。明細数 N ∈ {1, 5, 20, 50} |
| 商品 | **明細ごとにユニークな商品コード**（distinct code / 日本語名 / 異なる価格）で実取引に近い entropy を再現 |

各レイテンシ値には、ステートレスの**大きいリクエストのクライアント側直列化コスト**や、
DUAL モードゆえ**従来経路でも生成されるレスポンス用スナップショットの署名コスト**が
含まれる（＝クライアント観測のエンドツーエンド値であり、サーバー内訳の分離値ではない）。

## 2. 結果: レイテンシ（mean, ms）

### 2.1 addItem（1スキャン=1回の最頻オペ）

| カート明細数 | 従来(cache) | ステートレス(snapshot) | Δ(s−l) |
|---:|---:|---:|---:|
| 1 | 19.3 | 16.0 | **−3.2** |
| 5 | 20.5 | 17.0 | **−3.5** |
| 20 | 24.7 | 19.2 | **−5.5** |
| 50 | 35.2 | 28.5 | **−6.7** |

- **addItem はステートレスが一貫して速く、その差は明細数とともに拡大**（−3 → −7ms）。
  これはノイズではなく単調な実効果。従来経路は addItem ごとに**成長するカートを Redis
  から読み、書き戻す**が、ステートレスはリクエスト内スナップショットから再構成して
  **キャッシュ書き込みをスキップ**するため。カートが大きいほど Redis I/O 量が増え差が開く。
- ステートレスは成長するスナップショット（最大50KB）をリクエストで送るが、その
  クライアント直列化コストを含めても**なお速い**＝節約した Redis I/O が上回る。

### 2.2 subtotal / payment / bill

| 明細数 | op | 従来(cache) | ステートレス(snapshot) | Δ(s−l) |
|---:|---|---:|---:|---:|
| 1 | subtotal | 16.4 | 14.3 | −2.1 |
| 1 | payment | 16.9 | 18.1 | +1.2 |
| 1 | bill | 30.6 | 29.4 | −1.2 |
| 5 | subtotal | 19.2 | 13.0 | −6.2 |
| 5 | payment | 16.8 | 17.1 | +0.3 |
| 5 | bill | 30.6 | 31.0 | +0.4 |
| 20 | subtotal | 20.0 | 18.8 | −1.2 |
| 20 | payment | 20.0 | 19.5 | −0.6 |
| 20 | bill | 37.9 | 37.2 | −0.7 |
| 50 | subtotal | 27.4 | 21.0 | −6.4 |
| 50 | payment | 24.8 | 25.4 | +0.5 |
| 50 | bill | 56.5 | 51.0 | −5.5 |

- **両パターンはほぼ同等**（差は±数 ms ＝ M=10〜12 のノイズ範囲、符号も一定しない）。
- レイテンシは**明細数とともに両者とも増加**（subtotal は再計算/直列化、bill はレシート/
  ジャーナルテキスト生成が明細数に比例）。増え方は両パターンで同じ。
- **大バスケット（N=50）でステートレスがやや有利**（subtotal −6.4 / bill −5.5）。カートが
  大きいほど従来経路の Redis キャッシュ I/O 量が増えるため、**cache バイパスの優位が
  明細数とともにじわっと現れる**（小さな実効果＋ノイズ）。bill では加えて、従来経路の
  サーバー側カウンタ採番（取引番号・レシート番号の DB findAndModify ＋設定参照）を
  ステートレスは持ち回り採番でスキップする。

> ⚠️ 補足: 再起動直後の最初の計測では legacy bill が ~52ms と重く出て「ステートレスが
> −22ms 高速」に見えたが、これは**従来経路のサーバー側採番キャッシュがコールド**だった
> アーティファクト。ウォーム定常状態では legacy bill も ~30ms に下がり差は消える。
> 上表のウォーム計測を正とする。

## 3. 結果: 転送量

### 3.1 addItem レスポンス（最も重要なファクター）

addItem は1スキャンごとに1回起き、**レスポンスにカート全体＋署名付きスナップショットが
載る**。これが phase 2 の転送コストの主因。明細ごとにユニーク商品でのレスポンスボディ:

| カート明細数 | raw | gzip | brotli | うちスナップショット(raw) | スナップショット占有率 |
|---:|---:|---:|---:|---:|---:|
| 1 | 6,622 B | 1,597 B | 1,493 B | 5,291 B | **80%** |
| 5 | 11,564 B | 1,950 B | 1,806 B | 9,007 B | **78%** |
| 20 | 29,865 B | 3,096 B | 2,759 B | 22,786 B | **76%** |
| 50 | 66,502 B | 4,969 B | 3,939 B | 50,369 B | **76%** |

- **レスポンスサイズは従来・ステートレスで完全に同一**（DUAL モードでは両経路とも
  スナップショットを返すため）。よって**レスポンス側は両パターンの差ではなく、
  phase 2 そのもののコスト**。
- **レスポンスボディの約 76〜80% がスナップショット**。スナップショットは内部に
  `cart_document` を持つため、レスポンス内のカートビューと**大部分が重複**している
  （50明細でカートビュー約16KB に対しスナップショット約50KB）。
- 50明細で **raw 66.5KB / gzip 5.0KB / brotli 3.9KB**。これが**毎スキャン**返る。
- 1取引（50明細）累計のダウンロード量は、各 addItem レスポンスの総和でおおよそ
  **gzip で 100〜150KB 規模**（明細が増えるほど1レスポンスが大きくなるため）。
  phase 1（スナップショット非返却）比で、addItem レスポンスは概ね **4〜5倍**に膨らむ。

> 含意: phase 2 の転送増は「リクエストに同梱するスナップショット（§3.2）」だけでなく、
> **毎回の変更系レスポンスが運ぶスナップショット**がむしろ支配的。これは（鍵設定時は）
> 両パターン共通で発生する。クライアントは次リクエストで持ち回るため**必要なデータ**だが、
> カートビューとの重複が大きく、**圧縮・差分返却・スナップショット分離取得**などの
> 最適化余地がある（§5）。

### 3.2 addItem 等のリクエスト同梱スナップショット

明細ごとにユニークな商品コードでのラップ済みリクエストボディのサイズ（ステートレスのみ）:

| 明細数 | 生 JSON | gzip(6) | brotli(q5) | gzip比率 |
|---:|---:|---:|---:|---:|
| 1 | 5,358 B | 1,308 B | 1,214 B | 24% |
| 5 | 9,074 B | 1,565 B | 1,446 B | 17% |
| 20 | 22,853 B | 2,377 B | 2,114 B | 10% |
| 50 | 50,436 B | 3,640 B | 2,927 B | 7% |

- 生サイズは**ほぼ線形**に増加（約 +920 B/明細, ※日本語名の JSON `\uXXXX` エスケープで
  やや膨らみ気味）。
- 圧縮後も明細数に応じて増えるが**サブリニア**: 概ね **gzip ≈ +46 B/明細、brotli ≈ +33 B/明細**。
- 実用目安: **オンワイヤ ≈ 1.3 KB（基底）+ 約 40 B/明細（圧縮後）**。
  50 明細の取引で **約 3 KB（brotli）〜 3.6 KB（gzip）**。これは issue #148 の実測値
  「典型バスケットで gzip 約 3.3 KB」とよく整合する。

> 注: 全明細が同一商品コードだと圧縮率が過大に良く出る（50 明細でも gzip ~1.6 KB）。
> それは繰り返しによる楽観値であり、上表のユニーク商品版が実態に即した転送コスト。
> body-less / 小ペイロードのオペ（subtotal/payment/bill）ではこの同梱分が純粋な追加分だが、
> addItem では §3.1 のレスポンス側コストの方がはるかに大きい。

### 3.3 リクエスト方向とレスポンス方向の関係

- **リクエスト方向**（§3.2）はステートレスのみ。**レスポンス方向**（§3.1）は DUAL では両
  パターン共通。よって「ステートレス化で増えるのはリクエストのみ」ではなく、phase 2 の
  転送増は**主にレスポンス側のスナップショット**にあり、リクエスト側はステートレス選択時の
  追加分という整理になる。
- addItem レスポンスのスナップショット（出力）は、次の addItem でクライアントが持ち回る
  リクエストのスナップショット（入力）と**同一データ**。同じバイト列が往復する。

## 4. 結論

| 観点 | 従来パターン | ステートレスパターン |
|---|---|---|
| レイテンシ（addItem=最頻） | 基準 | **一貫して速い（−3〜−7ms、明細数で拡大）**。Redis 読み書きをバイパス |
| レイテンシ（subtotal/payment/bill） | 基準 | ほぼ同等。大バスケットで数 ms 有利 |
| リクエスト転送量 | 最小 | +約 1.3 KB + 40 B/明細（圧縮後）。ステートレス選択時のみ |
| **レスポンス転送量（addItem）** | **大（snapshot 同梱）** | **大（同左・両者同一）**。1スキャンごと、本体の **76〜80% がスナップショット** |
| サーバー状態依存 | Redis/Mongo キャッシュ必須 | **不要（ステートレス）** |

要点:
- **レイテンシ面ではステートレスが不利になることはなく、最頻オペの addItem はむしろ
  一貫して速い**（cache の読み書きバイパス）。phase 2 の目的である
  **ステートレス化（キャッシュ消失耐性・任意バックエンドで取引継続）** をレイテンシを
  犠牲にせず達成できている。
- **phase 2 の主たるコストは転送量、なかでも addItem レスポンスが運ぶスナップショット**。
  これは1スキャンごとに発生し、レスポンス本体の 76〜80% を占め、明細とともに増大する
  （50明細で gzip 約 5KB/回）。DUAL では両パターン共通で発生する。
- このレスポンス・スナップショットは、内部 `cart_document` がレスポンスのカートビューと
  大きく重複しており、**最適化の主戦場**（§5）。

## 4.5 補遺: コールド状態（サービス再起動直後）の計測

§2〜§4 はウォーム状態。ここでは**キャッシュが温まっていない初期状態**を計測する。
`stop.sh`/`start.sh` で Redis は揮発（永続ボリュームなし）するため、再起動で
**カートキャッシュ・マスタデータキャッシュが全消失**（MongoDB データは保持）。再起動直後から
**ウォームアップなし**で計測。N=10 明細・12反復、legacy/stateless は**別の商品コード帯**を使い
（各パターンの初回取引が自分のコールド検索を負担）、毎反復で交互実行。

| 指標 | 従来 cold(iter1-2) | 従来 warm(last4) | ステートレス cold | ステートレス warm |
|---|---:|---:|---:|---:|
| firstScan(初回addItem) | 30.9 | 29.4 | **39.5** | 25.1 |
| bill | **64.3** | 56.5 | 33.7 | 32.3 |
| total(取引全体) | 450.4 | 388.1 | 401.1 | 352.8 |

（最コールドの iter1 単発: 従来 bill **77.1ms** / ステートレス bill **35.4ms**）

所見:
- **コールドでこそステートレスが有利**。従来の bill はサーバー側採番（`terminal_counter` の
  findAndModify ＋ レシート番号の設定値マスタ参照）がコールドで重く（iter1 で 77ms）、
  ステートレスは**持ち回り採番でこれを回避**（iter1 35ms）。差は最大 ~42ms、コールド平均でも
  64.3 → 33.7ms（約半減）。
- **ステートレス唯一のコールド・ペナルティは「最初の addItem」**（スナップショット機構＋
  大きい初回リクエストの直列化の温まり）: iter1 firstScan 55ms。**2反復ほどで収束**し、
  以降は逆に従来より速い（warm 25.1 < 従来 29.4）。
- **取引全体はコールド・ウォーム両方でステートレスが速い**（cold 401 vs 450 / warm 353 vs 388）。
- 注意: この短い再起動直後ウィンドウの「warm(last4)」は完全ウォームではない（従来 bill は
  トラフィック増でさらに下がり、§2 の定常では一段低い）。本補遺の価値は**コールド・
  トランジェントの形状と相対差**にある。

> まとめ: 再起動直後はどちらも全体で遅くなるが、**従来パターンの方がコールド・ペナルティが
> 大きい**（サーバー側採番がコールドキャッシュ/プールに依存するため）。ステートレスは
> 最初の1スキャンだけ温まりを要するが、確定処理のコールド劣化を回避し、初期状態でも
> 総合的に速い。

## 5. 計測の限界と今後

- 単一クライアント・直列・ローカル（低競合）での実測。ウォーム（§2-4）と
  コールド（§4.5）の両方を計測。**並行負荷時のスループット／競合時の cache バイパス効果は
  未計測**。
- localhost ループバック（実ネットワーク遅延ゼロ）。本番では転送量の影響が相対的に拡大。
- サンプル数が少なく（M=10〜12）、一桁 ms の差はノイズ範囲。
- DUAL モードのため従来経路もレスポンス用スナップショットを生成（純 phase-1 ではない）。

より厳密化するなら: (a) サーバー側計測でサーバー内訳を分離、(b) 並行負荷で
スループット／競合時の cache バイパス効果を計測、(c) 実商品マスタ分布での転送量再計測。

転送量の最適化候補（addItem レスポンスのスナップショットが主因）:
- **レスポンス・スナップショットとカートビューの重複排除**（レスポンスは一方のみ返す、
  あるいはスナップショット内 `cart_document` を参照に置換）。
- **スナップショットの圧縮／別エンドポイントでの分離取得**（毎回返さず必要時のみ）。
- **差分（delta）スナップショット**で全カートの再送を避ける。
- クライアント側のレスポンス展開（`br`/`gzip`）徹底（応答圧縮は導入済み: commit cb2a2b4）。

> 計測スクリプトは throwaway（`tmp_*`）として実行後に削除済み。本ドキュメント以外の
> リポジトリ変更はない。
