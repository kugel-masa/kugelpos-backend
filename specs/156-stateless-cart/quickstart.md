# Quickstart: client-carried cart phase 2（#156）

phase 2 の動作を手元のフルスタックで確認する手順。phase 1（#148）が有効（`SNAPSHOT_HMAC_KEYS` 設定済み）であることが前提。

## 前提

- `./scripts/start.sh` でフルスタック起動済み。
- cart の環境変数:
  - `SNAPSHOT_HMAC_KEYS="v1:<base64key>"`（phase 1 と同じ署名鍵）
  - `CART_REQUEST_SNAPSHOT_MODE=DUAL`（既定。あり/なし両経路を受理）
- JWT 認証のトークンを取得済み（フェイルオーバー検証は JWT 前提、#67）。

## シナリオ 1: スナップショット同梱で別バックエンドに繋いでも継続（SC-001）

1. バックエンド A でカート作成 → レスポンスの `data.signedSnapshot` を保持。
2. その `signedSnapshot` を**リクエストボディの `signedSnapshot`** に入れて、バックエンド B（独立 Redis/MongoDB）に商品追加。
3. B はキャッシュにそのカートを持たないが、スナップショットから再構成して商品を追加し、新しい `signedSnapshot` を返す。
4. 以降 小計 → 支払い → 確定 を、毎回直前の `signedSnapshot` を同梱して任意のバックエンドに送り、取引が1件確定することを確認。

期待: 専用の復旧操作（restore API 呼び出し）なしで継続。各レスポンスに最新スナップショットが付く。

## シナリオ 2: キャッシュ全損下でも継続（SC-002）

1. 進行中カート（スナップショット保持済み）。
2. cart の Redis を全消去（または停止）。
3. スナップショット同梱で商品追加 → 成功すること（404 にならない）。

期待: あり経路はキャッシュ非依存。なし経路（スナップショット無し）は従来どおりキャッシュ依存で、ここでは失敗しうる（DUAL の想定挙動）。

## シナリオ 3: 改ざん拒否（SC-003）

1. 正当なスナップショットの `cart_document` の金額を 1 箇所改ざん。
2. 任意の変更系 API に同梱して送信。

期待: 署名不一致で操作適用前に拒否（400）、カート状態に影響なし、監査に記録。全変更系エンドポイントで再現すること。

## シナリオ 4: 確定の lost-ACK 再送が二重計上にならない（SC-004）

1. 確定（bill）を送る。サーバ側で成功（tranlog 生成・pub/sub 発行）するが、レスポンスを擬似的に破棄。
2. 同じスナップショットで確定を**再送**（別バックエンドでも可）。
3. report / journal / stock を確認。

期待: 同じ `cart_id`・同じ `(business_counter, seq)` の取引として下流で cart_id 冪等に収束。会計合計は1件、在庫引き落としは1回。

## シナリオ 5: 端末交換（SC-005）

1. 端末 T で open（business_counter=N）→ 取引を seq 1..k まで確定。
2. T を停止し、代替端末 T' で **逐次** open（business_counter=N+1 を取得）。
3. T' で取引を継続・確定。

期待: T' の取引連番は `(N+1, 1..)`。`(N, *)` と衝突せず、seq の復元処理は発生しない。

## シナリオ 6: 圧縮リクエスト（FR-009）

1. .NET 8 クライアント相当で、`Content-Encoding: br`（または gzip）でスナップショット同梱リクエストを送る。
2. 展開後サイズが上限内なら正常処理。上限超過の偽装ボディは 413 相当で拒否。

期待: 展開して処理。非圧縮リクエストも従来どおり受理。

## 計測（SC-005 サイズ / SC-006 レイテンシ）

`/perf-test` 標準手順で、40 商品カートの**スナップショット同梱リクエスト**の圧縮後サイズ（≤15 KB）と、変更系 API の p95 増分（phase 1 実装比 +50ms 以内）を実測し、結果を issue #156 に記録する。
