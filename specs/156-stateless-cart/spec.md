# Feature Specification: 毎リクエストでのカートスナップショット提示とサーバ側キャッシュの権威降格（client-carried cart phase 2）

**Feature Branch**: `156-stateless-cart`
**Created**: 2026-06-13
**Status**: Draft
**SPEC_TYPE**: functional
**Issue**: [#156](https://github.com/kugel-masa/kugelpos-backend/issues/156)（parent: [#146](https://github.com/kugel-masa/kugelpos-backend/issues/146)）
**前提**: phase 1（[#148](https://github.com/kugel-masa/kugelpos-backend/issues/148) / PR #154、マージ済み）

---

## 概要

phase 1 では「カート変更系レスポンスに署名付きスナップショットを付加し、restore API で別バックエンドに復元できる」ところまでを実現した。サーバ側キャッシュ（Redis / MongoDB フォールバック）は引き続き正であり、スナップショットは障害時の持ち出しコピーだった。

本フェーズ（phase 2）はこれを一般化する: **POS は既存カートに対するすべての変更系リクエストに、最後に受け取った署名付きスナップショットを同梱する**。バックエンドは検証のうえスナップショットからカートを再構成し、要求された操作を適用し、新しいスナップショットを返す。これにより:

- **クライアント保持のスナップショットが取引状態の正となり、サーバ側キャッシュは権威でなくなる**。Redis タイムアウト → 進行中カートが 404、フラッピング時の新旧スプリットブレイン、空の MongoDB フォールバック、という障害カテゴリそのものが消滅する（#146 の分析）。
- POS はリクエスト単位で任意のエッジ/クラウドバックエンドに接続できる（バックエンドアフィニティ不要）。フェイルオーバーは「特別な復旧手順（restore API 呼び出し）」から「次のリクエストを送るだけ」になる。

phase 2 着手の判断材料だった phase 1 の実測（#148 T029）は予算内で完了している: 40 商品カートのスナップショット込みレスポンスは gzip 後 3.3 KB（予算 15 KB）、変更系 API の p95 増分 +28.2 ms（予算 +50 ms）。

マスタ（商品・税・設定・プロモーション）は引き続き**スナップショットに同梱**する（#146 でバージョン参照方式は却下済み — `cart.masters` はカタログ複製ではなく「このカートでスキャンした商品だけ」のセッションスナップショットであり、取引中のマスタ更新から明細価格を守る整合性保証そのものである）。

## 前提（Assumptions）

本仕様は以下を前提とする。前提が崩れる運用は本フィーチャーの対象外であり、設計の安全性保証も及ばない。

- **A-1（1カート=1クライアント）**: 1つのカート（`cart_id`）を同時に操作するアクティブなクライアントは常に1つ。これにより、クライアントが自分のリクエストを直列化し、カートの系譜は常に1本道（linear）になる。
- **A-2（逐次引き継ぎ）**: 端末故障時の代替端末への引き継ぎは**逐次**（端末1が操作を停止してから端末2が最新スナップショットで継続）に限る。同一カートを2端末が同時に操作する運用は対象外（A-1 違反）。phase 1 FR-012 の「同一店舗内なら別端末でも復元可」はこの逐次引き継ぎの範囲で適用する。
- **A-3（同一操作リトライ）**: クライアントは、レスポンスを受け取れなかった操作を**同じ操作・同じ入力**として再送する。直前の操作の結果を取り込む前に別の操作へ進むことはしない（これを行うと系譜が分岐＝フォークし、A-1 を崩す）。
- **A-4（採番権威としての端末）**: 取引連番の seq 部分は端末が単一の直列発行者として所有する（FR-012）。これは A-1/A-3 が成り立つことで安全に成立する。
- **A-5（スナップショットは不透明・全フィールド保存）**: クライアントは署名付きスナップショットを**不透明な塊として保持・返送**し、中身を解釈して再構成・改変してはならない。署名は `cart_document` の全フィールドにかかるため、クライアントが未知フィールド（将来サーバが追加する `seq`・`transaction_datetime` 等）を**1つでも落とすと署名が一致せず拒否**される。検証は canonical JSON（キーソート・正規化）で行うのでキー順・空白の変化は許容されるが、**フィールドの集合と値は完全に保存**しなければならない。実装上は、スナップショットを生 JSON（不透明文字列）として保持・送信するか、未知フィールドを保持する仕組み（例: .NET の `JsonExtensionData`）を用いること。「型付きで読んで未知フィールドを捨てる」往復は禁止。表示は従来のビュー（レスポンスの整形済みカート）で行い、スナップショットは触らず往復させる。

## Clarifications

### Session 2026-06-13

- Q: 同一 `cart_id` のサーバ側残存状態とスナップショットが乖離した場合の勝者は？（FR-005） → A: **提示スナップショットを正とする**。前提 A-1（1カート=1クライアント）により系譜は本来1本道であり、乖離（フォーク）は通常運転では発生しない異常系（複数端末の同時操作・レスポンス欠落後の枝分かれ等）。よって「どちらが新しいか」の順序づけ機構は設けず、提示スナップショットを正としたうえで、乖離が起きた事実は監査証跡に記録する（検知）。スカラーのリビジョン比較は lost-ACK 後の正当な再送を「巻き戻し」と誤検知するため、判定には用いない（監査の補助情報に留める）。
- Q: 取引連番（transaction_no / receipt_no）をステートレス・マルチバックエンドでどう採番するか？ → A: **`(business_counter, seq)` の複合とし、seq は開設セッション内連番として端末が持ち回る**。`business_counter` は terminal service が open のたびに払い出す**単調増加・非リセット**の値（`terminal_service.py:429`）。`seq` は開設セッション内で 1 から始まる連番で、端末がローカルに採番・前進させ、スナップショットで持ち回る。確定時に持ち回り中の `(business_counter, seq)` を tranlog に刻む。cart backend は採番についてステートレスとなり、現行の `terminal_counter`（MongoDB アトミックカウンタ）による transaction/receipt 採番は撤去する。**根拠**: (1) 通し連番は本質的に単一権威を要するが、`business_counter` を非リセットのエポックにすると `(business_counter, seq)` が単独で一意になり、(2) 端末交換・再開設は必ず open を伴い open ごとに `business_counter` が新値になるため、seq を持ち回っても**交換時の seq 復元が不要**（新エポックで seq=1 から再開）、(3) 採番が持ち回りで完結するため確定時に中央権威へ問い合わせる必要がなく、エッジオフラインでも確定できる。代償は「番号が複合で、開設セッションごとに seq がリセットされる」こと（営業日内に複数回開設すると seq が開設単位で分かれる）。
- Q: 取引確定時、クラウド側で確定が成功したがレスポンスが戻らず、クライアントが再送した場合の二重計上をどう防ぐか？ → A: **確定はゲートしない（中央レジストリもピン留めもしない）。重複した取引ログを許容し、下流の消費者（report / journal / stock）を `cart_id` キーで冪等にして収束させる**。確定取引ログは不変であり、前提 A-1/A-3 により2回の確定は同じスナップショットから同じ操作・同じ `(business_counter, seq)` を適用して内容も番号も同一になるため、冪等は **「`cart_id` が既処理ならスキップ（insert-if-absent / 先勝ち）」** とする（後勝ち upsert ではない — 既存レコードを保全）。これで合計はちょうど1件に収束し、採番ギャップも生じない。在庫引き落としも既処理 `cart_id` はスキップ（加算しない）。重複排除キーは全消費者で `cart_id` に統一する（`transaction_no` 単独をキーにしている箇所は是正対象）。現行の下流消費者は既に insert-if-absent（既存ありはスキップ）で実装されているため、変更はスキップ判定のキーを `cart_id` へ差し替えることが主。この収束機構が #152 の phase 2 における実体であり、#152 は phase 2 の**必須前提**。この方式はエッジオフライン確定と両立する（確定時に中央依存がない）。
- Q: 連番の正しさ（一意・欠番なし）は誰がどう保証するか？ → A: **端末が seq の単一権威であり、バックエンドはステートレスゆえ強制できない。よって整合性は「強制」ではなく「監査検知」とする**（#146 の許容+検知方針と一貫）。下流で `(terminal, business_counter, seq)` の重複・欠番を `cart_id` 基準で検知し、異常を記録する。会計金額は `cart_id` 後勝ちで1件に収束するため、端末の不具合で番号が乱れても**合計は崩れず**、番号異常のみが監査に上がる。
- Q: 取引時刻（`generate_date_time`）はあり経路でどう決定するか？ サーバ確定時刻だと lost-ACK でリトライ先の時刻が変わり、先勝ち台帳と客のレシート（リトライ応答由来）が食い違う。 → A: **クライアント（端末）が確定（bill）時に打刻し、bill リクエストで供給する**。理由: (1) 「取引時刻＝確定時に決定」という要件を満たす（レジが bill した瞬間）、(2) 打刻したのは端末自身なので lost-ACK でレスポンスが返らなくても端末は時刻を保持し、同じ値でリトライできる、(3) 決定論的になりどのバックエンドでも同一時刻 → 先勝ちスキップで台帳=レシートが一致、バックエンド間クロックずれの影響を受けない（源は単一の端末時計）。サーバ確定時刻＋後勝ち案は、全バックエンドのクロック厳密同期と不変台帳の上書きを要するため却下。代償は時刻がサーバ時計でなく端末時計になることだが、POS では取引時刻の源は販売時点（端末）が自然で、現行の「確定の瞬間」という意味も保てる。
- Q: スナップショットなしリクエスト（phase 1 型クライアント）の互換方針と、権威降格後のサーバ側キャッシュの形態は？（FR-004 / FR-008） → A: **デュアルモードを採る**。移行期間中は「スナップショットあり=クライアント保持スナップショットを正として処理（ステートレス経路）」「スナップショットなし=従来どおりサーバ側キャッシュを権威として処理（phase 1 経路）」を経路ごとに分岐する。これにより phase 1 型クライアントと phase 2 型クライアントが共存でき、クライアントの段階移行が可能になる。**含意**: デュアルモードである以上、サーバ側キャッシュ（権威）は移行期間中は撤去できない（なし経路の権威として必要）。よって FR-004 のキャッシュ撤去・サーキットブレーカー/フォールバック経路の除去は移行完了後に持ち越す（あり経路は移行期間中もキャッシュを参照しない）。あり経路の権威は常にスナップショット、なし経路の権威は常にサーバ側キャッシュ、と経路で権威が決まる（乖離時の規則は FR-005 のとおりあり経路はスナップショットを正とする）。デュアルモードの有効/無効は設定で切り替え、配備ごとに移行時期を選べるようにする。共存期間中はあり/なし × キャッシュ正常/障害の組み合わせをテストで担保する。

## 影響するサービス

| サービス名 | 変更の種類 | 変更の概要 |
|---|---|---|
| cart | 変更 | 変更系 API のリクエスト契約拡張（スナップショット受領・検証・再構成）、採番の持ち回り化（`terminal_counter` 撤去）、あり/なし経路の分岐（デュアルモード）、乖離検知と監査。サーバ側キャッシュの権威撤去は移行完了後 |
| terminal | 変更（軽微） | `business_counter` の払い出しは既存（open 時）。seq の初期値（=1）をセッション開始コンテキストに含める調整が必要な場合あり（plan で確定） |
| report / journal / stock | 変更 | 取引データ消費を `cart_id` キーの冪等 upsert（後勝ち）に統一。連番の一意・欠番の監査検知。`transaction_no` 単独キーの是正 |
| kugel_common（共通ライブラリ） | 変更 | 圧縮リクエストボディの受領（展開後サイズ上限ガード付き — phase 0 で意図的に保留した分）。署名・検証は phase 1 のユーティリティをそのまま使用 |

**影響なしのサービス**: account, master-data。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - どのバックエンドに繋いでも取引がそのまま続く (Priority: P1)

POS は商品スキャンのたびに変更系 API を呼ぶが、リクエストごとに接続先バックエンドが変わっても（ロードバランサ経由・エッジ→クラウド切替を含む）、取引は一貫して進行する。どのバックエンドもそのカートを「見たことがある」必要はなく、リクエストに同梱されたスナップショットから処理する。

**Why this priority**: phase 2 の存在理由。これが成立すればバックエンドアフィニティと専用復旧手順（restore API 呼び出し）が不要になる。

**Independent Test**: カートを作成後、後続の変更系操作（商品追加 → 数量変更 → 小計 → 支払い → 確定）を毎回**別のバックエンド**（独立した Redis/MongoDB）に対して、直前のレスポンスのスナップショットを同梱して実行し、全操作が成功して取引が 1 件確定することを確認。

**Acceptance Scenarios**:

1. **Given** バックエンド A で作成したカートと最新スナップショット、**When** スナップショットを同梱して商品追加をバックエンド B に要求する、**Then** B はカートを再構成して商品を追加し、更新後のカート状態と新しい署名付きスナップショットを返す。
2. **Given** スナップショット同梱で B に移った取引、**When** 後続操作（小計〜確定）を B または別のバックエンド C で行う、**Then** すべて成功し、取引ログ・レシートは取引開始時点のマスタ文脈で正しく生成される。*（実装・検証の区分: 編集系の跨ぎ継続は US1、確定（bill）の跨ぎ・決定論的採番・冪等収束は US4 で扱う。US1 の独立テストは編集系の継続までを範囲とする。）*
3. **Given** 変更系操作の成功レスポンス、**When** クライアントがスナップショットを確認する、**Then** 操作適用後の最新状態を反映した新しい署名付きスナップショットが含まれている（phase 1 FR-001 の継続）。

---

### User Story 2 - サーバ側キャッシュの障害が取引に影響しない (Priority: P1)

サーバ側キャッシュが全損・タイムアウト・フラッピングしていても、スナップショット同梱の変更系リクエストは正常に処理される。「Redis が読めない ⇒ 進行中カートが業務エラー（404）」というカテゴリが消滅する。

**Why this priority**: #146 が解決すると宣言した根本問題。phase 1 では障害後に restore という追加手順が必要だったが、phase 2 では障害がクライアントから観測不能になる。

**Independent Test**: 進行中カートの取引中にサーバ側キャッシュを停止・全消去し、スナップショット同梱の後続操作（商品追加〜確定）がエラーなく継続することを確認。

**Acceptance Scenarios**:

1. **Given** 進行中カートと最新スナップショット、**When** サーバ側キャッシュを全消去した直後にスナップショット同梱で変更系操作を要求する、**Then** 操作は成功し、専用の復旧操作（restore API）を要しない。
2. **Given** サーバ側キャッシュが応答しない（タイムアウト）状態、**When** スナップショット同梱で変更系操作を要求する、**Then** キャッシュ障害がレスポンスの成否を左右しない。

---

### User Story 3 - 改ざん・偽造されたスナップショットでは操作できない (Priority: P1)

毎リクエストがスナップショットを入力として受け付けるため、検証は毎リクエストで行う。金額・明細・マスタを書き換えたスナップショットを同梱した変更系リクエストは、操作の適用前に拒否される。

**Why this priority**: phase 2 では攻撃面が restore API 1 本から変更系 API 全体に広がる。検証が 1 箇所でも欠ければ「クライアントが任意の取引状態を注入できる」ことになる。

**Independent Test**: 正当なスナップショットの本文を改ざんして各変更系 API に同梱し、すべてのエンドポイントで操作適用前に拒否されること、拒否が追跡可能であることを確認。

**Acceptance Scenarios**:

1. **Given** 本文を改ざんしたスナップショット、**When** いずれかの変更系 API に同梱して要求する、**Then** 署名不一致として拒否され、カート状態への影響が一切ない（操作は適用されない）。
2. **Given** 他テナントまたは他店舗の正当なスナップショット、**When** 変更系 API に同梱して要求する、**Then** スコープ違反として拒否される（phase 1 FR-005/FR-012 と同一規則）。
3. **Given** 検証失敗の発生、**When** 運用者がログ/監査証跡を確認する、**Then** いつ・どの端末が・どの `cart_id` で・どの API で失敗したかを追跡できる。

---

### User Story 4 - 確定の重複・古いスナップショットでも取引がちょうど 1 件になる (Priority: P2)

通信リトライ・二重タップ・フェイルバックにより、最新でないスナップショットの提示や確定の再送は**通常運転として**発生する。とくに「クラウド側で確定が成功したがレスポンスが戻らず、クライアントが再送する」ケースが重要。方針は「許容 + 収束」: 重複した取引ログを許容し、下流を `cart_id` キーで冪等（既処理 `cart_id` はスキップ＝先勝ち）にして合計をちょうど1件に収束させる。

**Why this priority**: 金銭整合性に関わるが、正常系（Story 1〜3）の成立が前提のため P2。

**Independent Test**: 同一カートの確定を 2 系統（別バックエンド含む）で実施し、report / journal / stock のいずれでも計上・在庫移動がちょうど1件・1回に収束すること、連番異常が監査から追跡できることを確認。

**Acceptance Scenarios**:

1. **Given** クラウドで確定済み（レスポンス未達）の取引、**When** 同じスナップショットで確定を再送する、**Then** 同じ `(business_counter, seq)` の取引として下流で `cart_id` 冪等に収束し、合計・在庫が二重計上・二重引き落としされない。
2. **Given** 確定の重複が下流に届く、**When** report / journal / stock が消費する、**Then** いずれも `cart_id` 既処理ならスキップ（先勝ち）して1件に収束する（加算・再適用しない）。
3. **Given** 端末の不具合等で `(terminal, business_counter, seq)` に重複・欠番が生じる、**When** 運用者が監査を確認する、**Then** 異常を `cart_id` 基準で検知・追跡できる（会計合計自体は崩れない）。

### Edge Cases

- **スナップショットなしの変更系リクエスト**: デュアルモード（FR-008）により、なし経路として従来どおりサーバ側キャッシュ権威で処理。挙動は明確に定義され、暗黙にエラーカテゴリが変わってはならない。移行完了後（なし経路無効化）は明確なエラーで拒否。
- **スナップショットとサーバ側残存状態の乖離**（フェイルバック直後等）: FR-005 により提示スナップショットを正とし、乖離の事実を監査記録。本来 A-1 下では発生しない異常系。
- **確定後のレスポンス欠落 → 再送**: User Story 4。下流 `cart_id` 後勝ちで収束。採番は持ち回りのため再送でも同じ `(business_counter, seq)`。
- **端末交換（セッション途中の故障）**: 代替端末は逐次引き継ぎ（A-2）。open により新 `business_counter` を取得 → 新エポックで seq=1 から。旧エポックの番号と衝突せず、seq 復元も不要。
- **端末初期導入**: 初回 open で `business_counter` 払い出し、seq=1 から開始。
- **営業日内の複数回開設**: open ごとに `business_counter` が変わり seq がリセット。日内の取引番号は開設セッション単位で分かれる（複合キーの想定挙動）。
- **巨大カート**（数百明細）: 上り方向（リクエスト）のサイズが新たに加わる。展開後サイズ上限ガード（FR-009）の上限超過は明確なエラーで拒否し、カート状態への影響なし。
- **圧縮リクエストの展開失敗・偽装された巨大ボディ**: 展開後サイズ上限で拒否（FR-009 — 資源枯渇攻撃の防止）。
- **鍵ローテーション中 / スキーマバージョン不一致**: phase 1 FR-008/FR-011 と同一規則を毎リクエスト検証に適用。
- **照会系（GET）**: サーバ側キャッシュ撤去後の GET の応答ソースを定義する（FR-004。クライアントがスナップショットを保持しているため、GET はクライアント側で完結させる／または最小限の参照手段を別途定義 — plan で確定）。
- **カート作成直後のスナップショット欠落**（phase 1 NFR-004 の縮退でレスポンスにスナップショットが付かなかった場合）: 以降の変更系リクエストに同梱できない。縮退時の救済経路（再取得 or restore）を定義する。

## Functional Requirements *(mandatory)*

### FR-001: 変更系リクエストでのスナップショット受領と検証

既存カートに対するすべての変更系 API は、リクエストに署名付きスナップショット（phase 1 で定義したエンベロープと同一形式）を受け付けなければならない（MUST）。受領したスナップショットは操作適用前に検証しなければならず（MUST）、検証は phase 1 の restore と同一のパイプライン（形式 → スキーマバージョン → 鍵 ID → 署名 → スコープ → 状態）に従う（MUST）。検証に失敗したリクエストは操作を適用せず、カート状態・サーバ側残存データに一切影響を与えてはならない（MUST NOT）。

### FR-002: スナップショットからの再構成と操作適用

検証済みスナップショットから、バックエンドはそのカートを事前知識なしに再構成し、要求された操作を適用できなければならない（MUST）。再構成は取引開始時点のマスタ文脈（同梱 `cart.masters`）を維持する（MUST — 最新マスタの再取得で明細価格が変わってはならない）。操作適用後のレスポンスには、phase 1 FR-001 どおり最新の署名付きスナップショットを含める（MUST）。

### FR-003: レスポンス契約の維持

変更系レスポンスの構造（カートのビュー + 署名付きスナップショット + 既存フィールド）は phase 1 から変更しない（MUST — 後方互換）。

### FR-004: サーバ側キャッシュの権威（デュアルモード）

スナップショット同梱リクエスト（あり経路）の処理は、サーバ側キャッシュの可用性・内容に依存してはならない（MUST NOT — あり経路はスナップショットを正とする）。一方、移行期間中はデュアルモード（FR-008）を採るため、スナップショットなしリクエスト（なし経路）は従来どおりサーバ側キャッシュ（Redis 主・MongoDB フォールバック）を権威として処理する（MUST）。したがって移行期間中はサーバ側キャッシュおよび現行のサーキットブレーカー/フォールバック経路を残置する（MUST）。権威としてのキャッシュ撤去・経路の除去は**移行完了後**（全クライアントが phase 2 化し、なし経路が不要になった後）に行う。照会系（GET）の応答ソースは、移行期間中は従来どおりサーバ側キャッシュから供給してよい（移行完了後の GET のあり方は plan / 後続フェーズで確定）。

### FR-005: 乖離時は提示スナップショットを正とする

スナップショット同梱リクエストの処理時、同一 `cart_id` のサーバ側残存状態が存在し内容が乖離している場合、**提示された（検証済みの）スナップショットを正として処理しなければならない**（MUST）。提示スナップショットとの乖離が検出された事実は監査証跡（FR-007）に記録しなければならない（MUST）。前提 A-1 によりこの乖離は通常運転では発生しない異常系であり、順序づけ（新旧判定）機構は設けない。リビジョン等のスカラー比較は lost-ACK 後の正当な再送を誤検知するため、判定には用いない（監査の補助情報に留めてよい）。

### FR-006: 確定の重複許容と下流での冪等収束

取引の確定（bill）は重複実行を許容する（ゲートしない）。同一取引が会計上二重計上されてはならない（MUST NOT）が、その保証は**取引データを消費する全サービス（report / journal / stock）が `cart_id` をキーに冪等であること**で達成しなければならない（MUST）。確定取引ログは不変であり、前提 A-1/A-3 下で重複は同一内容になるため、**冪等は「`cart_id` が既に存在すればスキップ（insert-if-absent / 先勝ち）」とする**（MUST — 後から上書きする必要はない。既存レコードを保全する）。とくに在庫移動は `cart_id` 冪等でなければならず、既処理の `cart_id` は適用をスキップする（MUST — さもないと二重引き落とし）。重複排除キーは全消費者で `cart_id` に統一しなければならない（MUST — `transaction_no` 単独をキーにしている箇所は是正する）。なお現行の下流消費者は既に insert-if-absent（既存ありはスキップ）で実装されているため、本変更は**スキップ判定のキーを `transaction_no` タプルから `cart_id` へ差し替えること**が主となる。この収束機構の実装は #152 に属し、**#152 は phase 2 の必須前提**（サーバが権威を失った後、二重計上を防ぐ唯一の機構）。確定処理は中央権威への同期問い合わせを要してはならない（MUST NOT — エッジオフライン確定との両立）。

### FR-007: 監査証跡

検証失敗・乖離検知・連番異常（重複・欠番）・終端状態拒否は、追跡可能なかたちで記録しなければならない（MUST — いつ・どの端末・どの `cart_id`・どの API・スナップショット発行時刻・結果）。正常系の毎リクエスト処理をすべて記録してはならない（MUST NOT — 記録量がリクエスト数に比例して膨張するため。#155 のログ肥大問題を悪化させない）。連番異常の検知は `(terminal, business_counter, seq)` の重複・欠番を `cart_id` 基準で行う（FR-013）。

### FR-008: スナップショットなしリクエストの互換方針（デュアルモード）

変更系 API は、リクエストにスナップショットがあるかないかで権威を分岐しなければならない（MUST）:

- **あり経路**: 検証済みスナップショットを正としてステートレスに処理（FR-001/FR-002）。サーバ側キャッシュを参照しない（MUST NOT）。
- **なし経路**: 従来どおりサーバ側キャッシュを権威として処理（phase 1 と同一挙動）。

これにより phase 1 型・phase 2 型クライアントが共存でき、クライアントの段階移行が可能になる（後方互換）。

モードは**サービス全体の設定（環境変数）**で切り替える（MUST — phase 1 の `SNAPSHOT_HMAC_KEYS` と同じサービスレベルの設定方式に倣う）。すなわち切替の粒度はバックエンド配備単位であり、テナント別・店舗別の切替は本フィーチャーでは設けない。モードは少なくとも次の2状態を持つ: `DUAL`（なし経路を受理＝移行期間）と `REQUIRED`（なし経路を明確なエラーで拒否＝移行完了後）。なお、あり/なしの**経路分岐そのものは毎リクエスト自動**であり、設定はなし経路を許すか拒否するかのポリシーのみを制御する。

移行完了の判定のため、なし経路（スナップショット非同梱の変更系リクエスト）の発生件数を運用メトリクスとして観測可能にする（SHOULD — 一定期間ゼロを確認してから `REQUIRED` へ切り替える）。これは FR-007 の異常系監査とは別の運用メトリクスとする。移行完了後（全配備が `REQUIRED`）に、なし経路と FR-004 のキャッシュ撤去へ進める。共存期間中は、あり/なし × キャッシュ正常/障害の各組み合わせの挙動が明確に定義され、テストで担保されなければならない（MUST）。

### FR-009: 圧縮リクエストボディの受領

スナップショット同梱によりリクエストが大きくなるため、圧縮されたリクエストボディを受領できなければならない（MUST）。展開後サイズに上限を設け、超過は資源を消費しきる前に明確なエラーで拒否すること（MUST — 偽装された巨大ボディによる資源枯渇の防止）。クライアント側の圧縮は任意とし、非圧縮リクエストは従来どおり受領する（MUST — 後方互換）。クライアントは .NET 8（`BrotliStream` / `GZipStream` 標準対応）を前提とする。

### FR-010: restore API の残置

phase 1 の restore API は、明示的な復元用途のため残置する（MUST）。毎リクエスト復元と restore API の検証・監査規則は一致していなければならない（MUST — 同じ入力が経路によって異なる判定を受けてはならない）。

### FR-011: 署名鍵管理の継続とスナップショット相互運用性

署名鍵の管理・配布・ローテーションは phase 1 FR-011 の規則（共有シークレット + kid 世代管理、現行 + 前世代受け入れ、猶予 24 時間以上）をそのまま適用する（MUST）。phase 2 で新たな鍵・新たな署名方式を導入しない（MUST NOT — phase 1 発行のスナップショットが phase 2 バックエンドでもそのまま有効であること）。

### FR-012: 取引連番の持ち回り採番（`(business_counter, seq)` 複合）

取引連番は `(business_counter, seq)` の複合とし（MUST）、以下に従う:

- `business_counter` は terminal service が open のたびに払い出す単調増加・非リセットの値とする（既存挙動を踏襲）。
- `seq` は開設セッション内で 1 から始まる連番とし、端末がローカルに採番・前進させ、スナップショットで持ち回る（MUST）。
- 確定時、tranlog には持ち回り中の `(business_counter, seq)` を刻む（MUST）。cart backend は取引連番について新たなサーバ側カウンタを参照してはならない（MUST NOT — 現行 `terminal_counter` の transaction/receipt 採番は撤去する）。
- 端末交換・再開設は open を伴い新 `business_counter` を得るため、seq の復元を要してはならない（MUST NOT — 新エポックで seq=1 から再開する）。
- `receipt_no` も同様に複合・持ち回りとする（MUST）。

取引の一意性キーは `(tenant_id, store_code, terminal_no, business_counter, seq)` とする（MUST）。

**確定が決定論的であること（取引時刻のクライアント打刻・持ち回り）**: 確定（bill）の出力（tranlog・レシート）は、提示された carried snapshot ＋ クライアント供給の確定時刻の決定論的関数でなければならない（MUST）。レシートはレスポンス受領後に発行されるため、lost-ACK でリトライ先（別バックエンド）が確定し直しても、**同じ取引番号・同じ取引時刻・同じレシート内容**を返さなければ、確定済み台帳（先勝ち）と客の手元のレシートが食い違う。

**取引時刻はクライアント（端末）が確定（bill）時に打刻し、bill リクエストで供給する**（MUST）。バックエンドは現状のサーバ時刻スタンプ（`generate_date_time = get_app_time_str()`）ではなく、このクライアント供給値を tranlog の `generate_date_time` に用いる（MUST — サーバ時刻スタンプ禁止）。lost-ACK 時、クライアントは自分が打刻した確定時刻を保持しているため、レスポンスが返らなくても同じ値でリトライでき、どのバックエンドでも同一の取引時刻になる。確定後のレスポンスが返す新スナップショット（completed 状態）にはこの確定時刻が `transaction_datetime` として含まれ署名される。これにより確定が決定論的になり、先勝ちスキップ（FR-006）と台帳=レシートの一致が、バックエンド間のクロックずれに依存せず両立する（取引時刻の源は単一の端末時計）。端末が取引の同一性（cart_id）・連番（seq）・時刻を所有し、バックエンドはステートレスな処理機となる。

### FR-013: 連番整合性の監査検知

seq の単一権威は端末であり、ステートレスなバックエンドは連番の一意・欠番を強制できない。よって連番整合性は監査検知とする（MUST — #146 の許容+検知方針と一貫）。下流（report / journal）は `(terminal, business_counter, seq)` の重複・欠番を `cart_id` 基準で検知し、異常を記録しなければならない（MUST）。会計合計は `cart_id` 後勝ちで1件に収束するため、連番異常があっても合計を崩してはならない（MUST NOT）。

## Non-Functional Requirements

- **NFR-001（上りサイズ予算）**: 標準的な 40 商品カートで、スナップショット同梱リクエストの転送サイズ（圧縮時）が 15 KB 以下に収まることを実測で検証する。phase 1 の下り実測（gzip 後 3.3 KB、うちスナップショット部 ~2.1 KB）から上りも同水準と見込むが、実測で確認する。
- **NFR-002（レイテンシ予算）**: 毎リクエストの検証 + 再構成による変更系 API の応答遅延の増加は、phase 1 実装比で p95 +50 ms 以内に収める。実測で検証する。
- **NFR-003（セキュリティ）**: phase 1 NFR-003 を継続（鍵の非露出、検証失敗のセキュリティイベント記録）。攻撃面が変更系 API 全体に広がることを踏まえ、検証の欠落したエンドポイントがないことをテストで担保する（NFR-003）。
- **NFR-004（可用性）**: スナップショット検証失敗・サイズ上限超過は当該リクエストの失敗であり、進行中取引そのものを失わせてはならない（クライアントは手元の正当なスナップショットで再試行できる）。確定はエッジオフラインでも成立する（FR-006）。
- **NFR-005（記録量）**: 監査・リクエストログの増加がリクエスト数に比例して際限なく膨張しない設計とする（FR-007、#155 と整合）。

## Key Entities

- **スナップショットエンベロープ**: phase 1 で定義済み（スキーマバージョン・発行時刻・kid・帰属情報・カート文書全体・署名）。phase 2 では「レスポンスで受け取り、次のリクエストで返す」往復の単位になる。カート文書には持ち回り中の `seq`（および `business_counter`）が含まれる。スキーマ変更の要否は plan で確定。
- **取引連番**: `(business_counter, seq)` の複合。`business_counter` は terminal service 払い出し（open ごと・単調増加）、`seq` は端末が持ち回るセッション内連番。
- **乖離・拒否・連番異常の監査レコード**: phase 1 の restore 監査レコードを毎リクエスト検証に一般化したもの。記録対象は異常系のみ（FR-007）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 取引中の任意の時点で接続先バックエンドを切り替えても、専用の復旧操作なし（次の通常リクエストを送るだけ）で取引を継続し、会計完了まで到達できる。
- **SC-002**: サーバ側キャッシュの全損・タイムアウト下でも、スナップショット同梱（あり経路）の変更系操作の成功率が通常時と変わらない（キャッシュ起因で進行中取引が業務エラーになるケースが 0 件）。なし経路は従来挙動を維持する。
- **SC-003**: 内容を改ざんしたスナップショットを同梱した変更系リクエストは、全エンドポイントで 100% 拒否され、すべて追跡可能なかたちで記録される。
- **SC-004**: 同一取引（同一 `cart_id`）の確定を何度・どの経路（別バックエンド含む）で行っても、report / journal / stock のいずれでも計上・在庫移動がちょうど1件・1回に収束する。
- **SC-005**: 端末交換後、代替端末が再入力なしで取引を継続でき、連番が旧端末の番号と重複しない（`(business_counter, seq)` の一意性が保たれる）。
- **SC-006**: 標準的な 40 商品カートで、変更系リクエスト（スナップショット同梱・圧縮時）の転送サイズが 15 KB 以下、かつ変更系 API の p95 悪化が phase 1 実装比 +50 ms 以内であることが実測で確認される。

## Out of Scope

- **クライアント（POS フロントエンド）側のスナップショット保持・同梱・圧縮・seq 採番ロジック**: API 契約と採番規約のみ提供（実装はクライアント側）。
- **マスタのバージョン参照化**: #146 で却下済み。再検討しない。
- **リプレイ・乖離の「防止」**（ワンタイムトークン・nonce・サーバ側リビジョン強制・確定ゲート）: 方針は許容 + 収束/検知（#146）。
- **取引連番の「セッション跨ぎ／端末永久の単一通し整数」**: 本フィーチャーは `(business_counter, seq)` 複合（開設セッション内連続）を採る。単一通し整数は単一権威・中央採番を要し、ステートレス・オフライン確定と両立しないため対象外。
- **複数端末による同一カートの同時操作**: 前提 A-1/A-2 の対象外（逐次引き継ぎのみ）。
- **サーバ側キャッシュ（権威）・サーキットブレーカー/フォールバック経路の撤去**: デュアルモード採用のため移行期間中は残置。撤去は移行完了後（なし経路無効化後）の後続作業とし、本フィーチャーのスコープ外。
- **cart 以外のサービスの状態持ち出し**。
