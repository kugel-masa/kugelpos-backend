# Research: 処理できなかったイベントを見えるようにし、直したあとに流し直せるようにする

**Feature**: `230-dead-letter-handling` | **Date**: 2026-11-25（2026-11-27 に R-1・R-3・R-4・R-5・R-5b・R-6・R-7・R-12・R-13 を改訂し、R-5c・R-14・R-15 を追加）

---

## R-1: どこでデッドレターにするか（受け手の中で諦めて、MongoDB に記録する）

**調べたこと**

- ローカルのスタック（RabbitMQ 3.13.7、daprd 1.17.14）
  - 受け手のキューは `<app-id>-<topic>`（例 `report-topic-tranlog`）。引数 `x-dead-letter-exchange: dlx-<app-id>-<topic>`
  - デッドレターの交換機 `dlx-<app-id>-<topic>` は fanout。デッドレターキュー `dlq-<app-id>-<topic>` がそれに結ばれ、引数は `x-queue-mode: lazy`
  - Dapr の購読で `queueName: dlq-…` を指定すると、Dapr が自分の引数でキューを宣言し直そうとし、`inequivalent arg 'x-queue-mode'`（406）で断られる
- Dapr の RabbitMQ のコンポーネント（components-contrib）のタグを比べた
  - 既存のキューをそのまま使う `queueDeclareMode: passive` は v1.19.0 から。v1.17.x・v1.18.x には無い
  - Dapr 1.19.0 は 2026-10-22 に出た
- Azure Container Apps の Dapr は `1.16.4-msft.13`（既存の環境を Azure CLI で確認）。Microsoft の文書では、版は選べず固定もできない（"Custom version selection is not supported"）。上げるのは自動で、予定は決まっていない
- 受け手の再試行（`pubsub-resiliency.yaml`）は exponential、`maxInterval: 3m`、`maxRetries: 18`（最大 19 回渡す）。初めの間隔 0.5 秒、倍率 1.5、ゆらぎ ±50% は固定。n 回目が届く時刻は、ゆらぎによって大きくずれる

  | 渡す回 | 最も早い | 標準 | 最も遅い |
  |---|---|---|---|
  | 15 | 2.4 分 | 4.8 分 | 7.3 分 |
  | 17 | 5.1 分 | 10.3 分 | 15.4 分 |
  | 19（最後） | 8.1 分 | 16.3 分 | 24.4 分 |

**Decision**: 受け手が**自分で諦めて、MongoDB の `dead_letter` に「未対応」として記録し、RabbitMQ には SUCCESS を返す**。RabbitMQ のデッドレター（`dlq-*`）は、MongoDB にも書けないときだけの最後の受け皿として残す。

- 受け手の処理が失敗するたびに、`dead_letter` の記録の失敗の回数を 1 足す（R-4）。今回の一続きの失敗の回数が **17 回**（`DEAD_LETTER_GIVE_UP_AFTER_FAILURES`、既定 17）に達したら、同じ更新で記録を `pending` にし、受け手に渡った CloudEvent を保存して、SUCCESS を返す
- 記録が書けないとき（MongoDB の障害など）は RETRY を返す。Dapr が使い切ると、今までどおり `dlq-*` に移る（`requeueInFailure: "false"`、`enableDeadLetter: "true"` は変えない）
- 発行した側には「受け取った」を伝えない（今のコードでも、伝えるのは処理できたときだけ）

**諦める回数を 17 にする理由**

意図は「**標準で約 10 分（5〜15 分）は受け直し、それで直らなければ諦めて人に渡す**」こと。17 はその長さを Dapr の受け直しの回数に読み替えた値で、どれくらい続く障害が多いかというデータから決めた数ではない。

- **#238 の受け直しの設定は変えない。** 最大 19 回（標準 16 分）のまま、その範囲の中でアプリが諦める
- **Dapr の最後の回より前に諦める。** 19 回目まで粘ると、その回で記録が書けなかったときに Dapr が使い切り、記録されないまま `dlq-*` に落ちる
- **余裕は 2 回（判断）。** アプリは今が何回目かを知らず（Dapr は回数を渡さない）、記録の `episode_failure_count` で数える。記録が書けなかった回と、受け手に届かなかった配送（サービスの再起動中など）は数えられない。1 回の余裕では数え損ね 1 回で間に合わず、3 回以上にすると受け直しの時間が大きく縮む。19 − 2 = 17
- **時間では決めない。** ゆらぎで最後の回（19 回目）が 8.1 分に来ることがあり、時間の条件を待つあいだに Dapr が先に使い切る
- **上限そのものは増やせない。** `maxRetries` を増やして 19 回で諦めようとすると、最も遅いときの合計が RabbitMQ の `consumer_timeout`（30 分）を超える
- 二重の配送で多めに数えることはあるが、早く諦めるだけで、失うことはない
- 数え損ねが 3 回以上になって間に合わなかったものは、R-14 の掃除が「失敗中」の取り残しとして 30 分後に「未対応」に上げる。失うことはなく、気づくのが遅れるだけなので、余裕の 2 回は厳密な値ではない

**回数が多く見える理由**: 間隔は 0.5 秒から 1.5 倍ずつ延びる（上限 3 分）ので、17 回のうち 11 回は最初の 1 分以内（標準 54 秒）に終わる。前半の短い間隔は一瞬の失敗（DB の切り替え、ほかのサービスの再起動）を、後半の長い間隔は数分続く障害を吸収する。回数が多くても、Slack は 1 回、DB への書き込みは失敗のたびの小さな更新 1 回、ログは失敗のたびに 1 行（今の 19 行から 17 行に減る）。

**引き換え**: 直らない失敗でも、約 10 分は「失敗中」のままで通知が来ない。短くするほど早く気づけるが、短い障害（デプロイや DB の切り替えと重なったとき）で未対応が増え、そのたびに人が流し直す。

| 諦める回数 | 標準の時刻（幅） | 一時的な障害への強さ |
|---|---|---|
| 13 回 | 2.1 分（1.1〜3.2 分） | 2〜3 分続く障害で諦める |
| 15 回 | 4.8 分（2.4〜7.3 分） | 5 分ほどの障害なら吸収する |
| **17 回（既定）** | **10.3 分（5.1〜15.4 分）** | 今の 16 分に近い強さを残す |

**変えるとき**: `DEAD_LETTER_GIVE_UP_AFTER_FAILURES` で変えられる。早く諦める方向（17 より小さく）は安全で、Dapr の上限との余裕が大きくなる。大きくする方向は、予算のテスト（`services/report/tests/unit/test_pubsub_redelivery_budget.py`、resiliency の `maxRetries` + 1 より 2 回以上少ない）で止まる。e2e では `DEAD_LETTER_GIVE_UP_AFTER_FAILURES` を小さくし、`maxRetries` もそれに合わせる

**Rationale**:

- Dapr の版に依存しない。Azure の 1.16 でも、手元の 1.17 でも、のちの 1.19 でも同じに動く
- 記録用のコンポーネント・キュー・ルートが要らない。デッドレターに移す判断と記録が 1 回の更新で済み、二重の配送でも「未対応になった」は 1 回しか起きない
- 記録が控えになる。RabbitMQ の `dlq-*` に残るのは、記録できなかったものだけになる

**Alternatives considered**:

- 受け手ごとのデッドレターの交換機（fanout）に、記録用の購読（`pubsub-deadletter`）を足す（改訂前の案）: 動くが、コンポーネント・キュー・受け取りのルートが増える。二重の配送と通知を分ける工夫や、記録用の購読の失敗の分け方（改訂前の R-5b）も要る。`dlq-*` を控えとして残すために、期限のポリシーを RabbitMQ の起動のコマンドで入れる仕掛け（改訂前の R-12）も要った
- `queueName: dlq-<app-id>-<topic>` で既存のキューを直接読む: 1.17 では 406 で失敗する
- Dapr 1.19 に上げて `queueDeclareMode: passive` で `dlq-*` を読む: Azure Container Apps は 1.16.4 で、版を選べない
- 各サービスが AMQP のクライアントで `dlq-*` を直接読む: 新しい依存が増え、Dapr を通らない経路ができる
- 記録を 1 つのサービスに集める: 流し直しで受け手を呼ぶために、サービスのあいだの呼び出しと認証が増える（R-3）

**最後の受け皿（`dlq-*`）に落ちるもの**: 17 回のうち MongoDB に書けなかった失敗（障害が長く続いたとき）と、テナントのわからないイベント（R-6）。どちらも、起きたその場で運用の担当者に知らせ（R-5c）、戻す手順は R-13。

## R-2: 誰が記録を持つか

**Decision**: report・journal・stock の**それぞれが、自分のデッドレターを記録し、API を持つ**。記録は、各サービスのテナントごとの DB に `dead_letter` コレクションとして置く。共通の部分（文書・リポジトリ・失敗の記録・通知・流し直し・API のルーター）は `kugel_common.dead_letter` に置き、3 サービスは配線だけをする。

**Rationale**: 失敗は受け手の中で起き、記録も受け手の中で書く（R-1）。流し直しも受け手が自分で行う（R-3）。記録・照会・流し直しが 1 つのサービスの中で閉じる。

**運用の担当者から見た違い**: 一覧は 3 つのサービスにそれぞれ問い合わせる。どのサービスに記録があるかは通知に出る。

## R-3: 流し直しの渡し方と、処理の本体の形

**Decision**: 流し直しは、受け手の**サービスの中で、購読の処理の本体を直接呼ぶ**。記録した中身（Dapr が受け手に渡した CloudEvent）をそのまま渡す。処理は同期で、結果をその場で返す（まとめての流し直しは R-7）。

**本体と薄いルートの分け方**: 3 サービスの購読の処理を、`Request` を受けない本体と、購読の薄いルートに分ける。

- 本体は CloudEvent の dict とトピックを受け、**処理の結果だけ**を返す。`PROCESSED`（処理できた）、`ALREADY_PROCESSED`（イベント ID の記録があり、処理済み）、`DROPPED(理由)`（形が壊れている）、`FAILED(理由)`（処理できなかった）
- 本体は、失敗の記録（`record_failure`）も、発行した側への「受け取った」の通知もしない。今は依存の解決で組み立てている `LogService` は、本体の中で組み立てる
- 購読のルートが結果を Dapr への応答に変える

  | 本体の結果 | 購読のルート |
  |---|---|
  | `PROCESSED` / `ALREADY_PROCESSED` | 発行した側に「受け取った」を伝え（今と同じ best-effort）、SUCCESS |
  | `DROPPED` | 今と同じ DROP の扱い |
  | `FAILED` | `record_failure`（R-4）。`GAVE_UP` / `ALREADY_RECORDED` なら SUCCESS、`KEEP_RETRYING` か例外なら RETRY |

**流し直し**: 引き受け（R-7）→ 本体を `asyncio.wait_for` 30 秒で呼ぶ → claim を条件に結果を書く。

- `PROCESSED` / `ALREADY_PROCESSED`: 記録を「流し直し済み」にする。そのあと、時間の上限の外で、発行した側に「受け取った」を best-effort で伝える
- `DROPPED`: 記録を「破棄」にし、理由に `dropped by the handler: <理由>` と書く
- `FAILED`・例外・時間切れ: 記録を「未対応」に戻し、`last_error`・`last_failed_at`・`failure_count` を流し直しが書く。失敗を返す。通知しない（操作した人がその場で結果を見ている）
- 流し直しは `record_failure` を呼ばない。流し直しの失敗で「記録できない」の知らせ（R-5c）が出ることもない

**Rationale**:
- 元のトピックに出し直すと、fanout なので、すでに処理できたほかの受け手にも届く。受け手の中で呼べば、その受け手にだけ渡る（FR-009）
- 同期なので、流し直しが効いたかどうかがその場でわかる
- 本体が処理の結果だけを返すので、購読と流し直しが同じ本体を使っても、結果の解釈が混ざらない（改訂前は、流し直し中の失敗が「記録済み」として SUCCESS に化け、「流し直し済み」になる穴があった）
- 発行した側への通知（`HttpClientHelper` の既定で最大 30 秒 × 3 回）を時間の上限の外に出すので、保存できたのに時間切れで「失敗」になることがない

**二重の処理を防ぐ仕組み**: 受け手のイベント ID の記録（状態ストア、48 時間）と一意の索引（#238・#240）。状態ストアの記録は処理が成功したあとにだけ書く（`report/app/api/v1/tran.py` の `save_state`）ので、諦めたイベントには記録が無く、流し直せば処理される。48 時間を過ぎていても、一意の索引が二重を防ぐ。閉設ログは `insert_if_absent` で保存するので、流し直すと精算の確定がもう一度走る（SC-005）。

**時間切れで途中で止めたとき**: 例外で途中で止まるのと同じで、今の受け直しでも起きる。stock は品目ごとに冪等（`stock_service.py`）、report・journal は 1 件の保存と一意の索引なので、次の流し直しで二重にならない。複数の品目の途中で止めたあとの流し直しのテストを足す。

**イベント ID**: 3 つの受け手とも、イベント ID の無いメッセージは失敗より前に DROP する（`report/app/api/v1/tran.py`、`journal/app/api/v1/tran.py`、`stock/app/api/v1/stock.py`）。記録は必ずイベント ID を持つ。

**確定した精算とのかかわり**: #343 で、精算が確定した営業の日報はあとから変えない。report で取引のイベントを流し直しても、`log_tran` に入るだけで、確定した精算実績・日報・欠けの件数は変わらない（US2 の場面 6、SC-004）。

## R-4: 失敗の記録と、諦める判断

**事実**: 失敗の理由は、失敗した受け手の中にしか無い。RabbitMQ のデッドレターのメッセージにも入らない。

**Decision**: 購読のルートは、本体が `FAILED` を返したら `record_failure` を await で呼ぶ。`record_failure` は `dead_letter` を 1 回の `find_one_and_update`（パイプラインの更新、upsert、**変更前の文書を返す**）で更新する（イベント ID ごとに 1 件）。

- `_id` はイベント ID にする（DB がサービス・テナントごとなので、それだけで 1 件に決まる）。索引の準備がまだでも同じ記録に集まる。upsert が重複キーで失敗したら（同時に最初の文書を作った）、1 回だけやり直す
- 外から来た値（CloudEvent、`summary`、`last_error`、トピック）は、すべて `{"$literal": …}` で包む。パイプラインの更新では、`$` で始まる値がフィールドのパスとして読まれるため
- 常に: `last_error`・`last_failed_at` を書き、`failure_count` を 1 足す。`first_failed_at` は無ければ書く。**`message` と `summary` は無ければ書く**（最初の失敗で保存する。R-14 の掃除で「未対応」に上げるときに要る）
- 変更前の状態ごと（全体の表は data-model.md）
  - 記録が無い・`failing`: `episode_failure_count` を 1 足す。17 に達したら `pending` にし（`purge_at` を外す、`dead_count` を 1 足す、`first_dead_at` は無ければ・`last_dead_at` を書く、`notified_at` を消す）、達しなければ `failing`（`purge_at` = now + 1 日）
  - `replayed`・`discarded`（発行した側が同じイベントを送り直した、など）: 状態は変えずに `episode_failure_count` を 1 足し、`message` を新しい中身で書き直す。`purge_at` が now + 1 日より前なら now + 1 日に延ばす（数えている途中で TTL で消えないように）。17 に達したら上と同じく `pending` にする（`resolved_*` と `replay_claim_*` も消す）
  - `pending`・`replaying`: 理由と回数だけを更新する。状態は変えない
- 判断は、返った変更前の文書から決める（パイプラインの式と同じ規則を Python でも持つ）
  - `GAVE_UP`（「未対応になった」）: 変更前が `—` / `failing` / `replayed` / `discarded` で、変更前の `episode_failure_count` + 1 が 17 以上 → 通知し（R-5）、購読には SUCCESS
  - `ALREADY_RECORDED`: 変更前が `pending` / `replaying` → すでに記録してあるので、購読には**すぐ SUCCESS**（17 回待たない）。通知しない
  - `KEEP_RETRYING`: それ以外 → 購読には RETRY
- 記録が書けない（例外）: `notify_unrecordable`（R-5c）で知らせてから例外を上げ直し、購読には RETRY
- 本体の失敗の理由が MongoDB につながらないこと（`ConnectionFailure`・`ServerSelectionTimeoutError` など）なら、記録を試さずに `notify_unrecordable` だけをして RETRY を返す（書けないとわかっている記録で、配送の時間を延ばさない）
- 1 回の記録に 5 秒の上限を付ける（`asyncio.wait_for`）。超えたら書けなかったものとして扱う。DB の既定のソケットの時間切れ（30 秒）を待たない（R-1 の予算）
- `episode_failure_count` は、`replayed`・`discarded` になったときに 0 に戻す
- 「失敗中」の記録は TTL の索引で消える（R-14 の掃除で消すこともある）。**成功の経路には書き込みを足さない**

**数え損ね**: アプリに届かなかった配送（サービスの再起動中、401/403、依存の解決の中の例外）は、Dapr には失敗の 1 回でも、`record_failure` まで届かない。記録が書けなかった回と合わせて 3 回以上になると、Dapr が先に使い切って `dlq-*` に移る。このとき記録は `failing` のまま残るので、R-14 の掃除が「未対応」に上げて通知する。中身は最初の失敗で保存してあるので、流し直せる。

**同時に届いたとき**: 同じイベントが 2 つのワーカーで同時に失敗しても、`find_one_and_update` は 1 件ずつ順に適用される。変更前の `episode_failure_count` が 16 なのは 1 回だけなので、「未対応になった」は 1 回しか起きない（`_id` がイベント ID なので、索引が無くても成り立つ）。

**書けたのに SUCCESS の応答が失われたとき**: 同じイベントがもう一度届く。原因が残っていれば失敗し、変更前が `pending` なのですぐ SUCCESS（通知しない）。原因が直っていれば処理でき、記録は `pending` のまま残る（成功の経路に書き込みを足さないため）。運用の担当者が流し直すと、受け手は処理済み（`ALREADY_PROCESSED`）として二重に数えずに成功を返し、記録は `replayed` になる。

## R-5: 通知を 1 回にする

**Decision**:
- report と journal の購読の処理から、失敗のたびの `send_fatal_error_notification` を外す。失敗はログに残す（FR-008）
- 通知は、記録が「未対応」になったとき（R-4 の `GAVE_UP`、または R-14 の掃除が上げたとき）に送る。判断は 1 回の更新で決まるので、複数のワーカー・レプリカ・二重の配送でも増えない
- 送れたら `notified_at` を書く。「未対応」になるときは `notified_at` を消す
- **送り損ねは R-14 の掃除が拾う**。Slack が失敗した、通知の前にプロセスが落ちた、のときは `notified_at` が空のまま残る。掃除が、「未対応」になってから 2 分を過ぎて `notified_at` が空の記録を、条件付きの更新で引き受けて（`notify_claimed_at`、10 分）送り直す。送るたびに `notify_attempts` を 1 足し、5 回で諦める（Slack が設定されていない環境で送り続けない）。届かなかったものは一覧の `notified=false` で見える
- 送ったあと `notified_at` を書く前に落ちると、次の掃除がもう一度送る。通知は**まれに 2 回届くことがある**（取りこぼすよりよい）
- Slack への送信に 5 秒の上限を付ける（`slack_notifier` は時間切れを指定していない）
- 通知の失敗は、購読の結果（SUCCESS）に影響しない
- 本文には中身を載せない。失敗の理由は**例外の型だけ**を載せる（R-15）

**Alternatives considered**:
- 最大 1 回で、送り損ねは人が `notified=false` を見て拾う（改訂前）: プロセスが落ちると、通知が 0 回のまま誰も気づかない
- 送る通知を DB の outbox に置き、別のワーカーが送る: R-14 の掃除が同じ役目を、記録の文書のフィールドだけで果たす

---

## R-5a: まとめた通知の窓

**Decision**: テナントと受け手ごとに 5 分の窓を持つ（`dead_letter_alert` の 1 文書）。通知するかを決めるたびに、1 回のパイプラインの `find_one_and_update`（upsert、変更後の文書を返す）で窓を進める。

- 窓が無いか、`window_started_at` が 5 分より前: 新しい窓にする（`window_started_at = now`、`count = 1`、`topics` はこのトピックだけ 1）。前の窓の `suppressed` を `carried_suppressed` に移す
- それ以外: `count` を 1 足し、`topics.<topic>` を 1 足す。`count` が 10 を超えたら `suppressed` も 1 足す
- 返った `count` で決める
  - 1〜9: 1 件ずつ通知する。`count` が 1 で `carried_suppressed` があれば、「前の 5 分で送らなかった N 件」を添える
  - 10: 件数とトピックごとの数をまとめた通知を 1 回送る（10 件目そのものは、まとめの中に入る）
  - 11 以上: 送らない
- upsert が一意の重複で失敗したら（2 つのワーカーが同時に最初の文書を作った）、1 回だけやり直す
- 窓の終わりを知らせる仕組みは作らない。送らなかった件数は、次の窓の最初の通知に添える。それまでは、まとめの通知が「残りは一覧で見る」と案内する

---

## R-5b: 記録の失敗の扱い

**Decision**: 失敗の記録（R-4）が書けないときは、例外の種類によらず RETRY を返す。Dapr の再試行に任せ、使い切ったら `dlq-*` に移る。

**Rationale**: 改訂前は、記録用の購読が `requeueInFailure: "true"` で戻すので、障害ではない理由で何度書いても失敗する 1 件が回り続けないよう、例外を分けて取り除いていた。今は受け手の購読そのもので、Dapr の再試行に上限があり、使い切れば `dlq-*` に移るので、回り続けない。分ける必要が無い。

**数え方**: `dead_count` は「未対応になった」回数で、R-4 の判断が 1 回しか起きないので、二重の配送でも正確。`failure_count` は配送の回数を数えるので、二重の配送で多めになることがある（目安）。

---

## R-5c: 記録できないときの知らせ

**Decision**: 記録が書けない失敗（`record_failure` の例外）と、テナントのわからないイベント（R-6）が起きたら、`notify_unrecordable` で運用の担当者に知らせる。記録が無いので、通知の窓は**サービスのプロセスの中**に持つ（レプリカごと）。

- 窓は 5 分。窓の最初の 1 件だけを送り、残りは数える。次の窓の最初の通知に「前の 5 分でほか N 件」を添える
- 本文はサービス・トピック・テナント（無ければ `unknown`）・イベント ID（無ければ `unknown`）・例外の型。中身は載せない。受け直しが続くこと、使い切ったら `dlq-<app>-<topic>` に移ることと、見つけ方（R-13）を添える
- `record_failure` が例外を捕まえて知らせてから、例外を上げ直す。購読の処理は今までどおり RETRY を返す
- 送れなくても、例外は出さない（購読の結果は変えない）

**Rationale**: これが無いと、`dlq-*` に落ちるもの（記録できなかったもの）だけが誰にも知らされない。落ちる原因が起きたその場で知らせれば、テナントがわからなくても伝えられ、MongoDB の障害そのものの知らせにもなる。失敗のたびに送ると、#230 の「通知が多すぎる」に戻るので、5 分に 1 回までにする。

**Alternatives considered**:
- `dlq-*` の件数を定期的に見て知らせる: RabbitMQ の管理 API の接続先と認証情報が要り、Azure の構成にも依存する。`dlq-*` の棚卸しとして、別に扱う
- 外の監視（Azure Monitor など）でキューの長さを見る: このリポジトリの外。配備の側で扱う

---

## R-6: テナントがわからないイベント

**Decision**: 中身から `tenant_id` を読めないイベントは、記録する DB が無い。本フィーチャーでは扱いを変えず、今までどおり受け直しを使い切って `dlq-*` に移す。失敗はログに残り、R-5c の知らせ（5 分に 1 回まで）で運用の担当者に伝わる。report・journal は、`tenant_id` が無くて 400 を返す分岐で知らせる。`dlq-*` に移ったものは R-13 の手順で戻す。

**Rationale**: テナントごとの DB しか無く、テナントの無い記録を置く場所が無い。取引・入出金・開設精算のログは必ず `tenant_id` を持つので、起きるのは中身が壊れたときだけ。report と journal は、テナントの無いメッセージを依存の解決で 400 にする（RETRY と同じに扱われる）。stock は最初から DROP するので移らない。DROP に変えるのは #238 の振る舞いの変更で、範囲の外。

---

## R-7: 状態の移り変わりと同時の操作

**状態**: `failing`（失敗中）、`pending`（未対応）、`replaying`（流し直し中）、`replayed`（流し直し済み）、`discarded`（破棄）。すべての状態とできごとの組み合わせは data-model.md の表に書いた。

**Decision**:
- 流し直しは、条件付きの更新で引き受ける。条件は「`pending`、または `replaying` で `replay_claimed_at` が 10 分より前」。引き受けるときに新しい `replay_claim_id`（UUID）と `replay_claimed_at` を書く。引き受けたワーカーだけが処理を呼ぶ（FR-013）。もう一方は 409
- 結果を書く更新は、`state = replaying` と自分の `replay_claim_id` を条件にする。引き受け直されたあとに遅れて終わった前の流し直しは、条件に合わず何も書かない（結果は API の応答には返るが、記録は新しい持ち主のもの）
- 1 件の時間の上限（30 秒、R-3）は引き受けの期限（10 分）よりずっと短い。期限を過ぎるのはワーカーが落ちたときだけ
- まとめての流し直しは、受け付けたら 202 を返し、サーバーの中の裏の処理で 1 件ずつ順に流し直す（1 回に 100 件まで）。要求の時間切れ・接続の切断に縛られない。結果は一覧（`state`）で見る。途中でサービスが落ちたら、引き受けたままの記録は 10 分で引き受け直せ、まだ引き受けていない記録は `pending` のまま残る
- 破棄も `pending` の条件付きの更新
- 流し直し中に、同じイベントが購読から届いて失敗した: 状態は変えず、回数と理由だけを更新し、購読にはすぐ SUCCESS（R-4）。流し直しの結果が状態を決める

---

## R-8: 保持

**Decision**: `replayed` と `discarded` になったときに `purge_at = now + 90 日` を付け、TTL の索引で消す。`pending` と `replaying` には付けない（FR-020）。`failing` は `purge_at = now + 1 日`（R-4）。`pending` に変わったら `purge_at` を外す。

---

## R-9: 権限

**Decision**: API は、人がサインインして得た利用者の JWT だけで受け付ける。commons に新しい依存 `get_user_with_token` を足す。

- 端末の JWT は 403（`_refuse_terminal_credential`、#331 と同じ）
- サービスアカウントの JWT（`is_service_account`）は 403
- 端末の API キーだけ（JWT なし）は 401（JWT が無い）
- 返すのは `username` と `tenant_id`。パスのテナントと違えば 403。既存の `verify_tenant_id` は 400 を返すので使わず、ルーターの中で比べて 403 を返す。`username` は `resolved_by` に書く

このシステムの利用者の JWT は、すべて本部の利用者のもので、役割の区別はない。FR-019 の「本部の利用者」は、利用者の JWT であることで満たす。

**Rationale**: 記録には個人情報を含む取引の中身がある。端末やサービスからは読めないようにし、流し直し・破棄は人の操作だけにする。

## R-10: エラーコード

各サービスの範囲に 1 つずつ足す。共通のコードは `kugel_common.dead_letter` が受け取る。

| 意味 | report | journal | stock | HTTP |
|---|---|---|---|---|
| 記録の状態が変わっていて、流し直せない・破棄できない | `413009` | `411007` | `414404` | 409 |

記録が見つからないのは、既存の `100001`（404）。イベント ID が無い記録は作られない（R-3）ので、そのためのコードは足さない。

stock の購読の処理（`handle_transaction_log`）は Slack に通知していない。失敗の記録と諦める判断（R-4）、流し直しだけを足す。stock は `topic-tranlog` だけを購読する。

## R-12: `dlq-*`（最後の受け皿）の期限

**Decision**: `dlq-*` に期限を付けない（改訂前の 90 日のポリシーはやめる）。FR-022 は削る。

**Rationale**: `dlq-*` に残るのは、記録できなかったもの（R-1 の最後）だけになった。ほかのどこにも控えが無いので、期限で消すと黙って失う。量は MongoDB の長い障害か、中身の壊れたイベントの分だけで、ふだんは 0 件。

**Alternatives considered**（改訂前の案。記録が控えになったので要らなくなった）:
- RabbitMQ のコンテナが起動するたびに `rabbitmqctl set_policy` で `^dlq-` に `message-ttl` 90 日を入れる（起動のコマンドを `su-exec rabbitmq`・`HOME=/var/lib/rabbitmq`・`await_startup` の繰り返しで包む。使い捨てのコンテナで動くことを確かめた）
- 起動時に読む定義のファイル: データの無いノードで既定の vhost とユーザーを作らなくなり、起動に失敗する（確かめた）
- Purge: キューを丸ごと消すので選べない

## R-13: `dlq-*` に落ちたものを戻す

**対象**: R-1 の最後の受け皿に落ちたもの（MongoDB の長い障害、テナントのわからないイベント）と、配備より前から `dlq-*` にたまっていたもの（古いデータのある環境だけ。新しく作る環境では要らない）。

**Decision**: 原因を取り除いてから、`dlq-<app>-<topic>` のメッセージを、**その受け手の購読のキュー `<app>-<topic>`** に戻す。受け手はふつうに受け直し、処理できればそこで終わり、17 回失敗すれば記録が `pending` になって通知される。

- RabbitMQ の shovel のプラグイン（`rabbitmq_shovel`、`rabbitmq_shovel_management`。同梱）を、戻すときだけ `rabbitmq-plugins enable` で有効にする
- 動的な shovel を、元 `dlq-<app>-<topic>`、先 キュー `<app>-<topic>`（既定の交換機）、`src-delete-after: queue-length` で作る。始めた時点の件数だけを移して止まる。購読のキューに直接入れるので、ほかの受け手には届かない
- 念のため、先に管理画面の Get messages（requeue あり）か `rabbitmqadmin` で書き出す
- 確かめ: shovel が移した件数と、`dlq-*` が空になったこと。戻したものの行き先（処理できた / `pending` になった）は、受け手のログと一覧で見る

**監視**: `dlq-*` の件数は、ふだんは 0 件。RabbitMQ の管理 API（`/api/queues`）か `rabbitmqctl list_queues name messages` で、0 でない `dlq-*` を見つける。落ちる原因が起きたときは R-5c で知らせが届く。`dlq-*` の件数を定期的に見る仕組みは本フィーチャーの範囲の外で、手順だけを文書に書く。

---

## R-14: 定期の掃除

**Decision**: report・journal・stock のそれぞれが、5 分ごとに全テナントの `dead_letter` を見る（stock の `multi_tenant_snapshot_scheduler.py` と同じく、DB の名前 `db_<service>_<tenant>` からテナントを集める）。共通の部分は `kugel_common.dead_letter.sweep` に置く。どの更新も条件付きなので、レプリカが同時に走らせても二重にならない。

1. **取り残された「失敗中」**: `state = failing` で `last_failed_at` が 30 分より前の記録。Dapr の受け直しはもう終わっている（最も遅いときの合計 24.4 分、`consumer_timeout` 30 分）
   - 受け手のイベント ID の記録（状態ストア、処理が成功したあとにだけ書く）があれば、途中で成功していたので、記録を消す
   - 無ければ、Dapr が使い切って `dlq-*` に移ったもの（R-4 の数え損ね）。条件付きの更新（`state = failing` かつ `last_failed_at` が同じ）で `pending` に上げ、通知する（R-5）。中身は最初の失敗で保存してある
2. **送り損ねた通知**: `state = pending`、`notified_at` が空、`last_dead_at` が 2 分より前、`notify_attempts` が 5 未満、`notify_claimed_at` が空か 10 分より前の記録。`notify_claimed_at` を書いて引き受けてから送る（R-5）

- 1 回の掃除で、テナントごとに最大 100 件まで。残りは次の回
- 掃除の失敗はログだけ。購読と API には影響しない
- 「失敗中」の記録の TTL（1 日）は残す。掃除が止まっていても、成功した記録は消える

**Rationale**: アプリに届かなかった配送や、記録が書けなかった回は数えられない（R-4）。数え損ねが 3 回以上あると、イベントは `dlq-*` に移り、記録は `failing` のまま誰にも知られない。掃除で上げれば、SC-003（黙って失うものは 0 件）を人の目に頼らずに満たせる。通知の送り損ね（R-5）も同じ掃除で拾える。

**Alternatives considered**:
- 成功の経路で `failing` の記録を消す: 成功の経路に書き込み（少なくとも読み出し）が増える
- 一覧で `failing` も見せるだけ: 気づくのが人の目だけになる

## R-15: 中身と秘密を外に出さない

**Decision**:
- `last_error` は `describe_exception_for_response`（#318）で作り、200 文字で切る。アプリ自身の例外はそのメッセージ、ほかの例外は型だけになる。Pydantic の `ValidationError` は、失敗した項目の名前だけにする（マスクは秘密と知られたキーしか伏せないため）。一覧と照会の API はこれを返す
- Slack の本文には、失敗の理由として**例外の型だけ**を載せる
- 照会の API が返す `message` は `mask_loggable` を通す（開設精算のログの端末の情報には `api_key` が入っている）。保存は生のまま（流し直しに要る）
- `dead_letter` のモジュールは、中身をログに出さない。本体の既存のログのうち、中身をマスクせずに出しているもの（stock の `handle_transaction_log`）を直す。流し直しでもこの行が走るため

**Rationale**: 例外のメッセージには入力の値が入りうる。記録の中身には個人情報と端末の `api_key` が入る（#211 の方針）。

## Azure Container Apps への配備（別に扱う）

本フィーチャーは Dapr の版にも RabbitMQ の設定にも依存しない。ただし、**受け直しの回数には依存する**。

- **配備の前提**: Azure Container Apps の Dapr の resiliency は、リポジトリの `pubsub-resiliency.yaml` ではなく、環境の側で設定する。3 つのコンポーネントの受け側の再試行が、手元と同じ（exponential、`maxInterval: 3m`、`maxRetries: 18`）であることを、配備のときに確かめる。再試行が 16 回より少ないと、受け手が諦める前に Dapr が使い切り、すべて `dlq-*` に移る（R-14 の掃除が「未対応」に上げるが、30 分遅れる）
- **自動化（2026-11-27 追記）**: 配備は別の担当者が行うため、人の確認に頼る部分を減らす。`scripts/azure-pubsub-resiliency.sh` が `pubsub-resiliency.yaml` から値を読み、3 つのコンポーネントの受け側の再試行を確かめる（`--apply` で設定する）。コンポーネントの `requeueInFailure`・`enableDeadLetter` は確かめるだけで変えない（接続の秘密を持つため）。`SLACK_WEBHOOK_URL` は Key Vault に置き、`scripts/azure-slack-webhook.sh` が 3 つのコンテナアプリにマネージド ID・Key Vault を読む権限・Key Vault 参照のシークレット・環境変数を設定する（URL はリポジトリにもスクリプトにも書かない。環境ごとに別の Webhook）。アプリの側では、`SLACK_WEBHOOK_URL` が無ければ起動時に警告をログに出し、受け直しが尽きて取り残された記録の通知とログに、受け手に要る `maxRetries` を書く。Container Apps の指数の伸び方（倍率）は文書に無く、1.5 より大きいと 19 回の配送に 16 分より長くかかる

ほかに配備のときに気をつけること（本フィーチャーでは変えない）:

- RabbitMQ のデータを残さない構成では、再起動やリビジョンの切り替えのたびに、受け手がまだ処理していないキューの中のメッセージと、`dlq-*` に落ちたものが消える。`dead_letter` の記録（MongoDB）は残る
- データを残すなら、ノード名（`RABBITMQ_NODENAME`）を固定する。RabbitMQ はデータを `rabbit@<ホスト名>` の下に置き、レプリカのホスト名は変わる
- compose は `daprio/daprd:latest` で版を固定していない。Azure は 1.16.4 なので、手元のテストを同じ版で回すには固定が要る（別に扱う）
