# Feature Specification: Motor から PyMongo Async API への移行

**Feature Branch**: `301-pymongo-async-migration`
**Created**: 2026-11-24
**Status**: Draft
**SPEC_TYPE**: maintenance
**Issue**: [#301](https://github.com/kugel-masa/kugelpos-backend/issues/301)

---

## 概要

7つのサービス（account、terminal、master-data、cart、report、journal、stock）と共通ライブラリ（kugel_common）は、MongoDB への非同期アクセスに Motor を使っている。Motor は 2026-05-14 に非推奨となり、重大な不具合の修正も **2027-05-14 で終わる**。それ以降に Motor で見つかった不具合や脆弱性は直らない。

本フィーチャーは、すべてのサービスと共通ライブラリを、MongoDB 公式の後継である PyMongo の非同期 API に移す。**利用者から見える挙動は何も変えない**: API の応答、保存されるデータ、インデックスは移行の前後で同じ。

あわせて、同じコードベースを共有する下流のツリーが同じ移行をできるよう、**移植の手順書**を作る。

対象:
- 7サービスと kugel_common のアプリのコード
- テスト（unit / integration / e2e、サービス横断の e2e）と性能テスト
- 依存の宣言（各サービスの Pipfile とロック、kugel_common のパッケージ定義）
- Motor に触れているドキュメント（CLAUDE.md、docs）

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 移行しても POS の業務がそのまま動く (Priority: P1)

運用者として、ドライバを移行したあとも、端末のサインイン・開設、商品登録、会計、取消・返品、レポート、電子ジャーナル、在庫が、移行前と同じに動いてほしい。ドライバの交換は内部の事情であり、業務にも、つながっている端末にも影響を出してはいけない。

**Why this priority**: 移行の目的は「サポートが切れる部品を外す」ことで、機能は増えない。挙動が変われば、それは移行の失敗である。

**Independent Test**: 移行後の全サービスで、既存の unit / integration / e2e とサービス横断の e2e が、移行前と同じ件数で通る。cart はスナップショットの既定のモード（DUAL）と必須のモード（REQUIRED）の両方で通る。

**Acceptance Scenarios**:

1. **Given** 移行後のスタック、**When** 既存の全テストを走らせる、**Then** 移行前に通っていたテストはすべて通り、テストを削って通したものはない
2. **Given** 移行前に作られたテナントのデータベース、**When** 移行後のサービスで読み書きする、**Then** データは移行なしでそのまま読め、新しく書いたデータも移行前の形と同じである
3. **Given** 移行後のサービス、**When** テナントを作る、**Then** 作られるコレクションとインデックスは移行前と同じである
4. **Given** 複数のワーカー、定期ジョブ（stock の定期処理、cart と terminal の未配信ログの再送）を持つサービス、**When** 移行後に動かす、**Then** どの処理も、データベースへの接続の取り違えで失敗しない

---

### User Story 2 - 下流のツリーが同じ移行を再現できる (Priority: P2)

同じコードベースから派生した下流のツリーの保守者として、このツリーで行った移行を、手順書に沿って自分のツリーにも適用したい。下流にも独自のサービスや共通ライブラリの改変があるので、「何を、どの順で、どう確かめるか」が分かれば、差分をそのまま当てられなくても移行できる。

**Why this priority**: 下流のツリーも同じ期限を抱えている。手順が無いと、各ツリーで同じ調査をやり直すことになる。

**Independent Test**: 手順書だけを読んで、このツリーの移行前の状態から同じ移行を最後までたどれる。置き換えの一覧、書き方が変わる箇所の見つけ方、確かめ方がすべて載っている。

**Acceptance Scenarios**:

1. **Given** 移植の手順書、**When** 下流の保守者が読む、**Then** 置き換える名前の対応表、機械的に置き換えられるものと人が判断するものの区別、各段階の確かめ方が分かる
2. **Given** 下流のツリーに独自のコードがある、**When** 手順書の「書き方が変わる箇所の見つけ方」に従う、**Then** 機械的な置き換えでは直らない箇所（集計、クライアントの終了、セッション、0件指定の取得、イベントループをまたぐ共有）を漏れなく探せる
3. **Given** 手順書、**When** 読む、**Then** 下流のツリーの名前は書かれていない

---

### User Story 3 - 性能が落ちていないことを数字で確かめる (Priority: P3)

運用者として、移行で処理が遅くならなかったことを、同じ条件の性能テストの前後の数字で確かめたい。MongoDB の公式の移行ガイドは、移行後に遅くなる場合があると注意している。

**Why this priority**: 遅くなっていれば本番で困るが、機能の正しさ（P1）より後に確かめられる。

**Independent Test**: 標準の性能テストを、移行前と移行後で同じ条件で走らせ、結果を並べて記録する。

**Acceptance Scenarios**:

1. **Given** 移行前と移行後のスタック、**When** 標準の性能テストを同じ条件で走らせる、**Then** 両方の結果が記録され、比べられる
2. **Given** 移行後に有意な劣化がある、**When** 結果を確かめる、**Then** 原因の説明か、対処が記録されている

---

### Edge Cases

- **件数 0 の取得**: これまで「0 は上限なし」として扱っていた取得が、移行後に「0 件」や誤りにならない
- **集計の結果の受け取り方**: 集計（aggregation）の結果の受け取り方が変わっても、レポートなど集計を使う処理の結果は同じ
- **接続の終了**: サービスの停止、テストの後始末、定期ジョブの終了で、接続を閉じる処理が正しく完了し、閉じ忘れや二重の終了で失敗しない
- **イベントループごとの接続**: 1つの接続を、作ったものとは別のイベントループから使わない。テストごとに新しいループを使う統合テスト、stock のスケジューラー、再送ジョブも含む
- **定期処理が呼ばれるたびに接続を作る箇所**（stock の全テナントの一覧）: 作った接続を閉じ忘れない
- **セッション**: セッションを使う処理（共通の抽象リポジトリ）で、開始・使用・終了が移行後も同じに働く
- **テストのモック**: Motor の型や関数を差し替えていたテストが、移行後も実際の挙動を確かめ続ける（差し替えの対象が消えて、何も確かめないテストにならない）
- **移行中の混在**: 共通ライブラリだけ先に移った状態、サービスだけ先に移った状態で、型や接続の受け渡しが食い違わない（段階的に出す場合）

---

## Requirements *(mandatory)*

### Functional Requirements

**挙動を変えない**

- **FR-001**: 移行後のすべてのサービスは、すべての API で、移行前と同じ応答（状態コード、本文、エラーコード）を返さなければならない
- **FR-002**: 移行後のサービスは、移行前に保存されたデータを、データの移行なしにそのまま読み書きできなければならない
- **FR-003**: テナントの作成と起動時のインデックスの整備で作られるコレクションとインデックスは、移行前と同じでなければならない
- **FR-004**: 「件数 0 = 上限なし」として扱っている取得は、移行後も上限なしとして働かなければならない
- **FR-005**: 集計を使うすべての処理（レポート、ジャーナル、在庫、共通の集計の補助など）は、移行前と同じ結果を返さなければならない
- **FR-006**: セッションを使う処理は、移行後も同じ範囲で同じように働かなければならない

**接続の扱い**

- **FR-007**: データベースへの接続は、それを作ったイベントループからだけ使われなければならない。uvicorn のワーカー、stock の定期処理、cart と terminal の未配信ログの再送、テストごとのイベントループを含む
- **FR-008**: 接続を閉じる処理は、サービスの停止、テストの後始末、一時的に接続を作る処理のすべてで、正しく完了しなければならない
- **FR-009**: 呼ばれるたびに接続を作っていた処理（stock の全テナントの一覧）は、共有の接続を使うか、作った接続を必ず閉じなければならない

**取り除く**

- **FR-010**: アプリのコード、テスト、性能テストのどこにも、Motor の読み込みが残ってはならない
- **FR-011**: すべてのサービスの依存の宣言、ロック、共通ライブラリのパッケージ定義から Motor を取り除き、非同期 API を持つ PyMongo の最低バージョンを明示しなければならない
- **FR-012**: CLAUDE.md と docs の、Motor を前提にした記述を更新しなければならない

**テスト**

- **FR-013**: Motor の型や関数を差し替えていたテストは、移行後の対象を差し替え、移行前と同じことを確かめ続けなければならない
- **FR-014**: 書き方が変わる箇所（集計、接続の終了、セッション、件数 0 の取得、イベントループごとの接続）には、実際の MongoDB に対して挙動を確かめるテストがなければならない

**下流への移植**

- **FR-015**: 移植の手順書を用意しなければならない。少なくとも次を含む: 置き換える名前の対応表、機械的に置き換えられるものと人が判断するものの区別、書き方が変わる箇所の見つけ方（検索の方法）、進める順番、各段階の確かめ方、依存とロックの更新の仕方
- **FR-016**: 手順書は、下流のツリーの名前を書いてはならない

**性能**

- **FR-017**: 標準の性能テストを、移行前と移行後で同じ条件で走らせ、結果を記録しなければならない。有意な劣化があれば、原因の説明か対処を記録しなければならない

### Key Entities

- **データベースへの接続**: プロセスで共有する接続。作ったイベントループに属し、別のループからは使えない
- **共通の抽象リポジトリ**: 各サービスのリポジトリの土台。取得・更新・集計・セッションの扱いがここに集まっている
- **移植の手順書**: 下流のツリーが同じ移行をたどるための文書

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 移行前に通っていた全テスト（7サービスの unit / integration / e2e、サービス横断の e2e、cart の DUAL と REQUIRED の両方）が、移行後に 100% 通る。件数は移行前と同じか多い
- **SC-002**: アプリのコード、テスト、性能テスト、依存の宣言、ロックのどこを検索しても、Motor が 0 件である
- **SC-003**: 移行前に作られたテナントのデータを、移行なしで 100% 読み書きできる
- **SC-004**: 標準の性能テストの主要な指標（応答時間、スループット）の、移行前後の比較が記録されている。劣化が 10% を超える指標には、説明か対処が付いている
- **SC-005**: 下流の保守者が、移植の手順書だけで、移行の対象と書き方が変わる箇所をすべて洗い出せる
- **SC-006**: 2027-05-14 より十分前（目安として 2027-02 まで）に、すべての変更が main に入っている

---

## Assumptions

- PyMongo の非同期 API は、各サービスがすでに間接的に入れている PyMongo（Motor の依存）の版に含まれている。最低バージョンは計画で決める
- データの形式とインデックスはドライバに依存しないので、データの移行は要らない
- 一度に全部を出すか、共通ライブラリ・サービスの順に段階的に出すかは、計画で決める。段階的に出す場合も、各段階で全テストが通る
- 標準の性能テストは、既存の手順（`/perf-test`）を使う
- 下流のツリーへの適用そのものは、この作業の範囲外。手順書を渡すところまでを行う

## Out of Scope

- 機能の追加や、既存の挙動の改善（移行で見つかった不具合は、別の issue にする）
- データの移行やインデックスの変更
- 下流のツリーへの実際の適用
