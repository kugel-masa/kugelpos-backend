# Feature Specification: 支払マスタのサブコード（派生）による支払の分類

**Feature Branch**: `311-payment-variants`
**Created**: 2026-11-22
**Status**: Draft
**SPEC_TYPE**: functional
**Issue**: [#311](https://github.com/kugel-masa/kugelpos-backend/issues/311)

---

## 概要

キャッシュレス（`11`）やその他（`12`）のような支払方法は、実際には多くの個別の支払手段をまとめている（VISA・JCB・PayPay・商品券・ビール券など）。現行の支払マスタは 1 行＝1 支払コードなので、支払は「キャッシュレス」「その他」としか記録できない。どの手段で支払われたかを記録・印字・集計できず、手段ごとに支払コードを増やせば、そのたびに cart の支払プラグインの登録（`plugins.json`）も増やすことになる。

本フィーチャーは、支払方法の下に**サブコード（派生）**を持てるようにする。サブコードは 1 つの支払方法の中での支払の分類である。

- **挙動は支払方法が持つ**: 支払プラグイン・上限額・返金可否・超過預かり可否・釣銭可否（#309 で cart が従うようになった設定）は支払方法のまま。サブコードは支払手段の識別（コードと名前）だけを担う
- **サブコードは API で登録・変更する**: 運用者は支払方法ごとにサブコードを追加し、名前を変え、使わなくなったら停止する。削除はしない
- **コードは自由形式**: 支払方法の中で一意であればよく、桁数や採番規則を強制しない
- **取引の支払行は支払方法とサブコードの両方を記録する**: 支払行の名前はサブコードの名前になり、支払方法の名前も別に残す
- **集計は支払方法単位のまま、サブコード別の内訳を加える**

## Clarifications

### Session 2026-11-22

- Q: サブコードの登録方法は？ → A: API で登録・変更する（種データだけにはしない）
- Q: サブコードのコード体系は？ → A: 自由形式。支払方法の中で一意であればよい
- Q: 支払行の名前は？ → A: サブコードの名前。支払方法の名前は別の項目に残す
- Q: 取消・返品で受け付ける支払種別は？ → A: 取消は売上の裏返しなので、売上時の支払種別（サブコードを含む）しか受け付けない。返品は現金でしか返金できない場合があるので、売上時の支払種別か現金を受け付ける
- Q: 取消・返品でサブコードを省略できるか？ → A: できない。売上時の行にサブコードがあれば、要求でもサブコードまで指定する（省略は「サブコードなし」の意味）
- Q: 返品で売上時の金額を超えて返金を指定したら？ → A: エラー
- Q: 現金の判定は？ → A: 支払コード `01`（report の現金の判定と同じ）
- 計画時の確認（plan）: 支払レポートの件数は取引の数なので、内訳の件数の合計は行と一致しないことがある（FR-021）

## 影響するサービス

| サービス名 | 変更の種類 | 変更の概要 |
|---|---|---|
| master-data | 変更 | 支払マスタにサブコードの一覧を持たせる。サブコードの登録・一覧・取得・更新の API を新設。支払マスタの取得の応答にサブコードを含める。既存の支払マスタの更新はサブコードを保つ |
| cart | 変更 | 支払の登録で任意のサブコードを受け、支払方法の有効なサブコードに照らして決める（自動選択・指定必須・拒否）。支払行にサブコード・支払方法の名前を記録する。取消は売上時の「支払方法＋サブコード」と金額で照合し、返品は売上時の支払種別（売上時の金額まで）か現金に限る |
| kugel_common（共通ライブラリ） | 変更 | 取引の支払行にサブコードと支払方法の名前の項目を追加（追加のみ） |
| report | 変更 | 売上レポート・支払レポートの支払を支払方法単位で集計し、名前を支払方法の名前から取る。サブコード別の内訳を加える |
| journal | 確認のみ | 取引ログをそのまま保存する。支払行の名前がサブコードの名前になるだけで、保存・検索の仕組みは変わらない |

**影響なしのサービス**: account・terminal・stock。

## 変更するインターフェース

| インターフェース | 変更の種類 | 後方互換性 |
|---|---|---|
| master-data の支払マスタの取得・一覧 | 応答にサブコードの一覧が加わる | 互換（追加のみ） |
| master-data のサブコードの登録・一覧・取得・更新 | 新設（支払マスタのリソースの下） | 新規 |
| master-data の支払マスタの作成・更新 | 要求はサブコードを受けない。更新は既存のサブコードを保つ | 互換 |
| master-data の支払マスタの削除 | その支払方法のサブコードも一緒に消える | 互換 |
| cart の支払の登録 | 任意のサブコードを受ける | 互換（サブコードを持たない支払方法は現行どおり。サブコードを 2 件以上持つ支払方法はサブコードの指定が要る） |
| cart の取消 | 要求の支払を「支払方法＋サブコード」で売上時の行と照合する | 互換（サブコードの無い取引は現行どおり。サブコードのある取引はサブコードの指定が要る） |
| cart の返品 | 返金の手段を売上時の支払種別（サブコードを含む）と現金 `01` に限る。売上時の手段での返金額は売上時の金額まで | **破壊的変更**: 現行は任意の支払方法で返金できる。売上時と違う支払方法（現金以外）での返品は拒否されるようになる |
| 取引ログ（pub/sub `tranlog_report` ほか）・カートの支払行 | サブコード・支払方法の名前の項目を追加。支払行の名前はサブコードの名前 | 互換（追加のみ。既存の項目の意味は、名前を除き変えない） |
| report の売上レポート・支払レポートの応答 | 支払ごとにサブコード別の内訳が加わる | 互換（追加のみ） |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 支払方法の下にサブコードを登録・管理する (Priority: P1)

運用者（テナント管理者）は、キャッシュレスの下に「VISA」「JCB」「PayPay」、その他の下に「商品券」「ビール券」のようにサブコードを登録する。名前を直し、使わなくなったサブコードは停止し、必要になれば再開する。コードの追加や配備は要らない。

**Why this priority**: サブコードが登録できなければ、支払の分類そのものが始まらない。本フィーチャーの土台である。

**Independent Test**: 支払方法を 1 つ用意し、サブコードを登録・一覧・取得・名前の変更・停止・再開して、それぞれが支払マスタの取得に反映されることを確かめる。

**Acceptance Scenarios**:

1. **Given** 支払方法 `11` にサブコードが無い, **When** サブコード `VISA`（名前「VISA」）を登録する, **Then** 登録され、`11` の取得・サブコードの一覧に有効なサブコードとして現れる
2. **Given** `11` にサブコード `VISA` がある, **When** 同じコード `VISA` をもう一度 `11` に登録する, **Then** 重複として拒否され、既存のサブコードは変わらない
3. **Given** `11` にサブコード `VISA` がある, **When** 支払方法 `12` に同じコード `VISA` を登録する, **Then** 登録される（一意なのは支払方法の中だけ）
4. **Given** `11` にサブコード `VISA` がある, **When** 名前を「VISA カード」に変える, **Then** 以後の取得で新しい名前が返る
5. **Given** `11` にサブコード `VISA` がある, **When** 停止する, **Then** サブコードは停止中として残り、取得で見える
6. **Given** 停止中のサブコード `VISA`, **When** 再開する, **Then** 再び有効になる
7. **Given** `11` にサブコードが 2 件ある, **When** 支払方法 `11` の説明や上限額を更新する, **Then** 2 件のサブコードはそのまま残る
8. **Given** 存在しない支払方法 `99`, **When** その下にサブコードを登録する, **Then** 支払方法が無いとして拒否される

### User Story 2 - 支払をサブコードで記録する (Priority: P1)

レジ係は、キャッシュレスで支払を受けるとき、支払方法 `11` とサブコード `PAYPAY` を指定して記帳する。取引の支払行には支払方法 `11` とサブコード `PAYPAY` が記録され、レシートには「PayPay」と印字される。支払の挙動（釣銭・超過預かり・上限額・返金可否）は支払方法 `11` の設定に従う。

**Why this priority**: 分類を取引に残すことが本フィーチャーの目的である。登録（US1）と合わせて最小の価値になる。

**Independent Test**: サブコードを 2 件持つ支払方法で、サブコードを指定して支払を記帳し、取引ログの支払行の支払コード・サブコード・名前・支払方法の名前を確かめる。サブコードの指定が無い・誤っている場合に拒否されることも確かめる。

**Acceptance Scenarios**:

1. **Given** `11` に有効なサブコード `VISA`・`PAYPAY` がある, **When** 支払方法 `11`・サブコード `PAYPAY` で支払を記帳する, **Then** 支払行は支払コード `11`・サブコード `PAYPAY`・名前「PayPay」・支払方法の名前「キャッシュレス」で記録される
2. **Given** 同じ支払方法, **When** サブコードを指定せずに `11` で支払を記帳する, **Then** サブコードの指定が要るとして拒否され、カートは変わらない
3. **Given** `11` の有効なサブコードが `VISA` の 1 件だけ（他は停止中またはなし）, **When** サブコードを指定せずに `11` で支払を記帳する, **Then** `VISA` で記録される
4. **Given** `11` にサブコードが無い, **When** サブコードを指定せずに `11` で支払を記帳する, **Then** 現行どおり記録され、支払行のサブコードは空、名前は支払方法の名前になる
5. **Given** `11` にサブコード `VISA` がある, **When** サブコード `JCB`（`11` に存在しない）を指定する, **Then** 存在しないサブコードとして拒否される
6. **Given** `12` にだけサブコード `GIFT` がある, **When** 支払方法 `11`・サブコード `GIFT` を指定する, **Then** `11` に存在しないサブコードとして拒否される（別の支払方法のサブコードへ読み替えない）
7. **Given** `11` のサブコード `VISA` が停止中, **When** `VISA` を指定する, **Then** 停止中として拒否される
8. **Given** `11` が超過預かり不可・サブコード `VISA` がある, **When** 残額を超える金額を `VISA` で記帳する, **Then** 支払方法 `11` の設定どおり拒否される（サブコードは挙動を変えない）

### User Story 3 - 取消・返品を売上時の支払種別で行う (Priority: P2)

レジ係は、サブコードで支払った取引を取消・返品する。取消は売上の裏返しなので、売上時の支払種別（支払方法とサブコード）と金額をそのまま指定する。返品は、売上時の支払種別か現金で返金する。返金の支払行には指定したサブコードが記録され、販売後にサブコードが停止・改名されていても処理は妨げられない。

**Why this priority**: 取消・返品は販売の後で起きる。分類が返金側で失われたり、売上と違う手段で返金されたりすると、サブコード別の集計と実際のお金の流れが合わなくなる。

**Independent Test**: サブコードで支払った取引を確定し、売上時の支払種別で取消・返品できること、売上時と違う支払種別・金額では拒否されること、現金での返品ができることを確かめる。

**Acceptance Scenarios**:

1. **Given** `11` を `VISA` 1,000 円と `PAYPAY` 2,000 円で支払った取引, **When** `11/VISA` 1,000 円・`11/PAYPAY` 2,000 円で取消する, **Then** 取消の取引の支払行は `11/VISA` 1,000 円・`11/PAYPAY` 2,000 円で、名前は売上時の行の名前
2. **Given** 同じ取引, **When** サブコードを指定せずに `11` 3,000 円で取消する, **Then** 売上時にサブコードなしの `11` の行が無いので拒否される
3. **Given** 同じ取引, **When** `11/VISA` 3,000 円で取消する, **Then** 売上時の `11/VISA` の金額と一致しないので拒否される
4. **Given** 同じ取引, **When** `11/JCB`・`12`・現金 `01` のいずれかを含めて取消する, **Then** 売上時の支払種別ではないので拒否される
5. **Given** 同じ取引, **When** `11/PAYPAY` 2,000 円と現金 `01` 1,000 円で返品する, **Then** 返品できる。返金の支払行は `11/PAYPAY` と `01`
6. **Given** 同じ取引, **When** `11/VISA` 3,000 円で返品する, **Then** 売上時の `11/VISA` の金額（1,000 円）を超えるので拒否される
7. **Given** 同じ取引, **When** `11/JCB` または `12` で返品する, **Then** 売上時の支払種別でも現金でもないので拒否される
8. **Given** 同じ取引, **When** 現金 `01` 3,000 円で返品する, **Then** 返品できる（現金は売上時に使っていなくても受け付ける）
9. **Given** 同じ取引の後に `PAYPAY` を停止・改名した, **When** `11/PAYPAY` で取消・返品する, **Then** 停止を理由に拒否されず、返金の支払行の名前は売上時の名前
10. **Given** 売上時の支払方法が返金不可（`can_refund=false`）, **When** その支払種別で返品する, **Then** 現行どおり拒否される（現金での返品はできる）

### User Story 4 - サブコード別に売上を集計する (Priority: P2)

店長・本部は、売上レポートと支払レポートで、支払方法ごとの合計に加えてサブコード別の内訳（金額・件数）を見る。支払方法の行はこれまでどおり 1 行で、サブコードの名前によって行が割れない。

**Why this priority**: 記録した分類を業務で使うのは集計である。ただし記録（US2）があれば、集計は後から作り直せる。

**Independent Test**: 同じ支払方法の異なるサブコードで支払った取引を複数作り、売上レポート・支払レポートで支払方法の行が 1 行で、内訳の合計が行の合計と一致することを確かめる。

**Acceptance Scenarios**:

1. **Given** `11` を `VISA` で 1,000 円・`PAYPAY` で 2,000 円・`PAYPAY` で 500 円支払った取引, **When** 売上レポートを作る, **Then** 支払方法 `11` は 1 行で合計 3,500 円・3 件、内訳は `VISA` 1,000 円 1 件・`PAYPAY` 2,500 円 2 件
2. **Given** 同じ取引（3 件とも別の取引）, **When** 支払レポートを作る, **Then** 同じく `11` は 1 行で 3,500 円・3 件、内訳は `VISA` 1,000 円 1 件・`PAYPAY` 2,500 円 2 件
3. **Given** 本フィーチャーの前に記録された支払行（サブコードも支払方法の名前も無い）, **When** 集計する, **Then** その行は支払方法の行に数えられ、内訳では「サブコードなし」の 1 項目になる
4. **Given** 支払行の名前がサブコードの名前になっている, **When** 集計する, **Then** 支払方法の行の名前は販売時点の支払方法の名前で、サブコードの名前ではない
5. **Given** 現金 `01` の支払, **When** 集計する, **Then** 現金の判定（釣銭・現金在高）は現行どおり支払コードで行われる

---

### Edge Cases

- **販売中にサブコードが停止された**: すでにカートに入った支払行はそのまま残り、確定できる。停止は新しい支払の記帳にだけ効く
- **販売中にサブコードが追加された**: 有効なサブコードが 1 件から 2 件に増えると、それ以後のサブコードの指定の無い記帳は拒否される。cart は支払マスタをキャッシュするので、変更はキャッシュの有効期限が過ぎてから効く。すぐに効かせるときは cart のマスタのキャッシュの無効化（`DELETE /api/v1/cache/master-data?namespace=payment_master`、特権の利用者・サービスアカウントだけ）を使う
- **有効なサブコードがすべて停止中**: サブコードを持たない支払方法と同じ扱い（指定なしで記帳でき、支払行のサブコードは空）。指定した場合は停止中として拒否
- **支払方法が停止中**: cart は現在、支払方法の有効フラグ（`is_active`）を見ていない（停止中の支払方法でも記帳できる）。本フィーチャーではこれを変えない。サブコードの有効フラグだけを判定に使う
- **支払方法の削除**: サブコードも一緒に消える。過去の取引の支払行は販売時点のコードと名前を自分で持っているので、集計は影響を受けない。取消・返品は現行どおり支払マスタを読むので、支払方法ごと削除されていれば拒否される
- **本フィーチャーの前の取引の取消・返品**: 売上時の行にサブコードが無いので、サブコードを指定せずに行う（現行どおり）
- **返品で同じ支払種別を複数の行に分けて指定**: 売上時の金額の上限は「支払方法＋サブコード」ごとの合計で確かめる
- **サブコードのコードの大文字・小文字**: 区別する（`visa` と `VISA` は別のコード）。正規化はしない
- **サブコードの名前が空**: 登録・更新で拒否する（支払行の名前・レシートの印字が空になるため）
- **カートのスナップショット**: 支払行は他の項目と同じくスナップショットに入る。スナップショットから再構成したカートの支払行はサブコードと名前を保つ

## Requirements *(mandatory)*

### Functional Requirements

#### サブコードの管理（master-data）

- **FR-001**: 支払マスタの各支払方法は、0 件以上のサブコードを持てなければならない。サブコードはコード・名前・有効フラグを持つ
- **FR-002**: サブコードのコードは自由形式の文字列で、支払方法の中で一意でなければならない。別の支払方法には同じコードを登録できる。長さと使える文字は Assumptions に定める範囲とし、範囲外は入力の誤りとして拒否する
- **FR-003**: 運用者は、支払方法を指定してサブコードを登録できなければならない。同じ支払方法に同じコードがあれば重複として拒否し、支払方法が存在しなければ拒否する
- **FR-004**: 運用者は、支払方法のサブコードの一覧と、1 件のサブコードを取得できなければならない。停止中のサブコードも含めて返す
- **FR-005**: 運用者は、サブコードの名前と有効フラグを変更できなければならない。コードは変更できない（変えたいときは新しいサブコードを登録し、古いものを停止する）
- **FR-006**: サブコードは削除できてはならない。使わなくなったサブコードは有効フラグを外して停止する
- **FR-007**: 支払マスタの取得・一覧の応答は、各支払方法のサブコードの一覧を含まなければならない
- **FR-008**: 支払マスタの更新は、既存のサブコードを変えてはならない。支払マスタの作成・更新の要求はサブコードを受けない
- **FR-009**: 支払マスタを削除したとき、その支払方法のサブコードも一緒に消えなければならない
- **FR-010**: サブコードの登録・変更の権限は支払マスタの作成・更新と同じ（テナントの管理者。端末からは不可）、取得の権限は支払マスタの取得と同じでなければならない

#### 支払の記帳（cart）

- **FR-011**: 支払の登録は、支払方法のコード（必須）に加え、サブコードを任意で受けなければならない
- **FR-012**: サブコードが指定されたとき、cart はそれが**その支払方法の有効な**サブコードであることを確かめなければならない。存在しない（別の支払方法にだけ存在する場合を含む）・停止中なら、理由を区別できるエラーで拒否する。黙って無視したり、別のサブコードに置き換えたりしてはならない
- **FR-013**: サブコードが指定されないとき、cart はその支払方法の有効なサブコードの件数で決めなければならない:
  - 0 件: サブコードなしで記帳する（現行どおり）
  - 1 件: そのサブコードで記帳する
  - 2 件以上: サブコードの指定が要るとして拒否する
- **FR-014**: 支払の挙動（支払プラグインの選択・上限額・返金可否・超過預かり可否・釣銭可否）は、サブコードにかかわらず支払方法の設定で決めなければならない
- **FR-015**: 支払行は、支払方法のコード（現行どおり）・サブコード・名前・販売時点の支払方法の名前を記録しなければならない。サブコードで記帳した支払行の名前はサブコードの名前、サブコードなしの支払行の名前は支払方法の名前とする
- **FR-016**: 取消の要求の各支払は、売上時の支払行にある「支払方法＋サブコード」でなければならない。サブコードの省略は「サブコードなし」を意味し、売上時の行にサブコードがあれば一致しない。一致しない支払種別を含む要求は拒否する
- **FR-016a**: 取消の金額は、「支払方法＋サブコード」ごとに売上時の合計と一致しなければならない（現行の支払方法ごとの照合を細かくする）。取消の支払行の名前・支払方法の名前は売上時の行のものを使う
- **FR-016b**: 返品の要求の各支払は、次のどちらかでなければならない。どちらでもなければ拒否する:
  - 売上時の支払行にある「支払方法＋サブコード」（省略の意味は FR-016 と同じ）。名前・支払方法の名前は売上時の行のものを使う
  - 現金（支払コード `01`）。売上時に同じ「支払方法＋サブコード」の行が無ければ、サブコードは販売と同じ規則（FR-012・FR-013）で決め、名前は現在のマスタのものを使う
- **FR-016c**: 返品で売上時の支払種別（現金を除く）に返金する額は、「支払方法＋サブコード」ごとに売上時の合計を超えてはならない。超える指定は拒否する。現金での返金額は現行どおり、返金の合計が取引の合計と一致することだけを確かめる
- **FR-016d**: 売上時の行にあるサブコードは、販売後に停止・改名されていても取消・返品で受け付けなければならない。支払方法ごと削除された場合は、現行どおり支払方法が無いとして扱う
- **FR-016e**: 返金の可否・上限（`can_refund`・`limit_amount`、#309）の確認は現行どおり支払方法で行う
- **FR-017**: カートに入った支払行は、記帳後のサブコードの停止・改名の影響を受けてはならない（確定まで記帳時のコードと名前を保つ）
- **FR-018**: 新しい拒否のエラーコードは cart の業務ルールの範囲（401–404）から割り当てなければならない。master-data のサブコードの重複・不在は、支払マスタの重複・不在と同じ既存のエラーで答える

#### 取引ログ・集計（commons・report）

- **FR-019**: 取引ログの支払行に、サブコードと販売時点の支払方法の名前の項目を追加しなければならない。既存の項目は残し、追加のみとする
- **FR-020**: 売上レポートと支払レポートは、支払を支払方法のコードで集計しなければならない。売上レポートの行の名前は、期間内で最も新しい販売時点の支払方法の名前を使い、それが無い支払行（本フィーチャーの前の記録）は支払行の名前を使う。支払レポートの行の名前は現行どおり現在の支払マスタの名前を使う
- **FR-021**: 売上レポートと支払レポートの各支払方法の行は、サブコード別の内訳（サブコード・その名前・金額・件数）を持たなければならない。サブコードの無い支払行は「サブコードなし」の 1 項目にまとめる。内訳の金額の合計は行の金額と一致しなければならない。件数は各レポートの行の数え方に従う: 売上レポートは支払行の数なので内訳の合計が行と一致し、支払レポートは取引の数なので、1 つの取引で同じ支払方法の 2 つのサブコードを使うと内訳の件数の合計が行の件数を上回る
- **FR-021a**: 内訳のサブコードの名前は、売上レポートは期間内で最も新しい販売時点の支払行の名前、支払レポートは現在の支払マスタのサブコードの名前（マスタに無ければ同じく最も新しい支払行の名前）を使う。期間中に改名があっても、同じ条件で作ったレポートの名前は変わらない
- **FR-022**: 現金の判定など、支払コードで行っている既存の判定は変えてはならない

#### 互換性

- **FR-023**: サブコードを持たない支払マスタでは、支払の記帳・取引ログ・集計の結果が本フィーチャーの前と同じでなければならない（追加された項目が空であることを除く）
- **FR-024**: cart の e2e テストは、スナップショットを伴う形で書くか、伴わない場合は `dual_only` を付けなければならない（#156 の運用）

### Key Entities

- **支払方法（支払マスタ）**: 支払コード・名前・挙動の設定（上限額・返金可否・超過預かり可否・釣銭可否・有効フラグ）を持つ。0 件以上のサブコードを内包する
- **サブコード（派生）**: 支払方法の中での支払の分類。コード（支払方法の中で一意・自由形式）・名前・有効フラグを持つ。挙動の設定は持たない。削除されず、停止で表す
- **取引の支払行**: 支払コード・金額・名前に加え、サブコードと販売時点の支払方法の名前を持つ。販売後のマスタの変更から独立している
- **レポートの支払の行**: 支払方法ごとの合計（金額・件数）と、サブコード別の内訳を持つ

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 運用者は、新しい支払手段を既存の支払方法の下に追加して、その日のうちに記帳と集計に使える。コードの変更・配備・店舗の停止は 0 件
- **SC-002**: サブコードで記帳した取引の 100% で、取引ログの支払行からサブコードと支払方法の両方が分かる
- **SC-003**: 売上レポート・支払レポートで、すべての支払方法についてサブコード別の内訳の金額の合計が支払方法の行の金額と一致する（不一致 0 件）
- **SC-004**: 販売後にサブコードを停止・改名しても、その取引の取消・返品が拒否される件数は 0 件
- **SC-004a**: 売上時の支払種別・現金以外での返金、売上時の金額を超える返金は 100% 拒否される
- **SC-005**: サブコードを持たない支払マスタの既存の運用で、記帳・集計の結果の差分は 0 件（既存の自動テストがすべて通る）
- **SC-006**: 誤ったサブコード（存在しない・別の支払方法の・停止中・指定漏れ）での記帳は 100% 拒否され、誤った分類のまま記録される取引は 0 件

## Assumptions

- **コードの形式**: 1〜20 文字の英数字・ハイフン・アンダースコア。大文字・小文字を区別する。支払方法のコードとは独立で、先頭の文字に意味を持たせない
- **名前の形式**: 空でない文字列（前後の空白だけは不可）。長さの上限は設けない（支払マスタの名前 `description` にも上限が無い）
- **件数の上限**: 1 つの支払方法のサブコードは運用上数十件程度を想定し、本フィーチャーでは上限を設けない
- **並び順**: サブコードの一覧と集計の内訳はコードの昇順。内訳の「サブコードなし」は末尾
- **キャッシュ**: cart の支払マスタのキャッシュの仕組み（有効期限・世代による無効化）は変えない。サブコードの変更は支払マスタの変更として扱い、有効期限（既定 600 秒）の経過後か、cart のマスタのキャッシュの無効化の端点（`namespace=payment_master`）を呼んだ後に効く
- **レシート**: 取引のレシートは支払行の名前（サブコードの名前）をそのまま印字する。レシート専用の名前は持たない。売上レポート・支払レポートの印字（レシートデータ）にサブコード別の内訳を出すことは本フィーチャーに含めない（応答のデータにだけ加える）
- **外部決済のブランド照合は範囲外**: 決済端末の応答のブランドからサブコードを自動で決める仕組みは本フィーチャーに含めない。サブコードは要求で指定するか、FR-013 の規則で決まる
- **配備の順序**: サブコードの登録は、commons・cart・report を本フィーチャーの版へ配備し終えた後に行う。古い cart はサブコードを知らないので、先に登録するとサブコードの指定が無視されて記帳される（運用手順・リリースノートに書く）
- **既存データの移行はしない**: 既存の支払マスタはサブコード 0 件として扱い、既存の取引ログはサブコード無しとして集計する
- **支払コードの体系は変えない**: 既存の支払コード（`01`・`11`・`12`）と cart の支払プラグインの登録は変えない
