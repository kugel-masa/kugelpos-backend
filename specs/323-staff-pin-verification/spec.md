# Feature Specification: 端末サインインでの従業員 PIN の照合

**Feature Branch**: `323-staff-pin-verification`
**Created**: 2026-11-23
**Status**: Draft
**SPEC_TYPE**: functional
**Issue**: [#323](https://github.com/kugel-masa/kugelpos-backend/issues/323)

---

## 概要

端末のサインインは従業員コードだけで通る。従業員マスタには PIN を登録できるが、どこでも照合していないので、従業員コードを知っていれば、PIN を登録した従業員としてもサインインできる。

#136 で PIN は書き込み専用になった（登録・更新では受け取り、どの応答にも返さず〔#216〕、端末にも写さない〔#296〕）。平文の保存は「照合が無い」ことを理由に据え置き、照合を入れるときに見直すとした。本フィーチャーはその照合を入れる。

- **PIN は、登録されている従業員にだけ必須**: PIN を登録した従業員は PIN が一致しないとサインインできない。PIN を登録していない従業員は、これまでどおり従業員コードだけでサインインできる
- **照合はマスタの中の 1 か所だけで行う**: PIN はマスタの外（応答・ログ・他のサービス）へ出ない
- **PIN を登録した従業員について、照合を飛ばす経路は作らない**
- **用語**: 「PIN あり」は従業員マスタの PIN が空でないこと（空白だけも含む）、「PIN なし」は `null` または空文字であること。「PIN を登録した」「PIN が入っている」は「PIN あり」と同じ意味

## Clarifications

### Session 2026-11-23

- Q: 既存のクライアント（従業員コードだけを送る）をどう扱うか？ → A: 従業員マスタに PIN が設定されている場合だけ PIN を必須にする。設定されていなければ従業員コードだけで通す
- Q: PIN を登録していない従業員に PIN が送られてきたら？ → A: 無視して通す（クライアントが従業員ごとに送り方を変えなくてよい）
- Q: PIN のハッシュ化、試行回数の制限・ロックアウトを含めるか？ → A: 含めない。照合だけ。ただし照合の 1 か所へ後から足せる形にする
- Q: これまで従業員の登録・更新で PIN が必須だったため、PIN を使っていないテナントの従業員にもダミーの PIN が入っている。どう扱うか？ → A: 判定は従業員マスタの PIN が空かどうかのまま。登録・更新で PIN を省略できるようにし、PIN なしでサインインさせたい従業員は PIN を空にするよう、リリースノートで告知する
- レビュー時の確認: 照合の成功の応答は、端末が使う従業員コードと名前だけ。サインインしたあとで PIN が設定・変更されても、すでにサインインしている端末には遡らない

## 影響するサービス

| サービス | 変更 |
|---|---|
| master-data | 従業員の照合をサービス間専用で提供する。照合はここだけで行う。従業員の登録・更新で PIN を省略できるようにする |
| commons | 端末などがマスタに照合を頼むための呼び出し口と、失敗の理由の受け渡し |
| terminal | サインインで照合を頼み、結果に従ってサインインさせるか断る |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - PIN を登録した従業員は PIN が一致しないとサインインできない (Priority: P1)

店舗が従業員に PIN を登録している。その従業員として端末にサインインするには、正しい PIN を入力しなければならない。PIN を入力しない・誤った PIN を入力した場合は断られる。

**Why this priority**: 本フィーチャーの目的そのもの。PIN を登録しても従業員コードだけでなりすましができる現状を止める。

**Independent Test**: PIN を登録した従業員で、正しい PIN・誤った PIN・PIN なしの 3 通りでサインインを試し、正しい PIN だけが通ることを確かめる。

**Acceptance Scenarios**:

1. **Given** PIN `1234` を登録した従業員 S1、**When** S1 として PIN `1234` でサインインする、**Then** サインインでき、端末に S1 が記録される
2. **Given** 同じ S1、**When** PIN `9999` でサインインする、**Then** 断られ、端末はサインインしていない状態のまま
3. **Given** 同じ S1、**When** PIN を付けずにサインインする、**Then** 断られ、端末はサインインしていない状態のまま
4. **Given** 同じ S1、**When** 空の PIN でサインインする、**Then** PIN なしと同じく断られる

---

### User Story 2 - PIN を登録していない従業員はこれまでどおりサインインできる (Priority: P1)

PIN を使っていない店舗や従業員は、これまでと同じく従業員コードだけでサインインできる。既存のクライアントは変更なしで動く。

**Why this priority**: 既存の運用・クライアントを壊さないための条件。US1 と同時に満たす必要がある。

**Independent Test**: PIN を登録していない従業員で、PIN なし・任意の PIN 付きの両方でサインインし、どちらも通ることを確かめる。

**Acceptance Scenarios**:

1. **Given** PIN を登録していない従業員 S2、**When** S2 として PIN を付けずにサインインする、**Then** サインインできる
2. **Given** 同じ S2、**When** 任意の PIN を付けてサインインする、**Then** PIN は無視され、サインインできる

---

### User Story 3 - 失敗の理由は呼び出し元に区別させず、運用者には分かるようにする (Priority: P2)

サインインに失敗したとき、端末（クライアント）には「従業員の認証に失敗した」ことだけを返す。従業員が存在しないのか、PIN が要るのか、PIN が違うのかは区別させない。運用者はログで理由を確かめられる。

**Why this priority**: 区別させると、どの従業員コードが存在するか・PIN を登録しているかを探られる。US1 の守りを弱めないための条件。

**Independent Test**: 存在しない従業員・PIN なし・PIN 不一致の 3 通りで失敗させ、応答のエラーコードとメッセージが同じで、ログには理由が残ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 存在しない従業員コード、PIN を登録した従業員への PIN なし、PIN 不一致、**When** それぞれでサインインする、**Then** 3 つとも同じエラーコード・同じメッセージで断られる
2. **Given** 同じ 3 通り、**When** 失敗する、**Then** ログにはテナント・端末・従業員コードと失敗の理由が残り、PIN の値は残らない

---

### User Story 4 - マスタに届かないときは認証の失敗にしない (Priority: P2)

マスタのサービスが落ちている・応答しないとき、サインインは「PIN が違う」ではなく、依存先の障害として失敗する。

**Why this priority**: 障害を認証の失敗として返すと、従業員は PIN を打ち直し続け、運用者は障害に気付けない。

**Independent Test**: マスタに届かない状態でサインインし、認証失敗のコードではなく障害として返ることを確かめる。

**Acceptance Scenarios**:

1. **Given** マスタのサービスに届かない、**When** サインインする、**Then** 認証失敗とは別の、障害を示すエラーで失敗し、端末はサインインしていない状態のまま

---

### Edge Cases

- 削除された従業員（従業員マスタの削除は物理削除）は、存在しない従業員と同じく失敗する
- PIN を登録した従業員に空文字の PIN を送ったら、PIN なしと同じく失敗する（空の PIN が一致したことにはならない）
- 従業員マスタの PIN が空文字のときは「PIN を登録していない」と同じに扱う
- 端末がすでにサインインしているときは、照合の前にこれまでどおり断る（照合は呼ばない）
- 照合を頼む側のテナントと、照合対象のテナントが違うときは断る
- PIN はリクエストの本文だけで受け取り、URL（パス・クエリ）には載せない
- PIN の前後の空白は取り除かない。空白だけの PIN も PIN として扱う（登録された値と送られた値をそのまま比べる）
- 文字列でない PIN（数値など）は要求の形の誤り（422）として断る。従業員に依らない応答なので、列挙の手がかりにならない
- `/` や `..` を含む従業員コードは、照合の呼び出し先を変えずに「存在しない従業員」として失敗する
- サインインしたあとで、その従業員に PIN が設定・変更されたり、従業員が削除されたりしても、すでにサインインしている端末には遡らない（次のサインインから照合が効く）

## Requirements *(mandatory)*

### Functional Requirements

**照合（master-data）**

- **FR-001**: マスタは、従業員コードと任意の PIN を受け取り、その従業員を認証してよいかを判定できなければならない
- **FR-002**: 判定は次のとおりとし、成功は下の 2 つだけでなければならない
  - 従業員が存在しない → 失敗（従業員なし）
  - PIN を登録している従業員で、PIN が送られていない、または空 → 失敗（PIN が要る）
  - PIN を登録している従業員で、PIN が一致しない → 失敗（PIN 不一致）
  - PIN を登録している従業員で、PIN が一致する → 成功
  - PIN を登録していない従業員 → 成功（送られた PIN は無視する）
- **FR-003**: PIN の比較は、比較にかかる時間から一致の度合いが分からない方法で行わなければならない
- **FR-004**: 成功したら、PIN を含まない従業員の情報を返さなければならない。応答の形そのものに PIN の項目を持たせてはならない
- **FR-005**: 失敗の 3 種類は、それぞれ別のエラーコード（405701 従業員なし、405702 PIN が要る、405703 PIN 不一致）と、日本語・英語のメッセージで返さなければならない
- **FR-006**: 照合はサービス間からだけ使えなければならない。端末やクライアントの資格情報（端末のトークン、API キー）では使えず、照合を頼むサービスのテナントと照合対象のテナントが一致しなければ断らなければならない
- **FR-007**: PIN はリクエストの本文だけで受け取り、パスやクエリには載せてはならない
- **FR-008**: マスタは、照合について、テナント・従業員コード・呼び出し元のサービスをログに残してよいが、PIN の値をログに残してはならない
- **FR-009**: PIN の比較はマスタの中の 1 か所だけで行い、後からハッシュ化・試行回数の制限・ロックアウトをその 1 か所へ足せる形でなければならない

**照合の呼び出し口（commons）**

- **FR-010**: 他のサービスがマスタに照合を頼むための共通の呼び出し口を用意しなければならない。呼び出しにはサービス間の資格情報を使わなければならない
- **FR-011**: 呼び出し口は、業務上の失敗 3 種類（405701 / 405702 / 405703）を、理由を持つ 1 つの失敗として呼び出し元へ返さなければならない
- **FR-012**: それ以外の失敗（マスタに届かない、マスタ側の障害など）は、認証の失敗にまとめず、依存先の障害として呼び出し元へ返さなければならない

**サインイン（terminal）**

- **FR-013**: サインインの要求は、従業員コードに加えて、省略できる PIN を受け取らなければならない。PIN を省略した要求は、これまでと同じ形で受け付けなければならない
- **FR-014**: サインインは、従業員の情報をマスタの照合で得なければならない。照合を通らない取得経路（PIN を確かめずに従業員を取る）でサインインさせてはならない
- **FR-015**: 照合に失敗したら、理由にかかわらず同じエラーコード・同じメッセージで断らなければならない。応答の本文（エラーコード・利用者向けのメッセージ・システムのメッセージ）は、同じ従業員コードに対して 3 種類とも同じでなければならない
- **FR-016**: 照合に失敗したら、テナント・端末・従業員コード・失敗の理由をログに残さなければならない（応答には出さない）。PIN の値は残してはならない
- **FR-017**: マスタに届かないなど照合を判定できなかったときは、認証の失敗とは別の、障害を示すエラーで断らなければならない
- **FR-018**: 断ったときは端末の状態を変えてはならない（サインインしていない状態のまま）
- **FR-019**: 端末に記録する従業員の情報は、これまでどおり PIN を含んではならない
- **FR-019a**: サインインの要求を受けたことを記録するログに、PIN の値を出してはならない
- **FR-019b**: 照合を頼むとき、クライアントから受け取った従業員コードは、内部の呼び出し先の URL を変えないように符号化して埋め込まなければならない

**変わらないもの**

- **FR-020**: 従業員マスタのどの応答にも PIN を返さないこと（#136 / #216）は変えてはならない
- **FR-020a**: 従業員マスタの登録・更新で、PIN を省略できなければならない。登録では、省略・`null`・空文字は「PIN なし」として保存する。更新では、省略すると今の PIN を変えず、`null`・空文字を送ったときだけ PIN を消す（名前だけを直す更新で PIN が黙って消え、照合が外れるのを防ぐ）。PIN を指定した登録・更新はこれまでどおり受け付ける
- **FR-021**: すでにサインインしている端末へのサインインを断ること、サインアウトは変えてはならない

### Key Entities

- **従業員（Staff）**: 従業員コード・名前・役割・PIN（任意）。PIN は登録・更新でだけ受け取り、外へは出さない
- **照合の結果**: 成功なら PIN を含まない従業員の情報。失敗なら 3 種類の理由のいずれか
- **端末のサインイン状態**: サインインした従業員（PIN を含まない）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: PIN を登録した従業員について、正しい PIN 以外（誤り・なし・空）でのサインインは 100% 断られる
- **SC-002**: PIN が空の従業員について、これまで通っていたサインイン（従業員コードだけ）は 100% 引き続き通る。既存のクライアントは変更なしで動く
- **SC-003**: 失敗の 3 種類は、端末への応答では区別できない（エラーコードとメッセージが同じ）
- **SC-004**: PIN の値は、どの応答・どのログ（DEBUG を含む）にも現れず、端末にも保存されない。端末から送られる先はマスタの照合だけである
- **SC-005**: マスタに届かないときのサインインの失敗は、100% 認証の失敗とは別のエラーとして返る
- **SC-006**: PIN の比較が行われる場所はシステム全体で 1 か所だけである

---

## Assumptions

- 照合はサービス間の内部用で、端末やクライアントから直接は呼べない。端末からの入り口はサインインだけである。サービスアカウントのトークンを持つサービスなら、どのサービスからでも呼べる（terminal だけに限らない）
- 失敗 3 種類を同じ応答にしても、処理時間の違いや、従業員の取得 API（端末の資格情報で呼べる）から、従業員の存在と名前は調べられる。本フィーチャーが防ぐのは、PIN の有無と一致の度合いを応答から知られることだけである
- 試行回数の制限・ロックアウトが無いため、サインインを繰り返して PIN を総当たりされうる点は残る。これは別の Issue で、照合の 1 か所へ足す
- PIN の保存は平文のまま（ハッシュ化は別の Issue）。比較の 1 か所だけを差し替えれば移行できる
- 端末側の失敗のエラーコードは、新しく採番するか既存のサインインのエラーコードを使うかを計画で決める
- サービス間の資格情報（サービスアカウントのトークン）の発行・検査の仕組みは既存のものを使う

## Out of Scope

- PIN のハッシュ化と、既存の平文 PIN の移行
- 試行回数の制限・ロックアウト
- 端末のサインイン以外で PIN を照合する経路（係員承認など）
- 従業員バッジなど、PIN 以外の認証手段

## Behaviour Change

- PIN が入っている従業員について、PIN なし・誤った PIN のサインインが断られるようになる（これまでは従業員コードだけで通った）
- これまで従業員の登録・更新で PIN が必須だったため、PIN を使っていないテナントの従業員にもダミーの PIN が入っていることが多い。リリース後、そうした従業員はサインインに PIN が要る
- リリースノートで告知する: PIN を使わずにサインインさせたい従業員は、PIN を空にする（更新で `pin` に空文字または `null` を送る。省略では消えない）。PIN を使う従業員のクライアントは PIN を送る
