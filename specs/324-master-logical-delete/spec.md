# Feature Specification: すべてのマスタの論理削除（is_deleted）

**Feature Branch**: `324-master-logical-delete`
**Created**: 2026-11-23
**Status**: Draft
**SPEC_TYPE**: functional
**Issue**: [#324](https://github.com/kugel-masa/kugelpos-backend/issues/324)

---

## 概要

master-data のマスタの多くは物理削除で、削除するとレコードが消える。取引ログ・レポート・端末がそのコードを参照していても、そのコードが存在したか、何という名前だったかが分からなくなる。論理削除（`is_deleted`）を持つのは商品（既定は物理、指定すれば論理）とプロモーション（常に論理）だけで、やり方も揃っていない。

本フィーチャーは、削除できるすべてのマスタに同じやり方で論理削除を持たせる。

- **削除は論理削除が既定**: 削除しても記録は残り、通常の取得からは見えなくなる。物理削除は明示したときだけ
- **削除したコードは、もう一度登録すれば復元される**: 削除済みのレコードが新しい値で戻る（商品ブックを除く。商品ブックの ID はサーバーが採番する）
- **削除済みも取得できる**: 取得で「削除済みも含める」を指定したときだけ
- **どのマスタでも同じ名前・同じ挙動**

対象: 分類、商品（共通）、店舗別商品、商品ブック、支払、プロモーション、設定、従業員。税は読み取り専用（削除の操作が無い）ので対象外。

## Clarifications

### Session 2026-11-23

- Q: 削除の既定は？ → A: 論理削除。物理削除は明示したときだけ（論理削除済みのレコードも物理削除できる）
- Q: 削除済みのコードで登録されたら？ → A: 削除済みのレコードを復元し、登録の値を反映する（成功として扱う）
- Q: 削除済みも取得する指定の名前は？ → A: `include_deleted`（既定は含めない）。全マスタの単体・一覧の取得で同じ名前。商品の既存の `is_logical_deleted` は非推奨の別名として残す
- Q: 復元の専用の操作は要るか？ → A: 要らない。もう一度登録すれば復元される
- Q: 論理削除したものを自動で物理削除するか？ → A: しない。物理削除は明示したときだけ
- レビュー時の確認: report の名前の解決（分類・商品・支払）は本フィーチャーから外し、#326 で扱う。本フィーチャーだけでも report は今の物理削除と同じ結果（削除したものはコードで出る）で、悪くはならない
- レビュー時の確認: 商品ブックの ID はサーバーが採番する（登録の要求に ID が無い）ので、「登録で復元」は商品ブックには当てはまらない。商品ブックは論理削除するが、登録はいつも新しい ID になる。採番は削除済みの ID も使用中として扱う

## 影響するサービス

| サービス | 変更 |
|---|---|
| master-data | 全対象マスタの削除・登録・取得・更新を論理削除に対応させる |
| cart | 削除済みのマスタを販売・支払・プロモーション・設定に使わない（master-data の通常の取得が削除済みを返さないことに依る） |
| report | 変えない（名前の解決は #326） |
| terminal | 削除済みの従業員はサインインできない（#323 の照合で「従業員なし」） |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 削除してもマスタの記録が残る (Priority: P1)

運用者がマスタ（例: 商品）を削除する。通常の取得・一覧には出なくなり、販売などにも使われなくなるが、記録は残り、「削除済みも含める」と指定すれば取得できる。

**Why this priority**: 本フィーチャーの目的そのもの。削除で記録が失われ、過去の取引やレポートが参照するコードの意味が分からなくなる問題を止める。

**Independent Test**: 各対象マスタで 1 件登録して削除し、通常の取得で見つからない・一覧に出ない・「削除済みも含める」の取得では削除済みとして見える、を確かめる。

**Acceptance Scenarios**:

1. **Given** 登録済みの商品 A、**When** A を削除する（指定なし）、**Then** A の通常の取得は「見つからない」、一覧に A は出ない
2. **Given** 削除済みの A、**When** 「削除済みも含める」を指定して取得する、**Then** A が削除済みの印付きで返る
3. **Given** 削除済みの A、**When** 「削除済みも含める」を指定して一覧を取得する、**Then** A が削除済みの印付きで含まれる
4. **Given** 削除済みの A、**When** A を更新しようとする、**Then** 「見つからない」として断られる（削除済みは更新できない）
5. **Given** 削除済みの A、**When** A をもう一度削除する（指定なし）、**Then** 「見つからない」として断られる
6. 上の 1〜5 が、分類・商品（共通）・店舗別商品・商品ブック・支払・プロモーション・設定・従業員のすべてで同じように成り立つ（商品ブックの単体の取得・詳細の取得を含む）

---

### User Story 2 - 削除したコードをもう一度登録すると復元される (Priority: P1)

運用者が誤って削除した、あるいは使うのをやめたコードを再び使いたい。同じコードで登録すれば、削除済みのレコードが新しい値で戻る。

**Why this priority**: 論理削除にすると、削除済みのレコードがコードを占め続ける。登録で復元できなければ、そのコードは二度と使えない（今の商品では、論理削除したコードを登録すると重複のエラーになる）。

**Independent Test**: 商品ブックを除く 7 種類のマスタで、登録→削除→同じコードで別の値を登録し、成功して新しい値で取得できることを確かめる。

**Acceptance Scenarios**:

1. **Given** 削除済みの商品 A（名前「旧」）、**When** A を名前「新」で登録する、**Then** 登録は成功し、通常の取得で A が名前「新」・削除済みでない状態で返る
2. **Given** 削除されていない A、**When** A を登録する、**Then** これまでどおり「すでに存在する」として断られる
3. **Given** 削除済みの A、**When** 復元の登録で、前の値のうち要求に無い項目がある、**Then** 前の値は残らず、要求の値（と既定値）だけになる（作り直しと同じ結果）
4. 上の 1〜3 が、商品ブックを除く 7 種類のマスタで同じように成り立つ
5. **Given** 商品ブックを削除した、**When** 商品ブックを登録する、**Then** 新しい ID で作られる（削除済みの ID は再利用されない）

---

### User Story 3 - 物理削除は明示したときだけ (Priority: P2)

運用者が誤登録などを完全に消したい。物理削除を明示したときだけ、レコードが消える。論理削除済みのレコードも物理削除できる。

**Why this priority**: 記録を残すのが既定になる一方、不要なデータを消す手段は要る。

**Independent Test**: 物理削除を指定して、削除されていない・論理削除済みの両方のレコードが消え、「削除済みも含める」でも見つからないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 削除されていない A、**When** 物理削除を指定して削除する、**Then** A は「削除済みも含める」でも見つからない
2. **Given** 論理削除済みの A、**When** 物理削除を指定して削除する、**Then** A は「削除済みも含める」でも見つからない
3. **Given** 存在しないコード、**When** 物理削除・論理削除のどちらで削除しても、**Then** 「見つからない」として断られる

---

### User Story 4 - 他のサービスが削除済みのマスタを正しく扱う (Priority: P2)

削除済みのマスタは、販売（cart）・サインイン（terminal）では使われない。

**Why this priority**: 論理削除にしても、他のサービスが削除済みを使ってしまえば意味がない。

**Independent Test**: 商品・支払・プロモーション・設定・従業員を削除し、cart で使えない・terminal でサインインできないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 削除済みの商品 A、**When** cart で A を販売しようとする、**Then** 存在しない商品として断られる（キャッシュの有効期間の後、またはキャッシュを無効にした後）
2. **Given** 削除済みの支払方法 P、**When** cart で P で支払おうとする、**Then** 存在しない支払方法として断られる（同上）
3. **Given** 削除済みの従業員 S（PIN の有無を問わず）、**When** S として端末にサインインする、**Then** 存在しない従業員と同じ応答で断られる
4. **Given** 削除済みのプロモーション、**When** cart で対象の商品を販売する、**Then** そのプロモーションの割引は付かない（同上）
5. **Given** 削除済みの設定、**When** cart がその設定を使う、**Then** 設定が無いときと同じ既定値が使われる（同上）

---

### Edge Cases

- `is_deleted` の項目を持たない既存のレコードは「削除されていない」として扱う（データの移行は要らない）
- 削除済みのレコードは、一覧の件数（ページングの総数）にも含めない（「削除済みも含める」を指定したときは含める）
- 店舗別商品は、商品（共通）とは別のレコード。商品（共通）を削除しても、店舗別商品は自動では削除されない。店舗別の詳細（共通と店舗の合成）の取得は、商品（共通）が削除済みなら「見つからない」になる
- 商品ブックの中の分類・タブ・ボタンの削除は、1 つの文書の中の要素の削除なので、これまでどおり物理削除（本フィーチャーの対象は商品ブックそのもの）
- 支払方法を削除すると、その支払方法のサブコード（#311）も通常の取得からは見えなくなる。削除済みの支払方法へのサブコードの追加・変更は「見つからない」で、文書は変わらない。復元の登録では、サブコードは要求の値（省略なら無し）になる
- 削除済みの商品ブックの中の分類・タブ・ボタンの追加・変更・削除は「見つからない」で、文書は変わらない
- 更新と削除が同時に起きたときは、更新が「見つからない」になる（内部エラーにならない）
- テナントのセットアップを繰り返しても、論理削除された初期の設定は作り直さない（重複にならない）。初期の設定を戻したいときは、もう一度登録する
- 商品（共通）を削除しても店舗別商品は残るので、同じコードで商品（共通）を復元すると、残っていた店舗別商品（店舗の価格など）がまた効く
- 削除済みの設定は、cart から見て「設定が無い」と同じ（cart の既定値が使われる）
- 削除の応答・復元の登録の応答は、これまでの応答の形を保つ
- 同じコードへの同時の復元の登録は、1 つだけが成功するか、両方が同じ結果になる（重複のエラーで 500 にならない）
- 「削除済みも含める」は、取得の権限を持つ呼び出し元なら誰でも指定できる（既存の取得と同じ権限）

## Requirements *(mandatory)*

### Functional Requirements

> FR-014・SC-006（report の名前の解決）は #326 に移したので欠番。追跡のため、番号は振り直さない。

**削除**

- **FR-001**: 対象のすべてのマスタの削除は、指定がなければ論理削除でなければならない（レコードに削除済みの印を付け、記録は残す）
- **FR-002**: 物理削除を明示したときだけ、レコードを消さなければならない。論理削除済みのレコードも物理削除できなければならない
- **FR-003**: 存在しないコード、または論理削除済みのコードを論理削除しようとしたら、「見つからない」として断らなければならない
- **FR-004**: 存在しないコードを物理削除しようとしたら、「見つからない」として断らなければならない

**取得**

- **FR-005**: 通常の取得（単体・一覧・それに準ずる検索）は、削除済みのレコードを返してはならない。一覧の件数にも含めてはならない
- **FR-006**: 対象のすべてのマスタの単体・一覧の取得は、「削除済みも含める」の指定（`include_deleted`、既定は含めない）を受け付けなければならない。指定したときは削除済みのレコードも返し、どれが削除済みかが応答で分からなければならない
- **FR-007**: 商品（共通）の取得の既存の指定（`is_logical_deleted`）は、`include_deleted` と同じ意味の非推奨の別名として受け付け続けなければならない
- **FR-008**: 削除済みの印を持たない既存のレコードは「削除されていない」として扱わなければならない

**登録・更新**

- **FR-009**: 論理削除済みのコードで登録されたら（商品ブックを除く。商品ブックの ID はサーバーが採番し、削除済みの ID も使用中として扱う）、そのレコードを削除されていない状態に戻し、登録の値で置き換えて、成功として応答しなければならない。前の値のうち要求に無いものは残してはならない
- **FR-010**: 削除されていないコードでの登録は、これまでどおり「すでに存在する」として断らなければならない
- **FR-011**: 論理削除済みのレコードの更新は、「見つからない」として断らなければならない。レコードの中の要素（支払のサブコード、商品ブックの中の分類・タブ・ボタン）の追加・変更・削除も同じで、文書を変えてはならない。更新の途中で削除されたときも「見つからない」にしなければならない
- **FR-012**: 同じコードへの同時の登録（復元を含む）で、重複の衝突が内部エラーとして利用者に返ってはならない
- **FR-012a**: 復元したレコードは、新規に登録したときと同じテナント・店舗の情報を持たなければならない（復元したものがテナントの取得から消えてはならない）
- **FR-012b**: テナントのセットアップの初期データの投入は、論理削除済みのレコードも「存在する」として扱い、作り直してはならない

**他のサービス**

- **FR-013**: cart は、削除済みの商品・支払方法・プロモーション・設定を、販売・支払・割引・設定値に使ってはならない。master-data の通常の取得が削除済みを返さないことで満たし、キャッシュは既存の有効期間・無効化に従う
- **FR-015**: terminal のサインインは、削除済みの従業員を「存在しない従業員」として断らなければならない（master-data の照合の内部の応答は 404 / 405701、端末の応答は他の失敗と同じ 401 / 406004）

**変わらないもの**

- **FR-016**: 削除の応答・登録の応答・取得の応答の形（項目）は、削除済みの印を加える以外は変えてはならない。ただし、分類・プロモーションの一覧の応答の `metadata.filter`（絞り込みの条件をそのまま返している既存の項目）には、削除済みの絞り込みが現れる
- **FR-017**: 税マスタ、商品ブックの中の分類・タブ・ボタンの削除は変えてはならない

### Key Entities

- **マスタのレコード**: 分類・商品（共通）・店舗別商品・商品ブック・支払・プロモーション・設定・従業員。それぞれのコード（または名前・ID）で一意。削除済みの印（`is_deleted`）を持つ。印が無いものは削除されていない
- **削除済みの印**: 論理削除で付き、復元の登録で外れる。物理削除ではレコードごと消える

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 対象の 8 種類のマスタすべてで、指定なしの削除の後もレコードが残り、「削除済みも含める」で取得できる
- **SC-002**: 対象の 8 種類のマスタすべてで、削除済みのレコードは通常の取得・一覧・件数に 1 件も現れない
- **SC-003**: 商品ブックを除く 7 種類のマスタで、削除済みのコードでの登録が 100% 成功し、新しい値で取得できる（今の商品のように重複のエラーにならない）。商品ブックは、削除後の登録が新しい ID で 100% 成功する
- **SC-004**: 削除済みの印を持たない既存のレコードは、変更前と同じく 100% 取得できる
- **SC-005**: 削除済みの商品・支払方法・プロモーション・設定は cart で使われず、削除済みの従業員はサインインできない
- **SC-007**: 削除・取得の指定の名前と挙動が、対象の 8 種類のマスタすべてで同じである

## Assumptions

- 一意の索引は変えない。削除済みのレコードもコードを占めるので、同じコードの登録は復元になる
- cart のマスタのキャッシュは、既存の有効期間（既定 600 秒）と明示の無効化で更新される。削除を cart へ即時に知らせる仕組みは足さない（更新と同じ扱い）
- 「削除済みも含める」の取得は、既存の取得と同じ権限で呼べる
- 物理削除の指定は、既存の削除と同じ権限で呼べる
- 商品（共通）を削除しても、店舗別商品・商品ブックのボタンなど、そのコードを参照する他のマスタは自動では削除しない（参照先が削除済みなら、参照する側の利用時に「見つからない」になる）

## Out of Scope

- 削除済みのレコードの自動の物理削除（保存期間）
- 復元の専用の操作
- 削除の履歴（誰がいつ削除したか）の記録。削除時刻は更新時刻として残る
- 税マスタ
- 削除を cart のキャッシュへ即時に知らせる仕組み
- report の名前の解決（分類・商品・支払。#326）

## Behaviour Change

- **商品（共通）の削除が、指定なしで論理削除になる**（これまでは物理削除が既定）。完全に消すには物理削除を明示する
- **分類・店舗別商品・商品ブック・支払・設定・従業員の削除が、指定なしで論理削除になる**（これまでは物理削除だけ）
- **削除したコードをもう一度登録すると、成功する**（これまでは物理削除なら新規、商品の論理削除なら重複のエラー）。商品ブックは新しい ID になる
- **商品（共通）の取得の `is_logical_deleted=true` の意味が変わる**: これまでは削除済みの商品だけを返した（有効な商品は 404）。これからは `include_deleted` と同じく「削除済みも含める」
- **商品（共通）を復元すると、残っていた店舗別商品がまた効く**（店舗別商品は商品（共通）の削除に連動しないため）
- **分類・プロモーションの一覧の応答の `metadata.filter` に、削除済みの絞り込みの条件が現れる**
- **report**: 削除したマスタはレポートでコードで出る（今の物理削除と同じ。名前の解決は #326）
- リリースノートで告知する
