# Feature Specification: 精算を report が確定するスナップショットにする

**Feature Branch**: `343-settlement-snapshot`
**Created**: 2026-11-24
**Status**: Draft
**SPEC_TYPE**: functional
**Issue**: [#343](https://github.com/kugel-masa/kugelpos-backend/issues/343)

---

## 概要

端末の精算（閉設）は、今は次のように動いている。

- terminal が cart に取引の件数を問い合わせ、その件数を閉設ログに書く。理論在高も、数えた現金との過不足も、精算の時点で report にまだ届いていない取引も、どこにも残らない。
- report の日報は、**読むたびにその場で集計し直す**。精算のあとに届いた取引で、印字済み・電子ジャーナルへ送信済みの日報が変わる。
- 閉設ログの件数と report に届いた件数が合わないと、日報は 403（`412101`）で出せない。取引が1件遅れたり失われたりしただけで、その端末と店舗の日報が、誰かが手を入れるまで止まる。

本フィーチャーは、精算を「その時点で report が確定させ、二度と動かないスナップショット」にする。

- 端末は精算のときに report へ確定を頼む。report は、その時点で届いている取引と入出金から**精算実績**を作って1回だけ保存し、それを返す。届いていない取引は、精算を断る理由にせず、精算実績に「未着」として記録する。
- 精算実績には、その時点の日報（売上・部門・商品・支払・プロモーション）を凍結して持たせる（**確定集計**）。日報はこの確定集計から返す。
- 精算のあとに届いた取引は保存するが、確定した精算実績と確定集計を動かさない。
- 精算のレシートと応答に、理論在高・過不足・未着の件数を出す。

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 精算すると、その時点の精算実績が確定する (Priority: P1)

店員として、端末を精算したら、その時点の売上・現金の理論在高・数えた現金との過不足・まだ届いていない取引の件数が、レシートと記録に残ってほしい。精算は、取引が1件届いていないくらいで止まってはいけない。

**Why this priority**: 精算は毎日必ず行う業務で、ここで記録が残らない・止まることが、現状のいちばん大きな問題である。

**Independent Test**: 取引と入出金を行った端末を精算し、応答・レシート・精算実績の照会に、理論在高・過不足・未着の件数が出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 開設中の端末で現金の販売と入金を行った、**When** 数えた現金を入れて精算する、**Then** 精算は成功し、応答とレシートに理論在高・数えた現金・過不足が出て、同じ内容の精算実績が1件保存される
2. **Given** 端末が打った取引のうち1件が report にまだ届いていない、**When** 端末が打った件数を名乗って精算する、**Then** 精算は成功し、精算実績とレシートに「未着の取引 1件」と、その番号が記録される
3. **Given** 端末が件数を名乗らずに精算する、**When** 届いた取引の番号に飛びがある、**Then** 飛んでいる番号だけが未着として記録される（末尾の未着は分からないものとして扱う）
4. **Given** 数えた現金を入れずに精算する、**When** 精算実績を見る、**Then** 過不足は「数えていない」と分かる値で残り、0 にはならない
5. **Given** 精算が report で計算されたあと、端末の閉設が失敗した（通信の失敗など）、**When** その端末をもう一度精算する、**Then** 精算実績はその時点で計算し直され、1回目と2回目のあいだの販売・入出金も含まれる。端末が閉じて閉設ログが report に届いた時点で精算実績は確定し、そのあとは変わらない
6. **Given** 入出金ログの1件が report にまだ届いていない、**When** 精算する、**Then** 入出金の未着として記録され、レシートと応答に出る
7. **Given** すでに閉設した端末、**When** もう一度精算を送る、**Then** 今までどおり「すでに閉設」として断られる

---

### User Story 2 - 日報は精算の時点の値で固定される (Priority: P1)

店長として、精算したあとの日報は、何度見ても、精算のあとに遅れて取引が届いても、精算のときと同じであってほしい。また、1件の遅れで日報そのものが出せなくなってはいけない。

**Why this priority**: 印字した日報や電子ジャーナルに送った日報があとから変わると、帳票の信頼性が失われる。日報が止まると店舗の締め作業が止まる。

**Independent Test**: 精算したあとに、その営業の取引を遅れて届け、端末の日報・店舗の日報が精算のときと同じであることを確かめる。

**Acceptance Scenarios**:

1. **Given** 精算した端末、**When** 端末の日報（売上・部門・商品・支払・プロモーション）を見る、**Then** 精算実績に確定した値がそのまま返る
2. **Given** 精算のあとにその営業の取引が遅れて届いた、**When** 端末の日報を見る、**Then** 値は精算のときと同じで、遅れた取引は含まれない
3. **Given** 店舗の全端末が精算済み、**When** 店舗の日報を見る、**Then** 各端末の確定集計を合算した値が返る
4. **Given** 店舗の中に、取引や開設はあるが精算していない端末がある、**When** 店舗の日報を見る、**Then** 日報は出せず、精算していない端末が分かる形で断られる
5. **Given** 期間を指定した日報、**When** その期間に精算していない営業がある、**Then** 日報は出せず、精算していない営業が分かる形で断られる
6. **Given** 精算した端末、**When** 速報を見る、**Then** 速報は今までどおりその場で集計される

---

### User Story 3 - 精算の前に、確定するはずの内容を確かめられる (Priority: P2)

店員として、精算を確定する前に、理論在高と未着の取引を見ておきたい。過不足や未着に気づいたら、精算の前に調べられる。

**Why this priority**: 精算は1回しか確定しないので、確定の前に内容を見られると誤りを防げる。精算の確定そのもの（P1）があってこその機能。

**Independent Test**: 精算の前に確認の問い合わせを行い、何も保存されないこと、そのあと精算した結果と同じ内容が返っていたことを確かめる。

**Acceptance Scenarios**:

1. **Given** 開設中の端末、**When** 端末から精算の前の確認を問い合わせる、**Then** 理論在高・届いた件数・未着が返り、精算実績は保存されない
2. **Given** すでに精算した営業、**When** 確認を問い合わせる、**Then** 精算済みであることが分かる

---

### User Story 4 - 本部が精算実績を一覧で確かめられる (Priority: P2)

本部の担当者として、店舗の精算実績を、端末・営業・期間で絞って一覧したい。未着の取引があった精算や、過不足があった精算を見つけられる。

**Why this priority**: 精算実績は記録として残すだけでなく、見られて初めて役に立つ。ただし店舗の業務（P1）より後でよい。

**Independent Test**: 複数の端末・営業の精算のあと、店舗の精算実績を条件で絞って一覧し、期待した行が返ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 店舗で複数の精算が行われた、**When** 端末・営業日の範囲で絞って一覧する、**Then** 条件に合う精算実績が、営業日・端末・営業の順で返る
2. **Given** 多数の精算実績、**When** 件数を区切って一覧する、**Then** 指定した範囲だけが返る

---

### User Story 5 - report に届かないときは精算しない (Priority: P1)

運用者として、report に届かない状態で精算が進み、精算実績の無い精算ができてしまうのは困る。そのときは精算を断り、端末は開設のままにしてほしい。

**Why this priority**: 精算実績の無い精算は、日報が出せない営業を作る。断って開設のままにすれば、復旧のあとに普通に精算できる。

**Independent Test**: report を止めた状態で精算し、断られること、端末が開設のままであること、閉設ログが書かれていないことを確かめる。

**Acceptance Scenarios**:

1. **Given** report に届かない、**When** 精算する、**Then** 精算は「一時的に使えない」として断られ、端末は開設のまま、閉設ログも精算実績も作られない
2. **Given** report が復旧した、**When** もう一度精算する、**Then** 普通に精算できる

---

### Edge Cases

- **取引が1件も無い営業の精算**: 精算実績は作られ、件数 0、確定集計は空の日報になる
- **名乗った件数より多い番号が届いている**: 名乗った件数を超える番号も、届いた件数に含めて記録する。未着は 1〜名乗った件数の範囲で数える
- **同じ番号の取引が別のカートから2つ届いている**: 重複した番号として記録し、精算は断らない
- **取引の取消・返品**: 理論在高と確定集計は、今の日報と同じ扱いで数える（会計前に取り消したカートは売上に含めず、会計後の取消・返品は相殺する）。会計前に取り消したカートも番号を持つので、届いた件数と番号には含める
- **釣銭準備金**: 開設時の入金ログとして入っているので、理論在高に二重に足さない
- **精算のあとに届いた取引・入出金**: 保存はされるが、精算実績・確定集計・日報を変えない
- **確定集計の一部の種類が作れなかった**: 精算実績を保存せず、精算を「一時的に使えない」として断る。端末は開設のままで、もう一度精算すれば5種類がそろう
- **精算を同時に2回送った**: 端末を閉じられるのは1つだけで、もう一方は「すでに閉設」として断られる。確定する精算実績は、閉じた方のもの
- **端末を登録し直した**: 同じ営業日・同じ開設の回数の営業が2つあっても、精算実績と確定集計は混ざらない
- **カートが運ぶ番号とサーバー側の番号が同じ営業に混ざる**: 未着と重複は、カートが運ぶ番号だけで数え、サーバー側の番号の取引は件数だけ数える
- **対象の営業が1つも無い日報**: 空の日報を返す（今と同じ）
- **閉設ログが report にまだ届いていない**: 精算実績は確定していないので、その営業の日報は「精算していない」と同じ扱いになる（閉設ログは未配信の再送で届く）
- **このフィーチャーより前に精算した営業**: 精算実績が無いので、その営業の日報は「精算していない」と同じ扱いになる（後方互換の節）
- **既存のテナント**: 新しい記録とその索引が、テナントを作り直さなくても使える

## Requirements *(mandatory)*

### Functional Requirements

**精算の確定**

- **FR-001**: 端末の精算は、閉設ログを書く前に report へ精算の確定を頼まなければならない。依頼には、営業を特定する情報（営業カウンタ・営業日・開設回数）と、数えた現金（任意）と、端末が打った取引の件数（任意、「名乗った件数」）を含める
- **FR-002**: report は、その時点で届いている取引と入出金から精算実績を作り、営業（テナント・店舗・端末・営業カウンタ）ごとに1件だけ保存しなければならない。精算実績は、その営業の閉設ログが report に届くまでは「仮」で、もう一度精算が依頼されたら計算し直して置き換える。閉設ログが届いたら「確定」し、そのあとは変えず、依頼には確定した精算実績を返す。精算実績の計算は、すべて同じ時点のデータを読んで行う
- **FR-003**: 精算実績は少なくとも次を持たなければならない: 営業を特定する情報、状態（仮・確定）、精算した人と日時、名乗った件数とその有無、届いた件数（カート単位で数える）、届いた番号の範囲、未着の番号とその件数、重複した番号、入出金の件数と入出金の未着の件数、理論在高とその内訳、数えた現金、過不足、確定集計
- **FR-004**: 未着の番号は、名乗った件数があれば 1〜名乗った件数の中で届いていない番号とし、無ければ届いた番号のあいだの飛びだけとしなければならない。report は名乗った件数を自分で推定して補ってはならない
- **FR-005**: 未着・重複・件数の不一致を理由に精算を断ってはならない。記録として残す
- **FR-005a**: 端末は精算の依頼に、自分が記録した入出金の件数を含めなければならない。report は、届いた入出金の件数との差を入出金の未着として記録する
- **FR-005b**: 未着と重複は、カートが運ぶ番号（営業の中で 1 から振られる）の取引だけで数えなければならない。サーバー側で振った番号の取引は件数だけを数える
- **FR-006**: 過不足は「数えた現金 − 理論在高」とし、数えた現金が無いときは「数えていない」と分かる値にしなければならない（0 にしない）
- **FR-007**: 理論在高は、売上レポートの現金の欄と同じ式で求めなければならない（現金の売上＋入金＋出金。釣銭準備金は開設時の入金として含まれる）。この式は1か所に置き、精算実績と売上レポートの両方が使う
- **FR-008**: 精算実績の確定集計として、売上・部門・商品・支払・プロモーションの5種類の日報を、精算の時点の値で、件数の区切りなしに保存しなければならない。確定集計はその営業だけのデータで作る（同じ営業日・同じ開設の回数の別の営業を含めない）。1種類でも作れなければ、精算実績を保存せずに精算を断る
- **FR-009**: 精算の確定のあとに届いた取引・入出金は保存するが、精算実績と確定集計を変えてはならない

**端末の精算**

- **FR-010**: report に届かない・report が失敗した・report が精算を確定できないときは、精算を「一時的に使えない」として断り、端末を開設のままにし、閉設ログを書いてはならない
- **FR-011**: 精算の応答とレシートは、理論在高・数えた現金・過不足・未着の件数を出さなければならない。未着が1件以上あるときは、レシートに「未着の取引 N件」を、入出金の未着が1件以上あるときは「未着の入出金 N件」を出す
- **FR-012**: 閉設ログは、精算実績の理論在高と過不足を持たなければならない。閉設ログの取引の件数・最後の番号は、端末が名乗った値とし、名乗りが無ければ空にする。terminal は精算のために cart へ取引を問い合わせない
- **FR-013**: 精算の要求の「名乗った件数」は任意とし、送らない既存のクライアントは今までどおり精算できなければならない
- **FR-014**: すでに閉設した端末への精算は、今までどおり「すでに閉設」として断らなければならない。同じ端末の精算が同時に届いたときは、1つだけが端末を閉じる

**日報**

- **FR-015**: 端末の日報は、その営業の確定集計を返さなければならない。精算実績が無いときは「精算していない」として断る
- **FR-016**: 店舗の日報と期間を指定した日報は、対象の営業の確定集計を合算して返さなければならない。対象の中に精算していない営業（開設・取引・入出金のいずれかがあり、確定した精算実績が無い営業）があれば断り、どの端末・営業が精算していないかを応答に含める。対象の営業が1つも無ければ、空の日報を返す
- **FR-017**: 日報の応答は、未着の件数と番号を含まなければならない
- **FR-018**: 速報は、今までどおりその場で集計しなければならない
- **FR-019**: 日報を作る経路から、今の「件数を照合して確定する」仕組みを外さなければならない。既存のその記録は消さない

**照会と確認**

- **FR-020**: 本部の利用者は、店舗の精算実績を、端末・営業カウンタ・営業日の範囲で絞り、件数を区切って一覧できなければならない。並びは営業日・端末・営業の順とする。一覧に確定集計の本体は含めない
- **FR-021**: 端末は、terminal を通して、精算の前に精算と同じ計算の結果（理論在高・届いた件数・未着など）を、何も保存せずに問い合わせられなければならない。すでに確定した精算実績があれば、そのことが分かる
- **FR-022**: 精算の確定と精算前の確認は、サービス間の認証でしか呼べてはならない。店舗の利用者や端末から直接呼べてはならない

**エラーと運用**

- **FR-023**: 日報の「精算していない」は既存のエラーコード `412101` の意味として扱い、精算実績が見つからないことは `413007`、精算の確定の集計に失敗したことは `413008` としなければならない。端末の精算で report で確定できないことには、端末のエラーコードを新しく1つ割り当てる。エラーコードの一覧の文書を更新する
- **FR-024**: 新しい記録と、その照会・計算に要る索引は、既存のテナントでもサービスの起動時に整備されなければならない

### Key Entities

- **精算実績**: 1つの営業（テナント・店舗・端末・営業カウンタ）の精算を、その時点の値で記録したもの。1つの営業に1件。閉設ログが届くまでは「仮」で、届いたら「確定」して変わらなくなる。名乗った件数・届いた件数・未着・重複・入出金の件数と未着・理論在高とその内訳・数えた現金・過不足・確定集計を持つ
- **確定集計**: 精算実績の一部。精算の時点の5種類の日報（売上・部門・商品・支払・プロモーション）。端末の日報はこれを返し、店舗・期間の日報はこれを合算する
- **名乗った件数**: 精算のときに端末が申告する、その営業で打った取引の件数。任意。未着を 1 番から数えるのに使う
- **閉設ログ**: 既存。精算実績の識別子・理論在高・過不足・未着の件数を持つようになる。report は、精算実績の識別子を持つ閉設ログを受け取ったときに、その精算実績を確定する

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 取引が届いていない状態でも、精算は 100% 成功し、その件数がレシートと記録に出る
- **SC-002**: 精算のあとにその営業の取引が遅れて届いても、端末・店舗の日報の値は 1 円も変わらない
- **SC-003**: 1つの営業の精算実績は常に1件で、端末が閉じて確定したあとは、何度照会しても同じ内容が返る。閉設に失敗してやり直した精算では、やり直しまでの販売が漏れない
- **SC-004**: report に届かないときの精算は 100% 断られ、閉設ログも精算実績も残らず、端末は開設のままである
- **SC-005**: 精算実績の理論在高と、同じ営業の売上レポートの現金の欄が、すべての精算で一致する
- **SC-006**: 既存のテナントで、作り直しをせずに、次の営業から精算実績が作られる
- **SC-007**: 既存のテスト（unit / integration / e2e、cart の DUAL と REQUIRED）が、変更の意図に沿って直したもの以外は、そのまま通る

## 後方互換性

- **API**: 精算の要求に任意の「名乗った件数」を足すだけで、既存のクライアントはそのまま精算できる。応答とレシートには項目が増える。日報の応答には未着の項目が増える。精算前の確認の口を terminal に足す
- **日報の件数の区切り**: 日報（daily）は確定集計を丸ごと返し、件数の区切り（limit・page）を使わなくなる。daily で区切りを使っているクライアントには挙動の変化になる（意図した変更）
- **期間の日報の現金の欄**: 今は空だが、確定集計の合算で値が入る（意図した変更）
- **日報の挙動の変化**: 日報が「読むたびに集計し直す」から「精算の時点で確定した値」になる。精算のあとに届いた取引は日報に入らない。これは意図した変更である
- **このフィーチャーより前の営業**: 精算実績が無いので、日報は「精算していない」として断られる。配備のときに開設中の端末は、配備のあとに精算すれば精算実績が作られる。配備より前に精算を終えた営業の日報は、出せなくなる（Assumptions）
- **配備の順序**: report を terminal より先に配備する。terminal を先に入れると、report に確定の口が無いため精算が断られる
- **データ**: 既存の記録（閉設ログ・日報の照合の記録）は変えない、消さない

## Assumptions

- 取引の番号は、その営業の中で 1 から振られる（カートが運ぶ番号）。カートの互換の経路で振られる、端末全体で増え続ける番号の取引では、名乗った件数を送らない運用にする（送ると 1 番から数えた未着が誤る）
- 配備より前に精算を終えた営業の日報を、配備のあとに出す必要は無い（必要になれば、その営業の精算実績をあとから作る手段を別の issue にする）
- 精算実績は、1 か所（1つの report）で確定する。複数の拠点で同じ営業を精算する場合は扱わない
- 端末が二度と閉設しない営業（開設中のまま端末を消した、オフラインの営業、閉設ログが届かない）は、本部の利用者が届いたログで確定させられる（管理者の精算。PR のレビューで足した。利用者が選んだ、2026-11-25）
- 決済端末・電子マネーに関わる現金の扱いは、今の売上レポートの現金の欄に含まれていないので、精算実績にも含めない
- 精算実績の確定集計は、日報 5 種類を合わせても、1件の記録として保存できる大きさに収まる
- 精算の確定は、精算の要求の処理時間の中で終わる（日報 5 種類の集計を含む）

## Out of Scope

- 複数の拠点での精算、重なった精算
- 決済端末・電子マネーに関わる現金の扱い
- 精算のレシートの本文の作り直し（理論在高・過不足・未着の行を足すことを除く）
- このフィーチャーより前に精算した営業の精算実績を、あとから作ること
